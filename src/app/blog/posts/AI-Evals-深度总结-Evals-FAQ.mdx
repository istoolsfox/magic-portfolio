## 1. 一句话主旨

**evals 是把"我判断什么是好"系统化为可重复测试的工程，而其中最重要的活动是 error analysis（错误分析）——先读 100 条真实 traces 人工注释出失败分类，再决定测什么、用什么测。** 作者的项目经验：**60-80% 的开发时间应该花在看数据（error analysis + 评估）上**，而不是写基础设施。

## 3. 基础概念

- **AI evals 定义**：告诉团队"AI 系统是否在做你想要的事"的测试；捕获的失败反哺为改进数据。
- **两种 evals**：**Model benchmarks**（GPQA Diamond / Terminal-Bench / MMLU，选模型的起点）vs **Product evals**（测你自己的产品：模型+prompt+检索+工具+应用代码整体，捕获对用户和业务要紧的失败）。例：取消订单 agent 的 product eval 查"是否选对了订单、是否等取消工具成功后才告知用户"——GPQA 满分对此零信息量。
- **Trace**：从单次初始用户查询到最终响应的完整记录（所有消息、工具调用、检索、跨 agent/组件的中间步骤）。各家 vendor 对 trace/span 定义不一。
- **最小可行设置**：不做基础设施，先做 error analysis——**每次重大改动后，花 30 分钟人工看 20-50 条输出**；一个懂用户的领域专家当质量决策者；notebook 就够用。
- **预算**：评估是开发过程的一部分（像 debugging 不是独立条目）；简单断言能抓的错不值得建 evaluator，LLM judge 类投入前做成本收益分析。**警惕追求高通过率：100% 全过说明挑战不够，70% 通过率可能才是真正在压测系统**。

## 4. 方法论核心：Error Analysis 四步法（借用定性研究方法）

1. **Creating a Dataset**：收集代表性 traces；没有数据就先合成（见 §8）。
2. **Open Coding（开放编码）**：人工审查者写开放式笔记——像"写日记"。**先自己注满 30 条，再让 agent 提建议**（太早介入会带偏你的判断）；起步只注第一个失败（上游错误引发下游问题）；必须由领域专家做。
3. **Axial Coding（主轴编码）**：把开放笔记归类成 **failure taxonomy（失败分类法）**并计数——作者称这是最重要的一步；可用 LLM 辅助。
4. **Iterative Refinement**：agent 聚类选多样化样本→你审建议（accept/reject）→迭代到 **theoretical saturation（理论饱和：新审查不再产生新失败模式）**。~100 条多样化 traces 是这个人机循环的护栏值。

配套纪律（Lenny 文章同款，此处更完整）：
- **不需要预先的参考答案或 rubric**——先写 rubric 会挡住你看见预期之外的问题（criteria drift 是特性不是缺陷）；退款政策的例子：只有读过几条真实交互才发现"按政策升级人工"对用户其实很烦。
- **记录非模型的问题**：任何让产品变差的事都记（包括"没给追踪链接"这种功能缺失）；推迟根因分析，先聚焦"用户视角什么坏了"。
- **复核频率**：定期重跑 error analysis（频率取决于产品变化速度）。

## 5. 数据量三阶段量表（FAQ 独有的工程化细节）

| 阶段 | 做什么 | 数据量 |
|---|---|---|
| 1. 错误发现 | 读 traces 写失败笔记 | **100 条多样化 traces 起步，前 30 条必须纯人工**，到理论饱和 |
| 2. 建验证 evaluator | 客观规则→code-based eval（每条件配 Pass/Fail 例+边界例）；需判断→LLM judge，**每个 failure mode 标 100-200 条**（可信领域专家标注，两类样本都要） | LLM judge 标注按 10-20% train / 40-45% dev / 40-45% test 切分；dev/test 各含 30-50 条 Pass + 30-50 条 Fail |
| 3. 可重复 eval 集 | 代表性工作流+确认过的失败，改动时跑 | 通常长到 100+ 例 |

## 6. 评估设计原则

- **Binary（Pass/Fail）优于 1-5 打分**：打分的相邻点差异主观且标注者不一致、统计显著性需要更大样本、标注者躲在中间值逃避决策；binary 逼你做决定、error analysis 时更快。想追踪渐进改进？把"事实准确性 1-5"换成 5 个独立 binary 检查（"4/5 预期事实已包含"）。**先用 binary 理解什么是坏；数值标签是高级玩法且通常不必要。**
- **合并成单一指标**：用 **pass-all rate**（一条样本须通过全部检查才算过）+ 可下钻的分层报表；或按主题/严重度分组各报 pass-all（如"阻断发布组" vs "可容忍组"）。**反对复杂加权综合分**：3.2→3.7 的周环比让人自我感觉良好但不知道用户得到了什么改善——"这类仪表盘通常是表演性的，浪费所有人时间"。
- **反对 eval-driven development（先写 evaluator 再实现功能）**：LLM 的失败面是无穷的，你无法预想什么会坏；**为你发现的错误写 evaluator，不为你想象的错误写**。例外：约束明确的（"永不提竞品"）可以先写。
- **自动化 evaluator 成本层级**：简单断言/正则/结构校验/执行测试（便宜）→ 带参考答案的检查（便宜）→ LLM judge（贵：100+ 标注、每周维护、跨角色协调）。**只为"修 prompt 后仍持续存在、且会反复迭代"的失败建贵 evaluator**；很多偏好类问题（要短回复、要特定格式）根本是你没在 prompt 里说清楚——先修 prompt。
- **LLM judge 本质是分类器**：返回 Pass/Fail；可用强模型开发 judge prompt，再试小模型量化精度损失；**必须对照人工标注验证**（测 TP/TN 率，用其修正系统真实失败率估计）；优化 judge prompt 时留独立 test set 防过拟合。
- **通用现成指标批判**：平台推销的 generic metrics 多数误导（会把注意力从真实失败上引开）；BERTScore/ROUGE 等相似度指标对 LLM 输出基本无用。

## 7. Gold 数据集过期（你 URL 锚点的问题）

- 过期是自然规律：产品和用户在变，用定期 error analysis 找新问题、更新样例/参考答案。
- **像单元测试一样防回归，但比单元测试贵得多**：逐个 eval 权衡信号价值；**一切全过 = 该退役或降频**。
- **分数跨版本不可比没关系**：evals 的目的是提供"可以爬山挑战"的题目集，题目应随产品演进；长期趋势用产品指标（churn/活跃/收入）补充。

## 8. 合成数据（比 Lenny 文章细一档）

- **时机**：生产流量不足时启动 error analysis；或复现稀有失败。**合成数据永远无法告诉你"失败在生产中有多常见"**，真实数据一到就对比校准。
- **维度元组法**：先定义维度（食谱 app：饮食限制×菜系×复杂度；客服 bot：问题类型×客户情绪×上下文）→ **先手写 20 个元组**理解问题空间 → 两步生成：①LLM 生成结构化元组 ②**另一个 prompt** 把元组转自然语言查询（分离避免措辞同质化）。例：(Vegan, Italian, Multi-step) → "我需要一份可以前一天准备的免乳制品千层食谱"。
- **两种生成策略**：笛卡尔积+LLM 过滤（保覆盖，适合多数组合有效）/ 直接让 LLM 生成元组（更真实但偏 generic、漏稀有场景）。
- **先修明显问题再生成**：prompt 没提饮食限制就去修 prompt，别急着生成专项测试。
- **五种不可靠场景**：复杂领域内容（法律/医疗文书）、低资源语言方言、无法验证真实性、高风险领域、欠代表用户群（合成会放大 LLM 训练偏见）。

## 9. 敏感数据四级降级（按优先级）

1. 找允许看的真实数据（客户共享子集/测试用户授权）；
2. 自己看不了就让能看的领域专家在产品内顺手验证（设计好验证点：给证据链接、拆小审查单元——"最终答案是否有用"信息量太少）；
3. 脱敏/改写后共享（检查脱敏工具输出，确认改写保留了要评估的行为）；
4. 实在不行才用合成数据（最后手段）。

## 10. 工具与基础设施

- **自建 vs 现成**：优先 notebook 或用 AI coding assistant 快速搭自定义注释界面；现成平台对"少数分布式标注者+企业权限控制"的场景才有意义，即便那时很多团队也发现配置开销不值。
- **好的自定义审查界面四原则**：①智能渲染 traces 而非通用展示（按数据类型）②显示进度+键盘导航 ③聚类/过滤/搜索导航 ④优先推可能有问题 traces 给你标。总原则：**保持最小**。
- **平台四大缺口要有自己填的准备**：错误分析与模式发现、全流程 AI 辅助、自定义 evaluator（而非通用指标）、支持自定义注释 App 的 API。
- **内部 eval 平台该标准化什么**：prompt 版本管理、数据/标注存储、eval 运行与追踪；不该标准化：具体指标（各团队失败不同）。
- vendor 推荐见原文（作者保持"看你需求"的立场，给了对比视频）。

## 11. 生产化

- **CI vs 生产监控**：CI 里 evals 是改动后的回归门（阻断发布）；生产里监控漂移与新增失败模式；**两套要连起来**：生产监控发现的失败→进 CI eval 集。
- **guardrails vs evaluators**：evaluator 测量质量（离线/在线），guardrail 在线拦截危险输出——guardrail 可以复用 evaluator 的判定逻辑，但职责不同。
- **evaluator 可以兼职自动修复**：可以，但修复本身要被评估（否则修错比不修更糟）。
- 模型选型不值得花太多时间：error analysis 优先级永远更高。

## 12. 领域应用速查

- **Coding agent**：宽任务→公共基准（SWE-bench/Terminal-Bench/Aider Polyglot/HumanEval）+ 私有难任务基准（OpenAI Codex 用真实内部任务+可运行环境+代码测试判定）；窄工作流→product evals。Anthropic 指南：先明确定义任务+稳定环境+单元测试可验证，再补单元测试测不到的（代码质量、交互）——Claude Code 团队就加了 file edits 和 over-engineering 的 evals（起步指标：净新增代码行数、圈复杂度）。**GitHub Copilot 做法**（John Berryman & Shawn Simister 演讲，t=534s 起）：代码补全=删掉仓库里的函数实现让模型重生成+跑现有测试；聊天=带具体判据的 LLM judge+工具调用正确性独立检查；再加 A/B（用户是否接受建议并保留代码）。
- **RAG**：拆两半。检索=搜索问题用 IR 指标（Recall@k/Precision@k/MRR），数据集可反向合成（从文档抽事实→生成能被该事实回答的问题）；生成=error analysis→LLM judge→对人工标注验证。参考 Jason Liu "只有 6 种 RAG evals"框架（Tier1=IR 指标；Tier2/3=Q/C/A 关系：C|Q 上下文相关、A|C 忠实、A|Q 对题），但**领域特有失败（成人 vs 儿童剂量、司法辖区混淆）只有看自己的数据才能发现**；Tier2/3 的 judge 别用现成 prompt，走完整验证流程。
- **Chunk 大小**：文档处理≠RAG。固定输出任务（抽取/问答/分类）→大块（减少查询数、避免上下文碎片化，但注意中间内容注意力不足+干扰敏感）；扩展输出任务（摘要/改写）→小块。成本/延迟敏感时先预处理过滤。
- **多轮对话调试**：注第一个失败；多 agent 系统按 agent 分段记录；优先简化系统而非堆 evals；从真实失败生成测试用例。
- **Human handoff 会话**：评估切两段（AI 段+交接决策点），交接时机和交接质量分开评。
- **Agentic workflow**：每步工具调用单独测（参数正确性/时机），再测端到端；复杂工作流先拆可独立验证的子任务。

## 15. 与 omniscient-agent 的关联（自用视角）

1. **`eval_knowledge.py` 的定位升级**：27 条话术回归 = Stage 3 可重复 eval 集的雏形；按 FAQ 口径下一步是 Stage 1——人工读 100 条 `chat.jsonl` 做 open coding（倾听误判/共情错位/知识注入错题各归一类），axial coding 出陪伴失败分类法；
2. **binary 原则直接可用**：`test_guard` 注入样本库已经是 pass/fail 口径（46 条全 Pass 才算过）= pass-all rate 的实践，方向正确；
3. **警惕"全绿陷阱"**：79/99 测试全绿 + eval_knowledge 78% hit@3——FAQ 的"70% 通过率才健康"提醒：游戏行为分析、decider 决策质量都还没有任何"会失败的测试"；
4. **guardrails vs evaluators 区分**：`core/safety.py`/`crisis.py` 是 guardrail（在线拦截），`eval_knowledge.py` 是 evaluator（离线测量）——两层都该有，且生产失败（如危机识别漏判）应回流成 CI 用例。
