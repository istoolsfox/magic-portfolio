# 深度总结：Advanced Evals —— 如何发现（并修复）产品中隐藏的 AI 失败

## 0. 一句话主旨

**做 evals 最大的错误是跳过"错误发现"（error discovery）直接写指标。** 错误发现之于 evals，就是产品发现之于产品管理——它决定你测什么。这套方法论给出三步人机协作流程（收集 traces → 审查注释 100 条 → 聚类成优先级清单），配合免费的开源 skill 插件，一个 coding agent 约 30 分钟就能带你跑完。

- **头部公司实证**（都公开了博客，原文带链接）：
  | 公司 | 成果 |

- **根本原因**：AI 产品"好改但难预测"——改一个 prompt/模型/代码，可能修好一个行为同时弄坏另一个。evals 把你对"什么是好"的判断变成可重复的测试；生产错误反哺为测试用例，形成**复利优势**。且现在 AI 产出变更的速度已超过人工 review 的速度，evals 是快速发布的自动把关机制。

## 2. 核心论点：error discovery = eval 流程中的 product discovery

- 两位作者与前作的框架：完整 eval 流程 = **发现并分析错误 → 定制指标 → 持续改进循环**。但他们服务 50+ 公司发现：**绝大多数团队跳过第一阶段直接写指标**。
- 为什么会跳过：翻长长的会话记录找失败"显得又慢又难规模化"，而指标具体、可自动化。
- 为什么要害：指标写早了 = 对"什么重要"做了过多假设 → **测错东西，或用错的方式测对的东西**。没有错误发现，团队会围绕通用指标做仪表盘，浪费时间和方向。
- **原句**：*"If you only have time for one part of the eval process, prioritize error discovery."*
- 术语演变：前作叫 "error analysis"，本作改名 **"error discovery"**——强调目标是"识别值得测量的失败"，而非穷尽分析。
- 作者声称：这套流程他们在 50+ 公司用过，**每次都挖出伤害客户体验的重大产品缺陷**；学会后整个流程约 30 分钟。

## 3. 为什么不能把错误发现全交给 Agent —— criteria drift

**criteria drift（判据漂移）**：在审查数据的过程中，你对"什么是好"的定义本身在变——很多标准只有看过数据才知道该有（原文引用了 arXiv 2404.12272）。Agent 可以被告知标准，但**发现标准本身只能靠人看数据**。

### 3.1 案例深挖：Nurture Boss（AI 租赁助手）的"表面成功"

> 租客："这超出我的预算了，谢谢你的服务。"
> 助手："不客气！如果以后情况有变或有任何问题，随时联系。祝你有美好的一天！"

- **任何 agent 都会判这是成功对话**：礼貌、完整、无错误。
- 但产品目标是促成销售：正确行为是**推荐更便宜的单元、或同公司其他房源**——这是 objection handling 失败。
- 关键推理链：如果**事先**在 prompt 里写了"检查 objection handling"，agent 确实能自动抓到这个错——但你只有**亲自看过这条 trace 之后**才知道该把"objection handling"加进判据。这就是 criteria drift 的经典呈现，也是"必须人先看数据"的铁证。

### 3.2 100 条生产 traces 的自动化研究（三条结论）

作者对同一租赁助手的 100 条生产 traces 跑自动化 eval 工具和 coding agent（原文附研究链接）：

1. **Agent 漏掉需要产品判断、或依赖 trace 之外上下文的问题**：短信里输出 Markdown 格式、该转人工没转（human handoff）、objection handling；
2. **Agent 擅长抓 trace 内显而易见的失败**：如答案与工具输出直接矛盾；
3. **Agent 也会发现人漏掉的问题**，但带来噪声——会把好回复标成失败。

结论：自动化有用，**尤其在与人判断结合时**。方案是借鉴 **active learning**：时间有限时优先审查信息量最大的样本——先看多样化样本覆盖数据全貌；发现一类失败后，多看几个同类实例确认理解；审够了再让 agent 批量注释、人来接受/拒绝。这些簿记和采样工作正是 coding agent 擅长的。

## 4. Step 1：Start with your traces（先有 traces）

**Trace 定义**：一条完整用户会话记录 = 用户输入 + system prompt + 中间发生的一切（检索、工具调用及结果、中间模型调用）+ 最终面向用户的输出。**信息量标准：审查者能据此重建发生了什么、并判断好坏**。存储随意：数据库 / eval 供应商（LangSmith、Arize、Phoenix、Langfuse）/ 本地文件夹（本文为简单起见用本地）。

### 4.1 没埋点？让 coding agent 现在埋（prompt 原文）

> *Instrument this app so every user session with the AI is logged as one complete trace.*
> *A trace is one user session. Include the user input, the system prompt, every tool call and its result, any retrieved context, every intermediate model call, and the final user-facing output.*
> *If this app already sends traces to a vendor (LangSmith, Arize, Phoenix, Langfuse, or similar), keep using that. Also write a local copy: one JSON object per session, appended to traces/traces.jsonl. If there is no vendor, the JSONL file is enough.*

要点：每个会话一个 JSON 对象、追加写入 `traces/traces.jsonl`；已有供应商则双写。

### 4.2 没上线？合成 traces 的"维度法"

合成数据**不能替代真实数据，但好过没有**。方法：

1. **定义维度**——预判产品可能失败的轴：租赁助手例 = 任务（约看房/问价格/问宠物政策）× 租客类型（首次租房者/搬家的家庭/学生）× 请求类型（清晰/含糊/超范围）；
2. **逐场景单独调用**——agent 把维度值组合成场景（每维取一值），**每个场景单独一次模型调用**，强制结构化输出单字段 `user_query`，存 `synthetic_queries.jsonl`（prompt 原文在原文存档 §Pro tip）；
3. **为什么逐个调用**：一次性让模型批量生成会导致**同质化**，这是作者实测经验；
4. **事后处理**：人工过一遍，删掉不真实的；发现维度没覆盖的场景就补维度重新生成。
5. 示例输出：`{ "user_query": "We have two dogs and may be moving next month. Would that work?" }`

**作者立场**：高质量合成数据（尤其多轮对话）超出本文范围；**能拿到真实用户就用真实用户**；实在要用合成数据，附录有配套 skill。

## 5. Step 2：Review and annotate（审查与注释）——流程核心

### 5.1 evals-skills 插件

基于教 4500+ PM/工程师 + 咨询 50+ 公司的经验做的免费插件：

```bash
npx skills add https://github.com/ai-evals-course/evals-skills
```

然后对 coding agent 说：

> *"Use the evals-start skill. My traces are in traces/traces.jsonl and I want to find issues occurring in my AI product."*

`evals-start` 是路由入口，按你的处境分发到对应工作流（此处 → `error-discovery`）。

### 5.2 自动生成定制化审查界面（插件最大价值之一）

`error-discovery` 先抽样读 schema，然后**为你的数据定制生成本地审查 App**：

- 租赁助手：渲染成**消息流**，工具调用及输出并列显示，注释写自由文本框；
- 写作助手：渲染成**文本块 + 旁边标 flags**——不同数据类型配不同界面。

两条界面设计原则：

1. **按用户看到的样子渲染面向用户的输出**（邮件长得像邮件、PDF 渲染成 PDF）；
2. **暴露对导航/过滤重要的元数据**（如租赁场景的渠道：SMS / voice / web chat 值得过滤）。

插件还会**先聚类 traces 构建多样化初始样本**（聚类代表 + 随机抽取混合），比朴素抽样更好的起点；界面可 hover 看聚类代表文档。

**coding agent 的杀手锏：界面随聊随改**——缺字段、想过滤某个切片、想换渲染方式，直接说。例如合成数据场景下按 persona/任务类型建过滤器，检查某类失败是否集中在特定场景。

### 5.3 注释纪律（四条规则，每条都有为什么）

先看示例注释："助手放弃了而不是提供替代方案" "没渲染排期组件、给了个时间列表" "这个 persona 下语气太正式"。

1. **写到同事（或 agent）能看懂**："Bad response" 是坏注释；"助手说单元可租但工具输出显示已租出" 才可执行；
2. **不做根因分析**：找的是**用户视角的什么坏了**，不是系统内部为什么坏（别去诊断检索问题）；
3. **在第一个上游错误处停下**：一条 trace 有多个问题时只注第一个——上游失败通常比下游重要，省时间聚焦高影响问题（熟练后可放宽）；
4. **起步只注失败**：注"好在哪"能帮 agent 理解，但时间紧可跳过。

### 5.4 人机循环：10 条起步 → 100 条目标

- **先人工注 10 条，agent 才开始提建议**——这是对 **automation bias** 的刻意防护；
- 对 agent 的早期建议**不要盲收**：仔细审，用分歧修正 agent 的工作理解，通常需要数轮人机迭代后建议才变可靠（插件界面支持逐条 accept/reject，也有按 failure mode 分组的建议视图）；
- **继续注到自己的学习平台期**，经验值 **100 条**——既防自己过早退出，也给 AI 更多信号改进建议；
- 注释**不必完美**：目标是找到可行动的问题，不是穷举。

## 6. Step 3：Turn failure modes into product priorities（付费墙前可见部分）

- 攒够 **100 条多样化注释** 后，任务变成把注释变成**带优先级的产品问题清单**；
- AI 把注释**聚类成 failure modes 并计数**，让你看出模式（租赁助手示例截图在付费墙内，公开部分到此截断）；
- 推断的完整流程（付费墙内，此处为结合作者公开博客 hamel.dev 的补充线索，非本文付费内容）：failure modes → 为每类写指标/测试 → LLM-as-judge 需要每类 100-200 条标注样本。**此段请勿当作本文原文引用。**

## 7. 可执行清单（从零到优先级清单，约 30 分钟）

1. ☐ 有 traces 吗？没有 → 把 §4.1 埋点 prompt 丢给 coding agent；
2. ☐ 没上线 → §4.2 维度法生成 synthetic_queries.jsonl，人工删不真实的；
3. ☐ `npx skills add https://github.com/ai-evals-course/evals-skills`，让 agent 走 evals-start → error-discovery；
4. ☐ 检查自动生成的审查界面：输出是否按用户视角渲染？关键元数据可过滤吗？不满意就聊着改；
5. ☐ **人工先注 10 条**（遵守 §5.3 四规则），再放 agent 提建议；
6. ☐ 逐条 accept/reject agent 建议，用分歧修正它，数轮迭代；
7. ☐ 注到 ~100 条或学习平台期；
8. ☐ 让 agent 聚类注释 → failure modes + 计数 → 排出产品优先级清单。

## 9. 批判性视角（读时保持清醒）

1. **"30 分钟"是熟练后的下限**：首次跑（埋点 + 学插件 + 100 条注释）远不止 30 分钟——100 条人工注释本身就是数小时量级的活；
2. **合成数据的局限作者自己承认**：不能替代真实数据，多轮对话合成是未解难题；
3. **聚类采样"not perfect"**：作者原话，初始样本策略只是"比朴素抽样好"；
4. **利益相关**：文章是课程的引流内容（插件免费但深度内容在课程里）——方法论本身扎实（50+ 公司实证 + 三条结论有真实研究支撑），但注意区分"免费可得的"与"要花钱学的"；
5. **criteria drift 是双刃剑**：文中把它当核心洞察，但也意味着注释中途标准在变，早期注释可能与后期不一致——实践中可能需要回头复核前 10-20 条（文章未展开此点）。

## 10. 金句摘录

> "Error discovery is the eval equivalent of product discovery. Just as product discovery shows which problems are worth solving, error discovery reveals which AI failures are worth measuring."

> "If you write metrics too early, you end up making too many assumptions about what's important—and potentially measuring the wrong thing, or the right thing poorly."

> "'Bad response' is a bad annotation. 'The assistant said the unit was available when the tool output showed it was leased' is actionable."

> "Evals turn your judgment about what 'good' looks like into repeatable tests your team can run before shipping."

## 11. 与 omniscient-agent 的关联（自用视角）

1. **现成的 traces**：`sessions/chat.jsonl`、`games/*.jsonl` 就是标准 traces（用户输入 + 工具调用 + 输出）——只差"审查界面"一步；
2. **已有同构实践**：`eval_knowledge.py`（27 条话术回归）= 第 2 层指标；注入样本库 v2（46 条攻击模板 + 多轮社工渐入）本质就是"failure modes 测试集"；缺的正是第 1 层——**人工读 100 条真实陪伴对话、注释聚类出陪伴失败模式**（如"倾听决策误判""主动关怀打扰""共情时机错位"），那才是陪伴质量的 error discovery；
3. **可立即偷的设计**：注释四规则、10 条人工先行防 automation bias、"第一个上游错误"停笔法——直接适用于游戏行为分析和对话质量审查脚本。
