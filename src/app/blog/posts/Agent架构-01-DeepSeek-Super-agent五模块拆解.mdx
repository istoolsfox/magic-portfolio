# 让 Agent 持续在线、同时干多件事：DeepSeek Super-agent 五模块拆解

> 你手上同时有三件事：一个 PR 等评审意见，一个 bug 要复现，一封邮件要回。每件事开一个 Agent 会话，你在三个窗口之间切换，还得记住哪个窗口里说过什么。Agent 做单个任务已经很强，可你能同时盯住的会话就那么几个。DeepSeek Harness 团队观察到的数字是 3 到 5 个。瓶颈从模型能力挪到了人的注意力。他们在 2026 年 10 月 31 日发了一篇架构文章，讲怎么把 Agent 从"一个会话做一件事"改成"一个 Agent 持续在线，同时推进多件事，彼此不干扰"。本文把这篇文章拆开讲清楚。全文不用比喻，只讲机制。

## 一、结论先行

原文叫《Super-agent 设计探索：迈向更自主的 Agent 系统》，DeepSeek Harness 团队 2026-10-31 发布于微信公众号，系统实现和写作由 Yujia Qiao 完成（[原文链接](https://mp.weixin.qq.com/s/zoS7GlReWPhfCjENGxXCdg)）。作者开篇就声明：这是面向工程实践的架构思路探讨，不是产品功能介绍。

配套原型 [dsh-superagent-prototype](https://github.com/deepseek-ai/dsh-superagent-prototype) 同一天开源，MIT 协议，TypeScript 约 1.2 万行。原型仓库的 README 写得很直接：它不等于内部版本，文章里讨论的部分设计是未来方向，原型没有实现。

一句话概括这篇文章：**把 Agent 和"一次手动会话"解绑。底层用五个模块接管会话管理、事件处理、上下文同步和故障恢复，用户面对的始终是同一个 Agent，而不是一堆会话。**

作者给这种 Agent 定了四个基础特征。连续：用户在 IM 聊天和 GitHub 评论里和它交互，感觉只有一个 Agent，不用去想"某个会话里有没有某条信息"。高效：响应快，能并行完成多个复杂任务，不用等上一条命令完成就能接下一条。主动：持续观察环境事件，值得处理的就推进，不需要介入时保持安静。持久：始终在线，接入真实工作环境，长期运行中遇到异常自动恢复。

成绩单来自文中的合成负载实验（作者自己说"仅作初步参考"）：Super-agent 方案的任务完成时间 p50 是 12.4 分钟，p95 是 15.7 分钟；对照的"单会话加子代理"方案在中性提示下 p95 达到 29.5 分钟。代价是 token，Super-agent 单次实验的读缓存 token 是 2323 万，单会话方案是 605 万。

先说清楚：文中所有数字都是原文自述，实验基于合成负载和简化环境，没有第三方复现。这不影响架构思路的参考价值，引用时注明出处即可。

## 二、先看问题：现在的 Agent 为什么做不到

Agent 的工作单位叫 Session，中文一般译作会话。一个 Session 的运行方式是：你输入一条提示，模型想一步，调一个工具，等工具返回，再想一步，再调一个工具，直到任务完成。这个循环叫 ReAct Loop。

这种设计有三个硬限制。第一，串行阻塞：工具没返回之前，这个 Session 接不了新指令。第二，Session 之间互相不知道对方：你在 IM 里说"用方案 A"，接着在 GitHub 评论里改成"方案 B"，两个 Session 各干各的。第三，本地设备停机即停：Agent Loop 跑在你的电脑上，电脑合盖，Agent 就没了。

作者把这个局面总结成一句话：单任务的上限取决于模型能力，多任务的上限取决于人的注意力。

作者还排除了一条看起来省事的路。在现有的本地单会话 Agent 上，用 CLI、MCP 或外部连接器做简单扩展，确实能让 Agent 接到外部消息。可是上面三个限制一个都没解决，还要大量人工维护。要突破限制，得从底层架构动手。

## 三、五个模块，每个解决一件事

作者给出的架构有五个模块。双层架构负责连续和高效，事件驱动负责主动，面向人的交互在交互层面同时保证连续和高效，计算、状态与环境的分离负责持久在线，Watchdog 负责异常自愈。

![Super-agent 整体系统架构，标号 2 到 6 对应原文第 2 到第 6 节](https://toolsfox.top/static/super-agent/03.jpg)

作者有一个贯穿全文的判断：这些问题和传统计算机系统长期研究的问题高度相似，所以经典设计思想可以直接拿来用。文中用到的有 Fast Path / Slow Path、批处理、缓存的 Inline / Spill、局部性、投机执行、存算分离、控制回路。下面逐个拆开。

## 四、模块一：双层架构，Router 层加 Worker 层

### 4.1 要解决的矛盾

会话怎么组织，两个极端都不行。所有事件进同一个 Session：上下文最连续，可是单个 ReAct Loop 串行执行，任务耗时长、吞吐低，多个任务的中间细节混在一起也影响完成效果。每条事件新开一个 Session：并发最高，可是任务之间不独立时结果彼此割裂，多个 Session 各自向用户回复，交互会乱。

作者把这两头的矛盾叫做连续性与吞吐量的根本权衡。解法是把"维护全局连续性"和"高并发执行"拆到两个层级。

![双层架构：Router 层统一负责路由与对外交互，多个 Worker Session 隔离并发执行任务](https://toolsfox.top/static/super-agent/04.jpg)

### 4.2 Router 层：只管交互和分派，不干活

Router 层是常驻的全局路由层。所有入口的人类交互都由它承接，跨任务的信息和决策都在它这里汇总。它是全局的序点、协调点和记忆。

关键约束是：Router 层不直接执行具体任务，只负责人类交互和任务分派，甚至可以不配 Bash 工具。这样它才不会变成性能瓶颈。作者从实践里得到的结论是，Router 层的任务没有想象中复杂，用较轻量的模型往往就能兼顾速度和效果。

这和常见的 Agent Team 有区别。Agent Team 里的 Team Lead 要深入理解单个任务的细节，规划子任务，高频协调成员，自己承担很重的推理负载。Super-agent 的 Router 层只处理任务之间的高层关联和分派，不介入单任务内部的拆解。反过来说，如果用提示词约束一个 Agent Team 的主会话"不亲自执行，只对外交互并把任务分派给成员"，那它也可以算作这种双层架构。

### 4.3 Worker 层：隔离上下文，专注一个任务

Worker 层由负责具体执行的会话组成。每个 Worker 上下文彼此隔离，挂载完整的执行工具，在独立上下文里专注完成单一任务。Worker Session 直接决定任务结果和代码质量，所以通常配能力最强的模型。

Worker 不直接和人交互。它的推理过程和工具调用不输出到外部信道，而是向 Router 层汇报状态，由 Router 层统一向用户回复。这样既保证并发度，又避免多个会话各自回复带来的混乱。

同层 Worker 之间通常不需要直接通信。多个 Worker 在同一个 PR 这类共享工作环境里发生冲突时，只要它们都订阅了对应的 Thread（下一模块会讲），就会收到相同的事件通知，有机会自己发现和解决冲突。少数跨任务协同由 Router 层中转。

Worker 内部也不限于单个会话。执行复杂任务时，Worker 内部可以再创建 Subagent，也可以本身就是一个 Agent Team。这些对上层的 Router 保持透明。

### 4.4 一个常驻 Router Session 够用吗：批处理

作者选了最直接的实现：单个常驻 LLM Session 做 Router 层。他们发现它不像表面看起来那么容易成为吞吐瓶颈，原因是批处理。

机制是这样的。Router 在做上一轮推理期间，新到的环境事件会积压下来，下一轮一并处理。Router 每一步都是长输入、短输出。把积压的多条事件合并进一次 LLM 调用，这些内容在 Prefill 阶段并行计算，单次请求耗时的增长远慢于批处理大小的增长。结果是积压越多，单个决定分摊到的推理时间越低。上限取决于上下文长度，以及模型一轮能准确处理多少条事件。

当事件流平稳时，事件逐条进入 Router，单次响应延迟低。当事件密集涌入、Router 开始排队时，积压的事件自动合并，有效吞吐反而上升。文末的压测数据会验证这一点。

规模再扩大、单个会话确实承载不了时，Router 层内部可以设计成多层过滤结构，或者水平切分成多个会话。作者提醒：切分粒度越细，并发吞吐越高，但分片之间的记忆和上下文连续性越低。在全局记忆问题被解决之前，这个权衡始终存在。

### 4.5 这一层带来的产品变化

双层架构让系统在底层接管了上下文管理和并发执行，用户侧的 Session 概念被淡化。作者有一个判断值得单独记下来：让用户手动管理 Session，很大程度上是从底层 LLM API 延续下来的设计惯性。Session 应当是系统的实现细节，不应是用户的认知负担。

现有设计里，Session 同时承担两件事：技术上的上下文管理，和面向用户的项目管理。把产品形态和底层 Session 解耦之后，向用户暴露什么样的任务管理方式，就变成一个独立的产品问题。作者把它列进了文末的开放问题。

## 五、模块二：事件驱动

要让 Agent 主动，先要换驱动方式。驱动 Agent 的主要输入不再是人在 Session 里逐条键入的提示词，而是环境里的半结构化事件。群聊消息、邮件、日程提醒、代码审查评论、CI 运行结果，这些在文中统称 Trigger。

围绕一条事件从进入到处理的全过程，作者讨论了四个递进的问题：怎么过滤噪音，怎么路由到 Worker，怎么组织上下文，怎么提前行动。

### 5.1 两级过滤：先用代码挡噪音，再让模型判断

接入真实群聊和代码平台之后，事件流的特征是高噪音、低触发率：绝大多数日常消息不需要 Agent 介入。每条事件都调大模型从头判断，延迟和算力成本都扛不住。

作者借用了操作系统设计里的 Fast Path / Slow Path。大模型推理是一条灵活但高成本的 Slow Path；把已经明确、稳定的高频判断写成确定性代码，就是低延迟、低成本的 Fast Path。

具体分两级。程序层策略是 Fast Path：针对事件来源、群组范围、用户或机器人白名单这类确定性条件，直接用代码做准入检查。比如对不同来源分别设置"仅响应明确请求""作为候选事件""直接忽略"，在调用模型前先滤掉大部分无关消息。语义层策略是 Slow Path：通过程序层准入的候选事件交给 LLM，由它按提示词里写的策略和上下文判断是否需要行动。语义层同时是面向人的自然语言扩展点，可以随时通过提示词开关或新增策略。

![两级过滤：先由程序层策略筛除大部分无关消息，再交由语义层策略判断](https://toolsfox.top/static/super-agent/05.jpg)

### 5.2 事件路由：Thread 和订阅直通

Router 层维持跨信道的连续性，但如果已分配任务的每个后续事件都要经过 Router 转发，这个全局节点还是会承受大量负载。所以 Fast / Slow Path 同样用在路由上：Router 只负责新任务的冷启动和跨任务协调，已确定归属的后续事件由程序直接发给对应的 Worker。

这里需要一个新概念：Thread。同一个 GitHub PR、同一个 IM 话题、同一封往来邮件串下的连续事件，构成一条事件流，就是一条 Thread。

![Thread 示例：同一个 IM 话题或同一个 GitHub Pull Request 下的连续 Trigger 构成一条 Thread](https://toolsfox.top/static/super-agent/06.jpg)

流程是：Router 根据某条 Thread 的初始事件创建 Worker Session，这个 Worker 直接订阅该 Thread。之后事件路由分成两条路。已订阅的是 Fast Path：同一 Thread 的后续事件由程序直通已订阅的 Worker，不需要 Router 再调用工具转发。如果新事件超出了当前任务范围，Worker 可以取消订阅，或交回 Router 重新分派。未订阅的是 Slow Path：Router 仍然能观测所有事件以掌握全局状态，但只负责判断和分派还没被订阅的新事件。

![订阅与直通：初始事件经由 Router 层创建 Worker 并建立订阅，同一 Thread 的后续事件直接发往该 Worker](https://toolsfox.top/static/super-agent/07.jpg)

订阅关系是多对多的。一个 Worker 可以同时订阅多条相关 Thread，一条 Thread 也可以被多个 Worker 订阅。多个 Worker 在同一个工作环境或讨论里交集时，这条 Thread 的新事件会同时直通给所有订阅者，它们不需要点对点通信，也能知道彼此的操作并自行解决冲突。输出侧不变，Worker 把关键结论汇报给 Router，由 Router 统一回复用户并同步全局记忆。

### 5.3 上下文组织：Inline、Spill 和链式召回

事件进入目标 Session 之后，下一个问题是往模型的上下文窗口里放多少信息。放多了挤占窗口、稀释注意力；放少了模型得反复调工具读取，步数变多。作者的原话是：**浪费上下文窗口，就是浪费模型的智能。**

作者的做法是把上下文窗口当成缓存来管理，操作归纳成两个。Inline 指把近期很可能用到的信息直接放进当前窗口，省掉额外的工具调用往返。Spill 指把超出窗口预算或低频使用的完整信息留在窗口之外，窗口里只保留引用或摘要，模型需要时再读。

结合局部性原则，优化分三步。第一步从最少信息开始，只提供当前对象的 ID 和内容摘要。第二步按局部性逐步 Inline 关联信息：先附上紧密关联对象的 ID，再附带时空相邻的内容，比如内容前 50 字、IM 消息的前后相邻消息和它回复的那条消息、代码评论所在评审讨论里的相邻评论。第三步超出上限就 Spill：对无法全部 Inline 的长内容设一个较小的长度上限，超出部分截断，保留续读入口，模型需要完整内容时再调工具读取。

还有一个长期运行才会暴露的问题。大量后续事件直通 Worker、系统累积了很多历史任务之后，Router 不能把所有任务的全量历史都放进自己的窗口，可用户跨信道提起某个旧任务时又要能找回上下文。把 Inline 和 Spill 一致地应用到系统里的各类对象上，就得到一种按需展开的多跳检索机制，作者叫它链式召回（Chain of Recall）。

![链式召回：每次召回的对象均内联下一跳关联对象的 ID，支持沿引用关系逐跳展开上下文](https://toolsfox.top/static/super-agent/08.jpg)

机制是：系统给 Trigger、Thread、Worker Session 这些对象都分配唯一 ID，注入时内联紧密关联对象的 ID，这些对象在底层就构成一张引用图。每次调工具召回的对象本身也遵循 Inline 和 Spill，返回结果里又内联了下一跳关联对象的摘要和 ID。模型从当前事件出发，顺着引用关系逐步召回。作者举的例子：从一条当前消息读取它所在的 Thread，再从 Thread 内联的 ID 追踪到相关的 Worker Session，进而找到该 Worker 关联的另一个代码评审 Thread。

### 5.4 提前行动：投机执行

计算机体系结构里有投机执行：在不确定结果是否会被采用的时候就先算，用额外的算力换时间。作者把它搬到 Agent 上：根据环境信号在后台提前尝试，结果有价值就交付，没价值就丢弃，用后台算力换人的等待和介入成本。

个人助手场景的例子：收到一封会议邀约邮件或一条待办消息，Agent 先在后台核对日程冲突、搜集相关背景资料、备好回复草稿，用户过目就能直接确认发出。

研发场景的例子来自作者内部的真实配置。他们在 DeepSeek Harness 内部用户群里设了一条"静默复现并修复"策略：群里有人反馈问题或讨论改动方案时，Agent 先在后台尝试复现并寻找修复方案。只有确认问题存在、而且找到了简单修法，它才把结果交付给用户；否则全程安静。

![投机执行示例：群内还在讨论解决方案时，Super-agent 已在后台提交了修复 Pull Request](https://toolsfox.top/static/super-agent/09.jpg)

## 六、模块三：面向人的交互

双层架构从上下文层面保证了跨信道的连续。要在实际体验里同时做到连续和高效，还要解决两个交互层面的问题：后台耗时操作怎么不阻塞前台对话，不同信道的输出怎么匹配各自的习惯。

### 6.1 全双工：异步 ReAct Loop

经典 ReAct Loop 里，模型发起一次同步的 run() 工具调用后，循环就阻塞，直到工具执行完返回最终结果。这期间会话无法响应任何新输入。对话是一问一答的半双工。

改法是把耗时的命令和子任务工具调用改成异步的 start() 和 stop()。模型调 start() 后立即收到"已启动"的返回，循环不再等这个工具。后台工具执行完之后，系统把最终结果作为一条新的事件消息投递进会话。模型也可以根据上下文调 stop()，主动终止执行时间过长的后台命令。

![经典 ReAct Loop 与异步 ReAct Loop 对比：异步调用立即返回 Started 通知，后台工具运行期间仍可响应新消息](https://toolsfox.top/static/super-agent/10.jpg)

效果是前台对话响应和后台任务执行解耦。Agent 在后台跑耗时任务的同时也能响应人的输入，新输入在当前推理步结束后就被处理，不用等后台工具完成。原文说明了状态：这个异步任务机制已经在 DeepSeek Harness 里实现，但还没有默认开启。

### 6.2 多信道：按信道定输出规范

不同工作信道的信息密度和交互习惯不同。把面向单人终端的交互方式直接搬进群聊，冗长的推理过程和密集的工具调用原样输出，多人协作里很容易信息过载。

双层架构先解决了一部分：具体任务里的推理过程和工具调用都隔离在 Worker Session 内部，不出外部信道，对外交互统一由 Router 负责。在这个基础上，再通过提示词针对不同信道定制规范。

IM 这类即时通讯信道，侧重低打扰的轻量沟通：只在需要决策或验收时发通知，只问直接的问题，给简短的结论。作者验证过一条简单有效的硬性规定：单次回复不超过 100 词。GitHub、邮件、文档这类异步信道，侧重结构化、高信息密度的交付：创建或更新 PR 时按项目规范写完整的问题背景、改动说明和验证结果；个人助手场景下直接起草结构化的邮件和文档摘要。

原型仓库里能看到这条规则的落地。prompts/replies.md 写了 100 词限制；prompts/team/communication.md 是一整页"什么时候可以主动发 IM"的规则，核心是默认沉默，只在人必须行动或能使用结果时才发，而且一句话只说用户可见的结果、链接和必要的下一步。

## 七、模块四：计算、状态与执行环境分离

现有的本地 Agent 把三样东西绑在同一台设备上：推进 Agent Loop 的计算、需要持久保存的会话状态、代码仓库和本地工具链这类执行环境。设备休眠或离线，Agent 就停；它也访问不了其他设备上的环境。作者借用存算分离的思想，分两步解耦。

### 7.1 第一步：计算与状态分离

推进 Agent Loop 的计算可以做成无状态的，需要持久保存的只是会话状态。所以第一层解耦是把 Agent Loop 的计算放进云端无状态的弹性计算容器，把 Session 等持久化状态存进数据库。无状态容器可以水平扩展、重启或替换，会话和任务的连续性由持久化存储保障。Agent 由此摆脱单台本地设备的生命周期限制，实现云端持久在线。

### 7.2 第二步：计算与执行环境分离

Agent Loop 和会话状态常驻云端之后，下一个问题是怎么访问任务需要的执行环境。模型工作需要的上下文，很大一部分要通过工具调用从代码仓库、本地文件、依赖服务里获取。从这个角度说，执行环境本身也是上下文的一部分。

常见的两条路作者都不满意。一条是在云端启动沙箱、拉取代码、重建并同步环境。真实工作环境往往包含未提交的本地修改、私有凭据、内网服务依赖和特定的硬件或工具链，同步这样的环境成本高，还容易遗漏。另一条是要求用户放弃本地环境、迁到云端工作，对很多用户来说迁移成本过高。

作者的选择是：既然难以复制的是环境本身，就不让执行环境跟着 Agent Loop 上云。Agent Loop 在云端运行，重状态的执行环境留在原地，端侧只部署一个不保存会话状态的轻量 daemon，它只负责执行命令和返回结果。Agent 按需读取环境里的上下文。

![存算分离与执行环境解耦：Agent Loop 与持久化状态在云端分离，并通过端侧 daemon 按需接入各类执行环境](https://toolsfox.top/static/super-agent/11.jpg)

这个结构支持 BYOM（Bring Your Own Machine），也就是把用户日常使用的开发机或个人电脑接入云端 Agent；也支持接入云端托管机器或按需创建的计算环境。它还能支持间歇在线的设备：用户的某台设备重新上线后，云端 Agent 自动触发并完成需要在该设备上执行的任务。

作者点名了和 Anthropic 的关系。Anthropic 在 2026 年 4 月的工程博客里提出"脑手分离"（Decoupling the brain from the hands），同样让 harness 保持无状态，把会话日志放在 harness 之外，通过统一接口按需接入执行环境。两者的差别在场景：Anthropic 那篇讲的是托管服务，讨论按需创建的沙箱和客户 VPC 内的资源；这里首先要接入的是用户日常使用、可能间歇在线的个人机器，上面有未提交的修改和本地凭据。

这一模块在原型里的状态要单独说明：**原型没有实现**。仓库里没有 daemon、BYOM 或云端相关的代码，原型跑在本地的 DeepSeek Harness profile 里，靠 tmux 保活。这正是 README 里说的"未来方向"。

## 八、模块五：Watchdog

持久在线的分布式系统很难只靠主系统内部的逻辑保证长期可靠，需要在主系统之外引入独立的外部控制回路。作者沿用了这个经典做法，但指出 Agent 系统有一个特殊之处：很多异常不是进程崩溃，而是模型在执行中陷入无效循环，或者偏离了目标。只做进程存活探测抓不到这类问题。所以长期运行的 Agent 系统不仅要监控基础设施是否存活，还要监控任务本身有没有进展。

做法是在主系统外配一个独立的 Watchdog Session，用定时消息驱动，构成外部的控制回路。它处理接口报错、状态恢复失败这类基础设施故障，还由模型判断各个 Worker 是否有实质进展、方向是否偏离整体目标。发现异常就介入修复；遇到外部偶发故障就持续复查，直到恢复正常。

Watchdog 本身是一个具备完整工具能力的 Agent Session。维护者可以用自然语言问它故障原因，也可以让它在线修正主系统的行为，比如增删提示词、调整触发规则。

原型里的状态：只有基础设施级的检查。部署文档要求从操作者自己的 DeepSeek Harness profile 里建一个每小时的定时任务，服务不在运行时把它修好。由模型判断任务进展和方向偏离的那种 Watchdog Session，原型没有。

## 九、实验：数字怎么读

作者从两个层面做了初步实验：端到端对比四种方案，单独压测 Router 层的批处理。作者自己强调实验基于合成负载和简化环境，部分设置可以更严谨，结果只作为初步参考。

### 9.1 消融实验怎么设的

用群聊和 GitHub CI 消息流同时驱动四种端到端方案。单次实验约 300 条消息，其中约 20 条是工作请求，其余是闲聊、跟进、叫停和 CI 消息。编码工作用一个只消耗时间的工具代替，所以实验衡量的是系统的调度与协作能力，不是单个任务的执行能力。每种方案重复运行 5 次。消息间隔和工作时长按 1/4 缩放，模型调用耗时是真实值。

四种方案分别是：Super-agent；去掉直通机制的 Super-agent；单 Session 加 Subagent 工具、中性提示；单 Session 加 Subagent 工具、提示优先委派。

两种提示词原文如下。中性提示写的是 "Use a subagent for a piece of work when appropriate..."。提示优先委派写的是 "Every message of the chat reaches you, so work you run yourself keeps stopping for new messages. Prefer handing each piece of work to a subagent of its own, and do only small things yourself..."。

![工作请求的累计到达曲线与四种方案的累计完成曲线（5 次实验运行均值）](https://toolsfox.top/static/super-agent/12.png)

### 9.2 结果

| 方案 | 任务完成时间 p50 / p95（分钟） | 单次实验读缓存 token（全部 Session） |
|---|---|---|
| Super-agent | 12.4 / 15.7 | 2323 万 |
| Super-agent，去掉直通 | 12.6 / 15.5 | 3177 万 |
| 单 Session + Subagent 工具，中性提示 | 20.4 / 29.5 | 605 万 |
| 单 Session + Subagent 工具，提示优先委派 | 13.8 / 29.0 | 1082 万 |

任务完成时间指从工作请求到结果消息的耗时。以上数字均为原文自述。

### 9.3 怎么读这张表

单 Session 加中性提示最慢。作者记录了原因：5 次运行里模型一次都没调用 Subagent，所有工作都在主 Session 里进行，并且不断被新消息打断，p95 达到 29.5 分钟。

改成提示优先委派之后，5 次里有 4 次进行了委派，完成时间缩短了，但整体仍慢于 Super-agent。剩下 1 次模型判断工作"很小"，选择自己执行，形成了图里的紫色长尾，p95 还是 29.0 分钟。

作者由此得出的结论是：在单 Session 里靠提示词工程和模型临场判断"分不分工"，表现不稳定。双层架构在系统层面把规则定死了，Router 不直接执行具体工作，Worker 只接收它订阅的 Thread 的消息，这个问题就被缓解了。

代价要算清。Super-agent 维护多个独立会话，单次实验的读缓存 token 是单 Session 中性提示方案的约 3.8 倍，2323 万对 605 万。作者的表述是：用更多的 token 消耗，换更短且更稳定的完成时间。

直通机制的价值在哪里，这张表也能看出来。去掉直通之后，完成时间和完整版基本一致，可是 Router 需要做的决定增加了约 30%，总读缓存 token 从 2323 万涨到 3177 万，增幅约 37%。也就是说，在这个负载下，直通不提高任务完成的质量和速度，但给 Router Session 省下了可观的 token 和推理开销。

### 9.4 Router 层压测：批处理到底有没有用

为了验证单个常驻 Router Session 的吞吐上限，作者单独压测了 Router 层：Router 调真实模型，Worker 用 Mock 模型，把需要决定的 Trigger 到达速率从每分钟约 1 条逐步提升到约 40 条。

![不同 Trigger 到达速率下 Router Session 的 batch 大小、单次请求耗时与单个决定的分摊推理时间](https://toolsfox.top/static/super-agent/14.png)

结果是：到达速率从每分钟约 1 条升到约 40 条，平均 batch 大小从 1.0 升到 2.8，单次请求耗时只从 2.5 秒增到 3.9 秒，增长慢于 batch 大小，于是单个决定分摊的推理时间从 6.4 秒降到 1.6 秒。这证明外部事件突发拥堵时，Router 能靠自动合并积压事件提高有效吞吐。这也解释了消融实验里的一个现象：去掉直通让 Router 峰值负载增加，却没有触及单个 Router 的吞吐瓶颈。所以作者说，在他们目前的团队规模下，不需要过早对 Router 层做水平切分而牺牲全局上下文的连续性。

## 十、原型到底实现了多少

文章配套的 dsh-superagent-prototype 是一个 DeepSeek Harness 的插件包，定位是"面向一个 GitHub 仓库的主动编码 Agent"。它监听 GitHub，可选监听飞书；有权限的人提出请求后，它开一个工单，在自己的 Session 和目录里干活，回到原来的对话里答复，比如提交一个 PR。原型还带一个 Web 面板，只显示需要人处理的事。

原型里的名词和文章里的不完全一样。下表按文章的概念逐条对照仓库里的实际情况，状态是我核对仓库源码和文档后的判断，不是原文自述。

| 文章里的概念 | 原型里对应的东西 | 状态 |
|---|---|---|
| Router 层 | Main Session，代码和提示词里叫 orchestrator | 已实现 |
| Worker 层 | Executor Session，代码里叫 worker；每个工单一个 Session 加一个目录 | 已实现 |
| Trigger / Thread | 同名 | 已实现 |
| 两级过滤 | Eval 分两层：Gate 是确定性准入，Assessment 是模型研判 | 已实现 |
| 订阅直通 | Subscription，工单和 Thread 之间多对多；同 Thread 的新事件扇出给所有订阅的工单，不再经过 Eval | 已实现 |
| Router 批处理 | 一条 Thread 上的 Eval 串行运行，运行期间到达的 Trigger 合并进下一批 | 已实现 |
| 主动接单 | 团队用自然语言写规则，加接受模式：observe 只记录"本来会接"但不执行，auto 真的执行 | 已实现；"静默复现并修复"是作者内部配的一条规则，仓库不带 |
| 投机执行 | 没有独立的机制 | 未实现 |
| Inline / Spill、链式召回 | 没有独立的机制 | 未实现 |
| 异步 ReAct Loop | 在 DeepSeek Harness 本体里（ctx.jobs 后台作业注册表），原型的 Executor 通过它管理 Worker 的后台作业 | DSH 已有，原文说未默认开启 |
| 多信道规范 | prompts/replies.md 的 100 词限制，prompts/team/communication.md 的 IM 发送规则 | 已实现 |
| 存算分离、端侧 daemon、BYOM | 没有相关代码；原型在本地 profile 里跑，tmux 保活 | 未实现 |
| Watchdog | 从操作者自己的 profile 发起的每小时存活检查 | 仅基础设施级；模型判断任务进展的 Watchdog Session 未实现 |
| 文章没讲、原型有的 | Ticket / Mandate / Policy 授权模型、Web 面板、GitHub 和飞书两个 Source 实现 | 原型有 |

原型的设计哲学文档只有一句核心原则：**占用尽可能少的人类注意力，提供尽可能多的价值。**从这一句推出的行为规则有五条：只在被请求或书面规则允许时行动；只在人必须行动或能使用结果时说话；一次只问一个具体的问题；按影响而不是按努力决定何时停下；诚实汇报，草稿标明未完成，失败报告为失败。

## 十一、作者自己列的开放问题

作者没有把这套架构说成定稿。文末列了四组还没解决的问题。

第一，双层架构怎么扩展。单常驻 Router、订阅直通、Worker 间不直接通信，这个简化组合覆盖了作者团队目前的大多数日常任务。任务规模和耦合度上去之后，Router 何时切分、粒度多大、Worker 之间何时需要直接通信、用什么协作拓扑，都没有定论。作者还提了系统与模型协同设计的方向：针对 Router 层的事件判别、批量分派、上下文召回做专项训练。运行周期拉到跨月之后，长程记忆会成为主要瓶颈。

第二，脱离 Session 之后怎么和 Agent 协作。作者认为以聊天窗口为中心的交互在一定程度上是路径依赖的结果。交互可以更多地发生在领域特化的界面里，比如直接在 GitHub 的 Issue 和 PR 里工作。另外，模型能力演进的过渡期里，很多任务仍然需要人在中途参与，怎么让用户随时介入、接管或实时协同，也还没有答案。

第三，上下文边界与 A2A。使用范围从个人或小团队扩展到更大组织时，怎么配备 Super-agent，实际上是在划分上下文共享与隔离的边界。多个彼此隔离的实例之间的协同，就是 Agent 间通信（A2A，作者说明不特指某个协议）。在互不共享底层上下文、各自代表不同权限边界的前提下，怎么做到安全可靠，仍需探索。

第四，安全与隐私。事件驱动让 Agent 能被更广泛的环境驱动，也增加了接触不可信输入的风险。云端的 Agent Loop 一旦被服务端入侵或提示词注入攻破，它连接的全部端侧设备都面临被控制的风险。即使云端没被攻破，端侧凭据只要能进入模型上下文，正常执行过程中就有泄露风险，所以需要一种让 Agent 完全不接触凭据本身就能使用凭据的机制。作者的判断很明确：解决不了安全与隐私，Super-agent 只能在一个很小且可信的范围里工作。

## 十二、边界，先说清楚

照抄之前要看清五点。

第一，实验是合成负载加简化环境，编码工作用一个计时工具代替，作者自己说结果仅作初步参考。它证明的是调度与协作机制有效，不证明端到端的任务质量。

第二，所有数字都是原文自述，没有第三方复现。

第三，原型不等于内部版本。原型 README 说大部分工程由编码 Agent 完成，要当研究代码看，风格和实践可能不一致，用之前要自己审一遍。

第四，这套架构的适用前提是"持续在线、并发响应环境事件"。如果你的场景就是一个人对着一个会话做一件事，这五个模块都是多余的。

第五，token 成本是实打实的。多个独立会话的读缓存 token 是单会话的约 3.8 倍，这是实验里测出来的数字。

## 十三、总结表

| 问题 | Super-agent 的答案 |
|---|---|
| 瓶颈在哪里 | 单任务上限是模型能力，多任务上限是人的注意力，一个人只能跟 3 到 5 个会话 |
| 为什么不能简单扩展 | 单会话同步阻塞、多任务上下文混乱、本地离线即停，CLI / MCP / 连接器解决不了 |
| 连续和高效怎么兼顾 | 双层架构：常驻 Router 只管交互和分派，隔离的 Worker 并发执行；单 Router 靠批处理扛住突发 |
| 主动从哪来 | 环境事件驱动；程序层先挡噪音，语义层再判断；Thread 订阅直通省 Router 开销；Inline / Spill 管上下文；投机执行后台先试 |
| 交互怎么不阻塞 | 异步 ReAct Loop，start() 立即返回，结果作为事件投回；IM 回复不超过 100 词，GitHub 写完整 |
| 持久在线怎么做 | 计算无状态上云，状态进数据库，执行环境留原地，端侧只放轻量 daemon |
| 异常怎么自愈 | 主系统外的 Watchdog Session，既查基础设施存活，也由模型判断任务有没有进展 |
| 实验说明了什么 | 完成时间 p95 从 29.5 分钟降到 15.7 分钟，代价是 token 约 3.8 倍；直通省 37% token 但不提速 |
| 原型实现了多少 | 双层、过滤、订阅、批处理、信道规范有；存算分离、投机执行、链式召回、模型级 Watchdog 没有 |

## 十四、行动清单

如果你想在自己的 Agent 上试这套思路，按成本从低到高排，顺序如下。

1. 先把"分派"和"执行"拆成两个会话。主会话禁用执行类工具，只做交互和分派，执行会话一个任务一个。
2. 给事件加程序层白名单：来源、群组、发言人。模型只看过了白名单的候选。
3. 定义你场景里的 Thread：同一个 PR、同一个话题、同一封邮件串。让执行会话订阅 Thread，后续事件直接发给它，不经过主会话。
4. 上下文注入从"ID 加摘要"起步，带上相邻内容，长内容截断并留续读入口。
5. 给 IM 回复定一个硬上限，比如 100 词；默认沉默，只在人必须行动或能用结果时才发。
6. 主动行为先用"只记录不执行"的模式跑一段时间，看记录对不对，再放开。
7. 加一个主系统外的定时检查。先查存活，跑稳了再让它判断任务进展。

最后用作者的一句话收尾：**Session 应当是系统的实现细节，而不应是用户的认知负担。**模型能力在涨，人的注意力不会涨。把会话管理、上下文同步和故障恢复收进系统底层，人才能从执行细节里退出来，只做决策和验收。
