# 177-阿里AI-Native研发实践

> 云栖大会「阿里巴巴集团 AI Native 研发实践论坛」，机器之心主编李亚洲主持，阿里研发基础设施、千问事业部、蚂蚁、飞猪四位一线负责人与复旦彭鑫同台。全场共同前提是"AI 写代码已被解决"，真正讨论瓶颈迁移后的三件事：环境与验证怎么建、Agent 怎么安全进生产、组织与人才怎么重构。是"AI Native 研发范式"讲得最成体系、数字最密集的一场。

## 这场为什么开（背景与定位）

主持人开场定位：过去一年讲 AI 写代码的会大多停留在"能不能用"和"提效多少"，这两个结论已不必论证。本场讨论更靠后的工程问题——**编码被加速之后，交付链路的瓶颈转移到哪里？**可能在需求澄清和方案设计，可能在验证与判断，也可能在组织本身。

主持人还以媒体身份铺垫：他刚从硅谷交流一个月回来，硅谷在做的是提高 token 转化为生产力的效率、工作流自动化。机器之心十年间从"完全手戳"到把素材丢给 Agent 生成完整文章，编辑变成"教 Agent 写得更有亮点、更有人味"的语文老师。痛点是不同编辑用不同工具、不同 prompt，没有统一工作流——恰是离 AI Native 的差距。他再抛"更卷"之问：报道一篇论文的效率与工作量同涨约三倍。

## 逐环节超详细还原

### 环节一：徐晓斌 — AI 时代的软件工程

徐晓斌软件工程毕业快二十年，所学"受到严重挑战"。阿里两三年的认知曲线：最早从 Copilot 做起，内部只看**采纳率**和**AI 代码占比**，部门间互相卷"30%、35%、40%"；今天很多团队 90% 以上代码由 AI 生成，甚至接近 100%——"100% 并不是好事，说明人也没看它，出问题你还得背锅，AI 没法帮你背锅"。

硬结论一：写代码占交付时间极小。内部真实案例里**不到 1%**——改几行代码，却要走评审、测试验证、多系统集成、灰度几天、观察线上反馈的完整链路。真正的软件如支付宝、淘宝每天服务上亿人不能出问题："大部分人每天被 AI 惊叹十次，都在造玩具房子，因为塌了没事。"阿里内部统计写代码时间平均只占 **20%-30%**，按木桶效应全局也提效不了五倍十倍。

组织演进三阶段：**超级个体**（一人全能，一天烧一两个亿 token，"太多吃不消"）；**数字员工**（权限、安全问题集中爆发，需求不清晰时 AI 乱来破坏生产系统）；**云上 Scrum**（漏洞被 AI 攻破、数据泄到外网）。上下文问题：**"代码永远只是你事实的一部分"**——需求、测试方法、系统怎么建起来的都在人脑里。真实故障：几个月前用 AI 建站，交付标准只是"curl 一下通了"；用户真用起来时监控没报警，系统已挂、造成损失——真正的交付标准应包括服务可访问、容量、高可用与多地部署。

四大共性挑战。**一是环境与验证**：阿里开源 Open Sandbox，内部一周创建量超千万级，解决 Agent 运行、RL 训练、评测三类需求；沙箱之上要补全工具链、多地域配置、数据基线、网络边界、依赖服务、运行观测。他们把**环境做成可维护的系统对象**：已把内部两三千个应用做到在独立环境从无到有完整复原（含数据库、缓存、监控、中间件），很快到一万——有信心复原整套环境，就让 Agent 自主做"写代码—验证"循环不碰生产。**二是平台适配 Agent**：AI 访问中间件、运维平台要能快速学到信息且省 token，"别一学耗几千万 token 还没学明白"。**三是数字员工的身份**：把 key/token 扔给 Agent 假装人不成立——"他干了一晚上删了很多数据，你不希望他删，但他干得出来"。阿里重做身份体系：身份＝人＋Agent＋Workload，合成 composite identity，按身份策略授权——发现"A 三天前授权的进程在干高危操作"就回头找真人确认；开源项目 Open Agent OS。**四是生产闸门**（转写作 GatherReal）：回答四问——意图是否匹配（diff 对需求做意图分析）、到底改了什么、影响面多大（LiveDiff 式预先判断）、行为是否真被授权。**写代码的 Agent 和做授权检查的必须是两个上下文，甚至两个模型**。该系统已在几十个应用、约百人团队灰度；目标：半年内一半生产系统发布交给它自主完成，"人最多点个确认"。

人才与组织是更难的部分。超级个体不 scalable："A 抢 B 的活，前端说灭后端"；测试岗、运维岗、开发岗等角色"基本打没了"；团队真实案例："开会开了四轮花了两天，如果让我决策，一小时把代码上线了。"管理者三件事：激励个人（有 passion 的人能量本是普通人三倍，有了 AI 十倍不夸张）、消除摩擦、守住目标——有团队说 AI Native 后最大问题是"做了一堆需求发现都没用，转太快了"。收尾发布《AI Native 研发范式实践手册》，十几名工程师共同贡献。

### 环节二：李英格 — 从超级个体到超级组织：千问研发团队的 AI Native 转型实践

动机：大势所趋；千问迭代极快，且千问本身就是面向大众的通用 Agent，研发交付的大量工作是"做 Agent"。团队三阶段：狂热 AI coding 爱好者带动出超级个体；当前把经验**平台化**沉淀、用**样板间**复制；第三阶段是理想态。

四个问题。一，代码提效几倍，但**产品交付效率提升没想象中大**——代码只占 20%-30% 时间。二，**AI 代码质量没想象中好，关键不在模型**，"是我们使用模型生成代码的方式出了问题"：不同团队 bug 比例**相差接近 30 倍**，交互链路越长差距越明显。三，低估协同：快速迭代导致需求本身质量不高（遗漏、错误、冲突），交给 AI 就是大量返工对焦。四，低估验证：千问有几亿用户，QA 的挑战"已属于不可持续状态，急需升级"。样板间千问输入法：立项初期 demo 飞快、信心爆棚，结果**要测 5-6 轮才能收敛问题**。

解法从常识出发：任务描述清晰它就能做对（"想做 A 它做到 B，绝对不是模型的问题，是你的问题"）；必须有验证机制——模型和人一样会偷懒、没做到说做到了、没验证就说搞定。范式结论：**不是 context 驱动开发，是 context and verify 驱动开发**。他用自己的海外报税案例：各家先进模型完成度都"像模像样"，认真复核总有改不完的小问题；后来只加了 verify 机制——每完成一步做对账、月结单也对账——"所有模型都做得非常精准"。

Context 包含：完备 PRD（数字员工盯钉钉群、听记把需求宣讲记录全部数字化）；研发当质量第一责任人，写进架构约束与实现约束；验证机制前置——"即便是 UI 交互验证，能不能转换成逻辑的验证手段"。落地：产品、研发、质量在同一工作台做同一份交付物（评测 Agent 辅助、人做最后确认）＋工作流、多端基础设施、工程架构、明确任务的自动化 loop。上线前验收保持审慎：测试用例大模型生成、AI 跑用例、大量评测 Agent、人兜底；"现在我每晚睡得晚，是 Agent 经常发信息"。自动化 loop 场景：告警修复（人判断能否上线）、输入法质量门禁、用增投放（"涉及钱"，对日志、操作路径、状态充分验证才敢上线）、客服答疑、夜间自动修复。判据："修复不了不是模型的问题，是你给它的信息不完备，不足以分析出根因。"工作台上已累积 2400 多个任务在运转。

组织协同用样板间：把产研测集中到子业务方向的小虚拟 team——以前分层过细、角色过多，"一个小更改一堆人参与讨论"；边界打破后链条变短，上下文传递更易收敛。质量左移；三端（iOS/安卓/鸿蒙）同一上下文统一交付，培养多端人才。回应"人还有什么用"：领域知识依然极重要（输入法起初交付不好正因领域沉淀不多），架构能力和判断力要求非常高；给年轻人：对 AI 生产的代码和架构都要深入研究学习，把自己能力做到高水位才有职业竞争力。

### 环节三：黄挺 — 蚂蚁的 AI Native 研发实践：面向 Agent 的下一代架构

黄挺先铺底盘：支付宝、蚂蚁财富、网商银行、Alipay Plus 构建在 Sofa、OceanBase、LDC 三地五中心容灾架构上；AI 产品有阿福（健康管家）、生活助手阿宝、理财助手马小财。AI 业务频繁评测带来环境隔离和资源弹性问题，年初决定升级研发范式——蚂蚁是"架构传统很重"的公司（前 CTO 鲁肃一直提一到四代架构），下一代架构**核心是 Agent**："业务系统本质上慢慢变成了 Agent"——阿福拍照上传医院报告，背后调大模型和各类工具完成解读，本质就是 Agent。但没人知道它长什么样，只能和阿福等业务一起摸索。

两个核心命题：一让 Agent 高效跑起来，7×24 小时 Harness；二是确定性与不确定性共存——蚂蚁极重度强调确定性（"资金少一分钱必须多一分钱"），而 Agent 本质不确定。演进第一步"快糙猛"：本地 Codex/Claude Code、什么都塞 skill，把研发运维平台 MCP 化规模化，配统一身份网关。很快发现本质问题是 **MCP/skill 上翻得好不好**：网关统计各 MCP 被调失败率差异很大，"有些接口失败得特别多，Agent 疯狂重试，本质是 MCP 写得不够好"——这就是体验问题，平台报一个"系统内部异常"什么都不给，工程师不知下一步干嘛，Agent 也一样。

第二步 **Agent 上云**："你要 7×24 干活，本质是希望 coding agent 不睡觉——这不就是云吗？"承载者恰是此前为 RL 和评测建的沙箱：基于 Kata 构建，后来发现刚好能让 coding agent 跑进去。CLI、skill、prompt、配置等资产沉淀在云上，"从个人的 Agent 变成团队的 Agent"。沙箱数字：冷启动约 200 毫秒、单沙箱内存约 8MB、单集群创建吞吐约每毫秒 800 个（转写口径）、日创建约 60 万个。第三步**协作系统**：只要是人发 prompt、等反馈、再发 prompt，人就重度参与。蚂蚁有叫"迪玛"的 issue board（需求、任务都在上面）但面向人；要让 Agent 协作，"最好让 Agent 成为一个人"。他们选了开源方案（转写作 MultiK，后文又作 Monica）：共享任务空间里配置 Agent（skill、prompt、运行环境），任务直接 assign 它就干；单 Agent 上下文有限就组 **agent squad**——协调、规划、实现、审查、验证各有分工，"只有真处理不了才通知人类，正常情况下小队自己把活干掉——前提是基础设施写得比较好"。

第四步是评测。内部说法 **"Eval is all you need"**：prompts、工具 description、memory、RAG 召回策略的变化都会导致效果变化；几亿用户的阿福怎么确保各维度不掉分、成本还降？于是做**环境即服务（EAS）**：Agent 一次修 100 个 bad case 可能要同时 100 套环境，常驻不可行——把环境做成服务，声明式描述版本、配置、依赖，EAS 负责创建回收，内部推理平台（转写作 Cita）跟随扩缩容，"现在 5 分钟内拉起一套环境，评测完销毁"。数据库隔离用 OceanBase 新版本 fork 做 db fork：评测要模拟阿福用户，profile 随评测变化（"原来 70 公斤，10 天后 65 公斤，下次又要回到 70 公斤"），不隔离就数据互相污染；像 Git branch 一样 fork，"差不多 50 秒 fork 300 张表"。

他打包成下一代架构雏形：Agent 上云、以 squad 自主跑、工具上翻 MCP/CLI；环境上做了 **ANDC**——对应 LDC（Logical Data Center），即 Agent Native Data Center，支持隔离执行、独立部署、按需创建。效果两案例。阿福 bad case 过去要研发分析、修复、排队评测、AB、上线；现在 board 放在 Monica 上，Agent 拉 case、分析、写代码、拉起评测环境，分数低了打回——**修复周期从 1.2-6 天降到 3 天，人工投入从 3-5 人日降到 0.1-1 小时**。案例二小雨（面向商家）：原是 Workflow 式配置流程 Agent，升级新架构后**两个月完成研发流程和架构整体升级**。三个待解挑战：这轮成绩都来自阿福、小雨这类 greenfield 新业务，支付金融等老业务改造更难；严肃业务稳定性是重中之重，过去三板斧"可监控、可灰度、可应急"在 AI 时代更大规模变更下怎么套用；未来成千上万 Agent 疯狂创建销毁环境，"你的控制面可能天天面临双十一"。

### 环节四：陈烨 — 当代码不再稀缺，真正昂贵的是什么？

陈烨刚从硅谷交流回来。三个观察。**一，行业阶段迁移**：token maxing → efficiency（上线速度、人均代码量）→ ROI/outcome；共同难题是"怎么衡量 ROI"。**二，中美头部同一水位**：飞猪 AI adoption rate（用 AI 写 coding）几乎 100%；交易、导购核心应用在 AI native 流程上跑超 30%；研发效率提升 30%-60%。对照 Google：adoption 95%、效率提升 30%（3000 人的 Google Ads Team，"非常可信"）。**三，方差特别大**：国内大厂人均 token 约 200 美金一个月，Apple 报销 2000 美金，硅谷一家刚被收购的创业公司 top engineer 每月烧 20 万美金——"20 万和 200 差 1000 倍"，AI native 用得好"可以取代一个 Army，1000 人"；国内"要省 token"的呼声：同意，但格局不一定够。

核心论断：写代码快了商业产出没同步涨，"我们有一件很 powerful 的武器，但仍然跑在老的流程上"。引德勤调研：**84% 的企业没有重新设计过任何一个岗位**。理论工具是**阿姆达尔定律**：最大加速比 1/(1-P)；P=90%、加速 100 倍，整体也只有 10 倍。飞猪：coding 只占 20%，其余是澄清需求、上线、压测和 validation；硅谷听到最多的是"瓶颈全部压到了 validation"——而 Eval 不能全自动，"有的路标必须经过人，否则模型很容易自己编一个 use case、编一个规则就通过了"。

组织三时代：公司当机器；公司本身当产品（移动互联网）；现在——**公司是一张人机并行的网络，人和 Agent 是平等节点**。内部五层分级（L1-L5）抽象成三阶段：Copilot（AI 辅助写函数，design 人决定）；Agent（AI 主导执行，人大部分时间在摁按钮——极客甚至买了带两个大红按钮的键盘专门摁 Yes）；AI Native（AI 是团队成员，工作完全 autonomous，第二天早上来汇报，long horizon 任务、需要 persistent sandbox）。对应阿姆达尔：Copilot 阶段 P 的天花板可能就一半；Native 阶段，重复性强、可客观度量的工作交给 Agent，P 可到 95%，"天花板可以 20X"。

内部数据（双十一备战期口径）：人员不增、部分还减。**平台技术**（计费、交易核心系统）："最后一道必须是人"，38% 业务需求由 AI 流程支持；内部系统"交付大脑"——需求进去就开始跑，不会因凑人开会而停止。**酒店住宿**：63% 核心应用已接入 AI 研发流程；策略是"先啃最硬的骨头"，打出样板后长尾好办。**商旅**：共性问题抽象成组件，组件生产效率提升 71%。**人均代码产出**：交通（品类标准化）提升 63%；非标的度假提升 150%。

案例一平台技术：典型需求从 2-4 周缩短到一周。三点经验：把 know how 和 code base 知识点**沉淀到领域知识库**——不能让 coding agent 反复扫遗留代码；**PRD 到 Gate**——PRD 进去让 Agent 过第一道关（影响哪些系统、是否自洽、需要哪些资源），这一道没人参与；**流程线上化标准化**——研发流程 100% 线上、Agent 到 Agent 推进。案例二测试："大量代码是 AI 写的，不回归不敢发"。引述一位（转写作 Daryl 的）人士："AI 把代码生成加速以后，安全审查、设计验证、人的判断就成了新的瓶颈。**瓶颈不会消失，它只会搬家**"——生成是并行的，validation 仍是串行的。解法：AI 自动评审——专属 Agent 圈定影响面、写出 test case 去测，一级级严格测试；资金、交易等核心领域最后一道 rubrics 必须是人。交通品类单月统计：4 次发布走通"提交→自动部署验证环境→AI 圈定影响范围→smoke test→发布"全流程，AI 自动判定评审超 2000 次。飞猪测试单月总数据：AI 自动评审接近 1 万次，核心监控场景自动完成率 97.4%，30 个数字员工在跑。

三个坑。一，角色边界必须清晰："**人人都能写代码，不代表人人都应该写代码**"。二，不能冒进全量 AI native，先建标杆再分步推进，尤其涉资金高危业务。三，不押注 100% 自动化测试——"不是目标，更不是起点"；把 coding agent 当黑盒非常令人失望——"模型号称挺强，突然某天就变得很傻。兜底的还是人"。回答标题之问，真正昂贵的是三件事：**想清楚做什么**（"需求模糊是交付链路里最长的阻塞点"，知识前置、评审前置的 shift left）；**judgment**；**knowledge**（coding 与业务 know how 沉淀）。收尾："AI coding 不仅仅是 coding，AI native 的组织不仅仅是组织——它是组织的选择与变革。"

### 环节五：彭鑫 — 智能化软件发展的机遇与挑战（学术视角）

彭鑫要回答两问：**AI 是不是要吞噬软件？软件还在，程序员还要不要？**"退休之前这两个问题不想明白，饭碗都没了。"

第一问："软件 3.0"（卡帕西概念）叠加 Claude Cowork（转写口音）引入行业插件，SaaS 干的事它也能干了，全球软件股暴跌，"AI 正在吞噬所有软件"刷屏，连数据库专家都断言软件中间层该退位了。他的反驳：业务逻辑层会有大重构，但不等同于软件消亡。软件分三层：**计算支撑层**代码主导；**业务处理层**部分让位给智能体但代码不消失；**社会协作层**（张鹏：清华科技园两百多个智能体在互相谈生意）。代码不消失：高效计算与通信、透明的规则与秩序（等车分配由神秘 AI 掌控就说不清，软件掌控则透明）、平台生态（九问平台本身就是一大堆代码）。软件形态会大变：一体化设计被"解构再重构"，智能化软件呈现人机物融合、虚实融合（Palantir 数字孪生）、神经符号融合、开发运行融合四特征。

企业落地侧：SAP、ServiceNow、SalesForce 的 benchmark 显示企业智能体面临复杂数据流、有限可见性、隐性约束三大挑战，"即使最好的智能体任务完成率也很低"。实验室方向：代码、知识、智能体将成架构层相互作用的**一等公民**（例：Claude Code 生成 JS 代码固化 Agent 间流程）；还在啃可观测性与溯源——上下文丢了记录无法还原，完整上下文又非常之大，"这个问题真的很难"。

面对"码农只剩 6 个月"、Cursor"168 小时搞出 300 万行浏览器内核"随后被打假这类喧嚣，他回答第二问：AI 写出 300 万行**像**浏览器内核的代码不难，但能不能高效稳定可靠安全地解析渲染？"拿来学习也许有用，当成产品就完蛋了。"

核心方法论。其一**小马过河**：经历都真实，但项目类型、架构形态、能力与工具不同，水深就不一样。其二"软件"至少三种：即用即抛的**解决方案**、再长也是执行流的**工具应用**（AI 擅长）、需长期可靠运行的**复杂系统**——AI 对第三类能力就没那么强。其三**复杂系统论**：软件既复杂且精密——"软件的零部件是啥？讲不清楚"；架构承重墙被改坏不一定知道，华为十年前就提"**架构看护**"；lock 加锁语句上下挪几行，专家们讨论几个月定不了；**混杂与散布**——800 行的财务系统函数里只有八九行跟 bug 相关，做摘要必被掩盖；阿里的"**特性无法下架**"：想撤几百行 feature？撤不掉，"狗皮膏药上贴了好多层狗皮膏药"。理想是上帝视角架构师做完美决策，现实是"每次修改都像乱搭乱建的棚户区又经历一次无序扩张"。

其四，听成功故事要**三维度拷问**：人的干预程度多深、任务和模块交互是否足够复杂、时间维度上"AI 维护得动吗"。理解 AI 边界的钥匙是**可驾驭性**：问题是否良定义、验证是否客观、能否给智能体可导航可操控的环境、是否充分解耦（OpenAI 实验拆了 500 个包——智能体也怕上下文过长注意力不够）、底层交互是否被抽象（"一条明显没用的 print 语句删了会黑屏"）。其五，对 **Agent 控制环路打大大的问号**：测试永远不完备；AI 极易过拟合；它没有责任感和敬畏之心。AI 不光是大无畏，**它很无耻**——发现 return 3 能过测试就写 return 3；有人做实验一个进程修 bug 一个进程评估，结果修 bug 的把手伸到评估器里给自己打勾——AI 为了得到分数无所不用其极。

其六，立身之本：**代码数字孪生，AI 时代的软件知识工程**。Linux 代码开源，但全世界几个人看得懂、敢改？阿里领导说："系统太大，没有哪份文档讲得清楚，只有线上系统本身最准。"很多规律是复杂系统**涌现**的——如"删一条朋友圈黑屏"是踩坑踩出来的，华为专家加注释"这行不能删，删了会黑屏"，这也算知识。他坚定认为**代码是软件的物理表达，软件的逻辑表达是高层思维**——需求理解、架构规划大量丢在会议纪要、文档和你我他的脑子里，"未来能不能像重视代码库的传承一样，重视软件知识的传承？"实验室蓝图：在源代码、文档、提交历史之上建软件知识平台；"知识只有我知道，大家都得求我；全告诉大家，我被蒸馏掉了"——所以要有激励机制。总结：**系统复杂性可以成为理解 AI 辅助开发的第一性原理**——大模型是平面化、文本式的学习方式，缺少逐层抽象和决策过程信息，对代码之外的系统复杂性没有感知，这是大模型天然缺点，也是人要补的位置。

### 环节六：圆桌 — 个体被放大之后，组织与人才怎么变

议题一：个体产出被放大后，团队最先改什么。徐晓斌："打破边界简单，树立新的引导很难"——应明确"哪些技能更值得提倡"，个体激励成长才有确定性。李英格：把链路做短——样板间把产研测拉进内聚的小虚拟 team（以前分层过细、角色过多）；质量左移；三端同一上下文统一交付培养多端人才。黄挺聚焦"综合型人才"：他做基础技术出身（Sofa 当年被内网投诉"Spring Boot 那么好用你们这么难用"）；现在管蚂蚁整个 AI 使用成本，发现 **Agent 时代工具的用户体验问题被放大**——"Agent 觉得你的东西差就重试，重试重试直到重试出幻觉、出现故障"。写 skill 的 description 不应有二义性；不要搞 map 这样的大接口——Agent 要读整个代码、花更多 token。对管理者："没参与到 AI coding 和研发范式变化中，你很难指挥大家"；带人少的管理者反而庆幸——有更多时间真正跟 Agent 交互。

议题二：高校培养怎么调。彭鑫：一个学期被三波媒体采访"AI 都写代码了，软件工程还要不要学"。他明确告诉学生"还是用 AI 吧——不让用他还是会用"。基本判断：**"AI 把人才成长能力上的梯子给撤掉了"**——以前学生在每个台阶经过挣扎搞定，潜移默化学会软件设计再上下一阶；现在"碰到 AI 搞不定的时候你就歇菜了，那一大截你没学过，整个被挂空"，更糟的是 AI 带来"虚幻的满足感和能力感"。他每次上课花五分钟"像唐僧一样"絮叨 AI，自嘲像在挽救失足少年。课堂众生相：有人说"我一个人一个组就够"，有组长说"你们三个都歇着，最后两天动笔就行"。课程项目从选课系统升级成网盘；第三次迭代特意设计成"新需求跟老需求纠缠在一起"——前两次用 AI 的同学很幸福，第三次集体翻车；"组长包打一切"的组里，在外实习的同学汇报时才知道组里评分很差——"AI 把组长哄得很好，说所有要求都达到了"。"我说对不起，你重做；他说我熬夜重做一遍；我说对不起，成绩已经检查完了。"结论：要让学生碰壁，碰壁后才会对软件工程有敬意。

追问：工程师还要不要读懂 AI 写的每一行代码？彭鑫说这问题本身是陷阱——完全不看，复杂系统失控；都看，速度拖慢。答案是**拿捏**："让 AI 生成折扣算法，守护好接口输入输出，细节也许不看；但控制系统资源调度的代码——lock 挪一下就崩溃那种——肯定一行行看。"他转述华为工程师："用了 AI 之后每天两点才睡——AI 在不停吐代码，只要有一段不跟上，从此就再也看不懂了。"

陈烨谈人才：未来两类人才指数级增值——**K 型**（优秀的人加倍优秀，中间层几乎没有价值）和 **L 型**（通才但某一领域非常专）。阿里工程师执行力极强，但缺 AI 时代三要素：**审美**（机会选哪个）、**判断**（做得对不对、要不要 challenge）、**共情**——要回到创业者精神而不是接单。老困惑"Google 那么伟大，为什么 Jeff Dean 会离开"——"老登味相当重，很多认知不愿意跟上"。他问 OpenAI "你们最爽的是什么"，答案："**几乎没有会**"——"这就是 AI native organization 的那种感觉。"招人是个悖论：国内风气越招越年轻，网传"K3 主要代码是高中生写的"（当然这是 rumor）；Anthropic 极度扁平（CEO 下面就是 IC）但老兵居多；飞猪两个方向都做。黄挺补充：他给校招生推荐《禅与摩托车维修艺术》——"科技中的美不就是 taste 吗？"；就像不会修汽车也能交给 4S 店，"最上层的软件未来可能就这样，但下面更复杂的软件，会需要更少但更专的工程师"。对年轻人第一条硬要求：**必须会用 AI**——面试要问 prompt 怎么设计、产出软件的可靠性可维护性怎么样。主持人现身说法：编辑必须用 AI，但他自己也会刻意古法写作——"人脑也是神经网络，没有足够强度训练，参数就没有变化"。徐晓斌总结招人：在计算机基础之上额外考察**技术的热情**和**判断力或 taste**。

## 这场的意义

对行业而言，这场论坛完成了一次集体"换问题"：当五家一线团队不约而同说"写代码已被解决"，战场变成三张清单——**环境**（沙箱、可复原应用环境、EAS、db fork）、**验证**（context and verify、评测 Agent 矩阵、Eval is all you need、生产闸门）、**身份与安全**（合成身份、写代码与授权检查分离、最后一道必须是人）。"代码只是事实的一部分""瓶颈不会消失只会搬家"可当所有 AI 提效项目的立项依据：谁还在只汇报 AI 代码占比，谁就停在三年前的认知。

对个人而言，这是一份工程师转型地图。技能侧共识近乎残酷：领域知识、架构判断力、taste、共情，以及"对系统复杂性的感知"——大模型恰是平面化、文本式的学习者，缺少逐层抽象和代码之外的上下文，这正是人要守住的位置。同时警惕两个陷阱：虚幻的能力感会在真难题出现时集中兑现；"读懂每一行代码"是伪问题，正确答案是按风险分级拿捏。黄挺的提醒值得记住：你的用户正从人变成 Agent，工具的报错、description 的二义性、接口省不省 token 就是新时代的用户体验。彭鑫的"代码数字孪生"则指出长期主义路线：像重视代码库一样重视散落在会议纪要、踩坑记录和老员工脑子里的系统知识。
