# 199-可观测智能开发运维

> 云栖大会第二天上午的「可观测与智能开发运维」专场：阿里云发布 AgenticOps 全家桶——AgentLoop（Agent 评估与数据飞轮）、StarOps（全域智能运维平台，现场亦称 SOPS）、云效研发智能体，客户侧凌越科技 SkillOps、吉利汽车"1530"实践，末段补上开源底座（采集、语义建模、基准测试）。讲者依次为夏明（阿里云 AgentLoop）、钟毅（凌越科技）、李田力（阿里云）、邹良（吉利汽车）、崔立强（阿里云云效）、张呼星与温希道（阿里云）。一句话价值：全场论证同一个判断——Agent 时代的运维竞争力不在模型本身，而在数据飞轮、语义上下文与可反复评测的工程底座。

## 这场为什么开（背景与定位）

企业用 AI 做运维研发已过了"能查数据、能分析异常"的阶段，卡住落地的是三堵墙：数据采不到、上下文读不懂（模型不理解对象/关系/时间/来源，一本正经胡说八道）、效果验不准（demo 灵光不等于生产可信）。本场是阿里云可观测团队的系统性回应：商业化产品线解决"采不到、看不清、读不懂、评不准"，开源与学术线把核心能力变成社区公共资产，凌越科技和吉利汽车给出已验证样本。全场隐性主线：让 AI 参与持续运维、把问题推进到闭环——从"人提问让 Agent 干"变成"Agent 围绕目标自己工作，人做关键决策"。

## 全场脉络（环节清单）

- 夏明（阿里云 AgentLoop）— Agent 评估、归因与数据飞轮（录制从中段开始）
- 钟毅（凌越科技）— SkillOps：Skill 全生命周期管理
- 现场抽奖第一轮 — 加湿器×5
- 李田力（阿里云）— StarOps 发布：构建 AgenticOps 智能运维闭环
- 邹良（吉利汽车集团）— 吉利全域智能运维实践："1530"
- 崔立强（阿里云）— 云效研发智能体正式发布
- 现场抽奖第二轮 — 无线充电万年历×5
- 张呼星、温希道（阿里云）— 面向 AgenticOps 的开源建设：采集标准化、语义建模与基准测试体系
- 终轮抽奖 — Cherry 机械键盘、云宝、保温杯×3

## 逐环节超详细还原

### 环节一：夏明（阿里云 AgentLoop）——Agent 评估、归因与数据飞轮

录制从其评估章节中段开始。第一版评估做的是业界通用的 LLM Judge 和 Code Judge，但到客户现场发现：评估器不能真实理解业务、不能调用私域知识和工具，就评不准。团队转向领域化评估后，在电商、汽车、物流等头部客户及凌越金融验证，评估有效率可达 90% 以上。

评什么？一是客服场景里人工客服与智能体客服回复的一致性；二是更关键的"说与做一致性"——Agent 说的与中间执行轨迹做的是否一致。两个案例：物流订单场景，客服说"我帮你找到了某某货源"，但中间工具调用其实失败；UGC 场景，Agent 说"我帮你发了一把枪"，屏幕上却没有那把枪，因为生成的代码不符合 API 库定义。结论：评估不仅看结果，更要看中间过程正确性；评估器必须能理解业务知识、挂载 skill 和工具。评估发现的问题要触发优化（提示词、skill、知识检索等），但落地仍以专家辅助调优为主——知识检索不到，是库里没这条知识还是召回算法有问题？这需要更多企业上下文。

最后一环是实验回测："要不然我们每一次的变更其实都是黑盒，都是盲猜，只能人工抽检。"只有沉淀经典数据集、每次变更能回测，才能保障优化整体正向。深圳某 UGC 客户三天驻场：从观测接入、轨迹构建，到把 UGC A 拍的完整 skill 挂载给评估器，当天发现线上十几个真实问题，打新包结合 bad case 回测后真正解决。这一切服务业务 Agent 的北极星指标：客服看全托率、满意度，有的场景看自闭环率。客户侧对照：很多客户养十几二十人标注团队，标注周期 T+1 甚至 T+3，抽检率不到 10%——经 AgentLoop 数据飞轮都有很大改善。收尾观点：未来企业 Agent 竞争不再比拼谁的模型更好——企业端在模型侧能做的少，不是每个企业有资源做 RL 训练——竞争更依赖 Agent 效果迭代，谁的数据飞轮转得快，谁就跑得远。

### 环节二：钟毅（凌越科技）——SkillOps：Skill 全生命周期管理

钟毅不讲怎么做某一个 skill，而是讲管理公司几百个 skill 的系统——SkillOps。判断："模型是工具，Agent skill 才是企业的核心生产力。模型大家都能买，prompt 谁都会写，但把业务逻辑、内部系统调用方式、踩过的坑沉淀成可复用 skill，这才是真正的护城河。"问题在于 skill 散落在个人电脑和代码仓库角落，是"用最贵的方式重复造轮子"。

背景：凌越科技是以大数据和 AI 为基础的数字科技集团，聚焦消费金融，遍布中国大陆、东南亚和拉美；全球注册用户超 1.9 亿，合作机构超 116 家，累计交易额超 5700 亿——业务链条长、规则密集，是 AI skill 最好的土壤，跨国分布式团队让能力跨团队流转成刚需。AI 投入：大规模推广 Claude Code、Cursor 等工具覆盖研发、产品、运营及财税法岗位，AI skill 下沉到业务全生命周期，已迭代数百个高频核心 skill——"AI 已过实验性阶段，成为不可或缺的生产力基础设施，需要像管理基建一样去管理它"。

但工具数量不等于资产价值：碎片化与低复用率（各团队重复开发、无统一标准）；质量黑箱化（发布后安装量、调用量、效果、失败原因全不知道，缺数据到优化的闭环）。答案 SkillOps：代码多了有 DevOps，模型多了有 MLOps，skill 多了就需要 SkillOps；Skill 是可被发现、衡量、迭代的战略资产，是 AI 时代的 SKU，"既然是 SKU，就应该有货架，有销量，有质检，有迭代"。四大广场：模型广场（统一接入与智能路由）、MCP 广场（连接内部数据和工具）、Skill 广场（做什么业务）、Plugin 广场（怎么分发）；五条原则：复用优先、数据驱动、质量可量化、流程自动化、可扩展。

骨架是六阶段闭环。发现——翻找现成轮子可能比重写还高；IDE 里 Skill Find 或广场 UI 问一句话，给出"直接复用/继承改造/全新创建"建议，把查找做成流程第一步，用机制保证复用优先。创建——写 prompt 配工具是样板代码；平台继承需求上下文一键生成工程包，消除约 80% 重复配置。发布——Git 与广场打通，push 即上架；首次上架 0 审批鼓励沉淀，关卡放在常态化版本更新，由评测门禁兜底。采集与加工——质量黑箱的解药、与 AgentLoop 共创最深的一段。评测——解决发版靠感觉："改了 prompt 测几个 case 没问题就上线，一上线就翻车"；双轨评测=生产增量按天盯趋势+离线实验发版前卡准入，正确性、增益、成本三指标配分级门禁（核心 skill 强制拦截、常规告警），"只看正确性不关心成本，就会养出又慢又贵的 skill"。迭代——报告给 bad case 集合供定向优化；进阶方向 Skill 自我进化，边界是 Human in the loop：发版权在开发者。

与阿里云 AgentLoop 共创的 skill 数据链路：横向三层（用户层、阿里云数据底座、内部 AI 中台），纵向四阶段（采集、加工、离线实验、评测）；主链路是本地 Agent 经 LongSight 采集器得 Trace、打标做 skill 归因、成数据集、本地离线实验、评测，另有 ground truth 回灌与 bad case 回流两条虚线。采集无感——本地 hook 静默异步上报、先做 PII 脱敏、安装包一键铺开，资产大盘统计真实安装量与覆盖率；精准——入库时服务端再脱敏并做 skill 归因打标（凌越提出、与 AgentLoop 共建），仅靠规则打标偏差多，不提纯则门禁不可信。加工职责收敛为一件事：让样本归因可信——机器剔除误标，低置信样本宁缺毋滥、走旁路反哺规则，开发者补 ground truth 回灌；全量数据集反映线上真实分布，人工确认样本构成离线回归黄金子集。

Demo：AI rag skill 查"单点登录有哪些权限点"，发现未接入 RAG 服务；让 AI 自动迭代补上，基于已有数据集创建离线实验（底层调 AgentLoop 实验能力），with/without skill 基线对比，评测结果：启用后得分 2.35，增益 87%。共创亮点 Coding skill 离线实验——代码每天在变怎么重跑？四步：采集记录代码基线；关联实际合入的 PR 作 ground truth；按基准检出代码还原当时工作区；新代码与 PR 结构化对比+verify 检测点评分。

收尾盘点：业务场景层 skill 深入风控、资金、营销、客服；研发工程层形成 SDD（需求驱动开发）到评审、测试、发布的 AI 研发流水线；平台基建层用 AI 治理 AI。感悟：从零散工具到核心资产；没有数据指引 AI 落地就是开盲盒；开发者壁垒转向沉淀高质量 skill。收束："让每一次 AI 调用都在沉淀企业的核心竞争力。"

### 环节三：李田力（阿里云）——StarOps 全域智能运维平台：构建 AgenticOps 智能运维闭环

李田力（StarOps 产品经理，可观测团队）的话题：AI 已能查数据、分析异常，接下来怎么让它参与持续运维、把问题推进到闭环。三个老问题：数据割裂（运行时数据、资源信息、研发变更分散在不同系统）；不知道该查什么（应用自身还是下层依赖问题，依赖老专家且经验难复用）；处理没人推（谁来处理、有没有风险、谁来验证、是否真恢复）。演进：监控规则→异常检测与关联分析→AI 助手给初步结论，但推进解决还不够。StarOps 的 AgenticOps：持续关注核心应用健康状态，发现问题自动定位调查、处置验证、闭环、可追溯；最大变化是从"人不断提问让 Agent 干"变成"Agent 围绕保证应用健康的目标自己工作，人做关键决策"。

核心架构两个重点：一，构建异构系统、异构环境的统一上下文——运行观测数据、系统数据、研发流水线和代码资产整体关联；二，核心执行链路——长期任务持续观察，问题发现（Findings）承载根因、处置建议与处置全过程记录，再到调查、执行、验证；企业自己的 Skills、CLI、工作流可被自主调度。

统一上下文三步：接入智能化——自动感知云上资源及变化、自然语言接入、SaaS 数据员工自动匹配接入方案；统一 Connect——云上直连或环境代理，连跨账号、企业 IDC、其他云的数据和系统，统一鉴权与连接状态管理，连的不止日志、指标、链路，还有代码、实例、资源、应用；Fabric 统一建模——语义关系、实体关系、动态拓扑。

自然语言查询不返回裸数据而是给结论——"这个应用错误率比其他高非常多"，可继续追问是接口问题还是关联依赖问题。诊断定位：先大范围确定哪个环节、哪条链路出问题，再结合指标、链路、事件、代码定位；机制是假设驱动验证——提出假设、找证据、不对就继续搜寻，直到根因和处置建议，"跟我们做事件调查有点像"。

持续闭环：长期任务按目标自动生成观察执行计划，发现问题自动诊断调查；Findings 承载关键问题、根因、处置建议及人机处置全过程记录，解决并验证后，处理轨迹自动收敛成经验沉淀。安全靠分层执行策略：危险操作（配置变更、扩缩容）找人确认，查数分析自动放行，禁止规则强制拦截，执行时权限校验——权限永远无法越界；调了什么工具、谁审批全部进审计。

四个 demo：数据接入——对话式把 ACK 集群接入日志服务与云监控，Connect 连新项目后自动建模。告警调查+恢复——可展开看故障传播链和根因，恢复的关键行为进 human loop 人确认；延时回落、自动验证，可生成 HTML 报告复盘。长期任务巡检——"对北京地域资源巡检、整理稳定性报告"，生成巡检计划、人确认后落地，执行记录可查。核心应用发布值守——基于发布事件监控，发布致异常自动定位根因，生成回滚+修 bug 两个待办；回滚需人确认，Agent 拉代码修掉、提交 PR，借云效 pipeline 和 Codeup 完成构建部署——"不太需要切换太多平台就把问题闭环处理掉"，人机动作全部留痕。入口：控台，页面/API、IM、CI 或 Skill 接入。

### 环节四：邹良（吉利汽车集团）——吉利全域智能运维实践："1530"

邹良（吉利汽车集团数字化质量高级经理）开场解释"1530"：吉利内部小目标——1 分钟发现、5 分钟快速定位、30 分钟快速恢复，全场围绕把 1530 变成可执行链路。痛点四关键词：发现慢、定位难、告警风暴、恢复慢。核心矛盾："监控工具其实并不缺少，真正缺少的是跨云、跨机房、跨业务系统之间的数据上下文。"链路上用户反馈→业务服务→应用层→集群层→基础层看似合理，但缺故障视图——运维要人肉跨系统、跨云把关联建起来才知道问题在哪。日志、指标、链路、事件、工单分散在不同平台。

根因六条：日志格式不统一；缺统一 CMDB 资产可视化；缺统一观测大盘（大海捞针）；全链路缺关联；调用链冗长（一个请求穿过大量微服务，问题节点不知在哪）；流程缺标准。抽象为三个缺失：数据缺失、关联缺失（资产与服务割裂、告警无法聚合收敛）、智能缺失（纯靠人肉）。目标：1530 变可执行链路，从"人找问题"变"问题找人"——精准路由到部门、团队、场景。

方案上 StarOps 不是一次性项目，而是积累运维知识的飞轮闭环：数据（云监控 2.0 统一整合指标、日志、链路、事件）；建模（打通资产与服务关系）；诊断（AI 自动化推理、经验沉淀）；效能飞轮（案例、故障、SOP 沉成可复用资产，越用越聪明）。

三大闭环：监控告警——基础监控补齐、告警治理（过去一个故障成千上万条信息无从下手）、精准路由分层管理；根因定位——故障诊断、trace ID 贯穿端到端全链路、CMDB 资产可视化从上层业务到基础设施；故障自愈——预案匹配、标准 SOP，以及他强调最多的定期攻防演练：极氪、领克、雷达、吉利品牌、吉利银河等核心链路已具备同城多活基础能力。演练打法硬核：不在 UAT 不在 PRE，凌晨 1 点直接把生产环境的某个应用打挂，全程计时、高标准 30 分钟，达不到就继续演练；每次演练第一时间通知吉利汽车 CDO——"一把手，这是真实客观存在的"。

底座四大能力：设施实体层；接入汇聚层（四套网关统一流量入口）；数据层（uModel 层统一聚合指标、日志、链路、事件）；标准 SOP 层（"整个过程不是自嗨"，由数字质量团队全程验证）。最上层是 L2 级指挥中枢：全域感知，"不是纯粹抓瞎"。数字员工四个：告警智能数字员工做聚合、收敛、降噪；智能诊断数字员工五步流程——异常告警→证据采集→拓扑推理→根因定位→基于 Notebook 生成标准命令执行。高风险操作现阶段保留人工 check。

实际效果（涉密未放视频，场景还原）：上午 10 点出问题告警，10:00:20 数字员工介入，做错误码、调用链、metrics 分析到根因定位，给出明确建议——扩容、连接数、慢 SQL 还是资源不够——"整个全链路完整闭环，只要花 5 分钟"。对比传统运维：MTTR 直接提升 7 倍，效率提升 15 倍，查询速度提升 20 倍——过去跨多系统人工聚合找问题，现在一个 trace ID 精准定位；高警准确率提升到 70%。人力也在优化——"不是把人裁掉，而是把人拿出来做了更多更有意义、更有价值的事情"。最深转变是角色：运维从救火队变成规划师——把高频故障、容量趋势、top 风险转成可排序、可落地的执行计划。总结：吉利从被动响应到智能运维；但智能运维不是一蹴而就，需要持续精进迭代。

### 环节五：崔立强（阿里云）——云效研发智能体正式发布：构建 Agent 驱动的研发交付闭环

崔立强（阿里云云效技术负责人）从研发侧接棒：云效是 DevOps 平台，从需求到上线快速交付，后面对接 StarOps 运维能力。前 AI 时代提效两方向：交付效率（CI/CD 流水线、单元测试、发布自动化）和协作效率（工作项、代码平台、合并请求协作）。智能化时代沿这两方向重新想。

交付效率的时间花在三段：工作项管理、编码、验收测试。编码段 copilot 类工具已越来越可用，重点讲前后两段。工作项管理：过去靠模板化填空，要填背景、验收场景、非功能指标，费大量思考；智能体天生适合——博学、可找业界资料和项目内知识帮把需求写出来，人仍要看产出做判断。测试验收：单端测试稳定性差（环境一变、改个 selector 用例就失效），交给智能体——给 shell、playwright 工具操作备测系统，拆用例执行、沉淀脚本下次召回复用。

除单点提效，最重要的是八个字：并行处理和自主发起。n 个任务人只能串行，丢给智能体可并行；既然能并行，为什么还要人发起？缺陷指给我，智能体是不是该自动上线干活？机制：任务/工作项产生事件，捕获事件、定义智能体任务，把工作自动化串起来。协作效率两点：一，过程规范化——需求、代码、MR 都是中间产物，各有上下游；需求不详、MR 没描述，来回问形成瓶颈；智能体按团队要求写出需求、用例、代码，一个环节高质量，后续协作都受益。二，知识沉淀——丢钉钉/飞书文档内容多、过时甚至错；"为什么不让它自己生成知识库呢？"它每天工作，知道什么该沉淀（测试环境、方法偏好、脚本），自己总结、自己消费。

三个目标：全场景智能化覆盖；自主工作（并行度越高越好，人只在关键决策、发布前介入）；自主维护团队知识库——一个人告诉智能体的知识，团队任何成员都可复用。

落地机制：云效智能体基于 StarOps 打造。开通组织智能体开关，即为每个登录用户创建 StarOps 数字员工——云端 24 小时工作、事件或指令驱动；形态是数字分身：每人独立、可定制（MCP、记忆），并自动与云效权限对齐——它能做的事就是你能做的事，不越权。

全流程：PRD（甚至一句话）→需求优化拆分→云端编码→触发 CI/CD（编译、单测、代码检测）→有问题回编码循环（可自动可手动）→代码评审（评审智能体把团队规范落进去）→功能验收→发布。演示：输入"支持在 iOS APP 上接入支付宝收费"即产出符合模板的工作项；自动找关联代码库提交 MR，CI 扫描失败可点"智能排查"触发修复再 push；智能评审可让它修，也可告诉它团队规范让它记住。发布侧专门针对 ACK 做发布风险评估：找出涉及的 workload，比对发布前后 pod 在云监控、日志服务的状态，有没有新异常、新错误日志。最后用云效全新 AI 工作台管理任务——背后跑的就是 StarOps 智能体任务。

自主工作=定时任务+事件触发。定时任务例：leader 每天跟进迭代进展、按天检查主干新增代码、开发每天看日志监控修小异常——"很多大故障都是由小问题堆积产生的"。业务事件例：需求先让 agent 细化；任务待测试就主动拆用例开测；有人提 MR 就按提示词预提审。团队知识以代码库为格式——目录结构对智能体有用，真正有效的知识不多，一个代码库足够；例子：需求链接丢给它做外部 UI 测试，脚本沉淀进知识库，下次直接复用。总结：云效智能体是专为研发团队的垂类智能体方案，单点提效+越用越聪明越理解你的项目和团队。

### 环节六：张呼星、温希道（阿里云）——面向 AgenticOps 的开源建设：采集标准化、语义建模与基准测试体系

#### 张呼星：采集标准化

从两年前的故事讲起：OpenTelemetry 是仅次于 Kubernetes 的第二大 CNCF 活跃项目。当时 Go 语言缺标准化、无侵入、编译时插桩采集可观测数据的项目，他们做了开源带给社区——社区一开始不乐意接受；经长时间沟通、引入 DataDog 等伙伴成立 SIG，才做成符合规范的标准化项目，从捐赠方案到第一版发布历时近两年——从提案到稳定版本，要花非常大的时间精力。

AgenticOps 生产落地三大挑战：采不到、读不懂、验不准。采集侧：数据来自各层技术栈（机器、GPU、Infra 到应用层），要覆盖盲区，Agent 和普通应用统一采集。阿里在 OpenTelemetry 社区长期投入，贡献语义规范、各语言项目（Go、Java、Python）和 coding 场景 Agent 采集；并发布开源项目 LongSight——基于 OpenTelemetry 标准做扩展、回馈社区，数据以 OTLP 协议可发任意后端。数据之上用开源 uModel 做关联、BRISE 做评估实验。

重点项目：OBI（OpenTelemetry eBPF instrumentation）——基于 eBPF 面向无法改代码的系统，无侵入在任意语言、任意环境自动捕捉信号；kprobe 拦截网络请求采集，AI 场景自动识别大模型协议（OpenAI、Anthropic、Gemini、千问）并提取数据，输入输出、工具调用、MCP 调用、RAG embedding 完整采集——Agent Sandbox 难做侵入埋点，云监控的 Sandbox 可观测能力即基于 OBI。框架侧以 Apache Dubbo 为例：与社区为 RPC 类框架定义语义规范（含 trace、metrics），花了一年多到两年，范式拓展到网关、数据库、任务调度、消息等。Agent 领域语义规范：与社区共建 GenAI 语义规范，社区要求先有真实场景验证——联合阿里控股和蚂蚁集团推出集团内规范，验证后做成开源项目再回馈社区。两例：entry span 记录 Agent 一次对话入口的原始输入输出（有些框架会篡改用户原始输入）；step span——Agent 执行复杂任务可能迭代几十上百轮，每轮是一个 react 过程，逐轮清晰记录。skill 规范：记录 description、版本、何时加载。实现覆盖 AgentScope、LangChain 及 Claude Code、Codex 等 Coding Agent。推理引擎侧把请求一路透传——向 SGLang 等框架贡献观测能力，从请求级别到 prefill/decode/kv cache 各阶段再到 token 级别分级采集。coding agent 标准化采集用于定位问题、看 token 消耗、评测、优化 skill、安全审计。治理成果：大量 PR/issue 贡献，拿到多个社区 maintainer 和 approver 席位；大会前夕 OBI 又有成员新晋升 Approver。

#### 温希道：语义建模（uModel）与基准测试（BRISE）

温希道接棒：商业化产品线解决"采不到、看不清、读不懂、评不准"，再把核心能力通过开源、学术合作、论文发表获得社区反馈。

第二堵墙：上下文读不懂。读懂错误日志只是小小炫技，关键是让模型理解背后的数据、对象、关系、时间、来源；没有对齐，"agents 在每一次调查里都得一本正经地胡说八道"，SRE 难以相信。uModel 要做：围绕当前故障对象，把分散在各监控系统的指标、日志、链路、事件统一组织，形成可查询、可追溯、可补充证据的调查上下文。用 OTel Demo 的 Checkout Service 例子：业务感知的现象是成功率下降 7.5 个百分点；用户不关心是数据库、容器还是下游问题，只抱怨支付不顺畅。Agent 可访问的数据看似齐全：指标、日志、trace、CMDB、发布事件。时间线：10:01 一次发布（V2.4），10:04 数据库连接数变化，10:05 payment 超时——SRE 第一反应"是不是发布引起的"，合理但时间近不等于强因果；Agent 要确认：发布影响了哪些实例？连接数变化对应哪个 MySQL 对象？payment 超时与 Checkout 成功率下降是否在同一依赖路径上？必须把所有事实放进同一时间窗口判断。

uModel 三层：左，静态语义模型——定义 Checkout、Payment、MySQL、Pod 对象及调用/依赖/归属/运行关系，定义数据及规则动作；没有这层约束，同一对象在不同系统对不上。中，语义运行时——三个条件：焦点对象是 CheckoutService；时间范围 9:58~10:06 这 8 分钟；目标是排查"成功率为什么下降"（不是巡检）——无关数据全排除。右，任务上下文输出——对象实例、关系子图、状态快照、关键事实、证据及建议验证顺序。agent 反馈需要的字段：entity id（排查对象）、window（时间范围）、source reference（来自哪里）、plan（服务于排查链路哪个环节）——不失去最初问题边界，人可复查，另一 agent 可按链路 validate。实验证明能在不同模型上提高 50%~100% 的诊断质量。

开源 uModel 三件事：仓库已开源——是可运行、可查询、可接入 agents 的公共资产，从定义一个运维对象或一个查询开始；联合伙伴发起企业通用语义标准，可通过 MCP 把查询能力给 agents；对评测关键——固化对象关系、问题、时间窗口和查询入口，不同 agents 可横向比分数。

第三堵墙：验不准。上下文准备好了 agents 就能做对吗？"不见得。"demo 里 nail 几个问题、偶尔线上立功，不足以证明能力稳定可靠可让 SRE 信赖——系统状态随时变、故障证据每次不同，模型、工具、skill、提示词也不同。这是系统化的 experiment design & evaluation 数据科学问题，要固化故障环境、任务、评分标准，让同一问题被反复执行、被不同团队执行——这是 BRISE 的职责。金融场景用户问"防火墙入口 any 访问 any 的日志"——听着只是查日志，实际要明确方向、源目的、时间范围、字段含义——"关键词查到了，不代表这个题就能答对了"。

评测流程三角色分开：左边仿真应用——提供问题环境，背后是复杂仿真和大量故障注入；中间被测 agents——排查并记录过程和结论；右边 BRISE 负责评测。三件事分开，才能分别检查题目是否有效、有难度、有区分度，agents 怎么做，结果怎么判断。他参与了大概七季 AIOps 挑战赛，围绕故障定位——"故障定位是运维任务皇冠上的明珠"。现有开源 benchmark 主要围绕 RCA（OpenRCA、RCAEval、AIOps lab），但与日常运维有距离：日常工作分数据查询、巡检和异常分析、故障诊断，巡检占大头，benchmark 覆盖要补；产业界已把离线提测、线上回放、人工复核、版本回归接入研发流程；学术界从判结论转向看排查过程与推理合理性（SWE-bench 式轨迹检验）。因此分层评测：数据查询、巡检和异常分析、故障诊断。针对故障诊断已发布 RCA100 和 RCA200 数据集，更多题目在开源 pipeline。开源建设四条：更多 bad case 仿真；离线和 replay benchmark 固定环境与评分规则；故障处置闭环需严谨评测规范，可靠验证恢复且在安全边界内；云原生故障注入工厂——依托国家重点研发项目，与中科院软件所、清华、复旦、南开等共建，近期发布测试智能体报告和运维智能体报告。Take away：把运行事实通过采集可靠拉回来，让 agents 清楚获取调查上下文，让 AgenticOps 能力经得起反复评测——"AgentOps 能力走向生产，需要的不只是更强的模型，而是一套像这样持续建设的工程基础。"

## 这场的意义

对行业，这是"Agent 进生产"的完整拼图：采集侧用 OpenTelemetry 生态+eBPF+GenAI 语义规范把"运行事实"标准化带回来；理解侧用 uModel 固化为语义运行时；验证侧用 BRISE 固化成可反复执行的 benchmark。吉利和凌越证明这不是 PPT：一个把 MTTR 提升 7 倍、把运维从救火队变成规划师；一个把几百个 skill 运营成"有货架、有销量、有质检、有迭代"的 SKU 资产。全场最一致的判断：模型之外，数据飞轮、语义底座和评测体系才是真正拉开差距的地方。

对企业实践者，可直接搬走：双轨评测×三维指标×分级门禁；"宁缺毋滥"的归因纪律；高危操作三层防线加全程审计；"1530"式目标拆解——把口号变成介入时效、定位时长、恢复计时的硬指标；凌晨打挂生产的常态化攻防演练。

对个人，人机分工重新划线：发版权、审批权、关键决策权留在人手里。开发者护城河从写代码转向沉淀高质量 skill，运维者从"人肉找问题"转向定义巡检、验证假设、经营经验资产。懂采集规范、会建语义模型、能设计评测的人，正是这套工程基础最缺的人。
