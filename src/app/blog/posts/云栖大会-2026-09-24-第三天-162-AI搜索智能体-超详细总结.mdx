# 162-AI搜索智能体

> 云栖大会「AI 搜索智能体·从检索到推理」论坛，上午场，阿里云计算平台事业部 AI 搜索团队主办。四位讲者（邢少敏、杨孔仕、夏小文、汤贞杰）加一场五方圆桌（Qoder / EXA / 倍思 / 识季 / Elastic），把"AI 搜索"拆成三件可检验的东西：一套范式（Agentic Search 2.0）、一台可购买的引擎（Elasticsearch Agent 引擎版）、三个生产级证据（Qoder 千亿向量、倍思洞察、识季多模态主搜）。一场等于拿到"范式—引擎—选型—避坑"的完整决策材料。

### 环节二：邢少敏《新范式与新引擎：阿里云 Agentic Search 重塑 AI 搜索》

全场的定调之作，分"市场—新范式—新引擎"三段。

**市场：商业化验证已完成。** Google 在 I/O 大会披露 AI Overviews 月活超 25 亿、AI Mode 上线一年超 10 亿——AI 搜索已是"新的交互基础设施"。流量价值上，一家调研公司（转写 CNA Interactive）对真实客户跟踪 7 个月：AI 搜索转化率最高达传统搜索 9 倍，综合不同口径他判断为 4~6 倍。结论：企业必须"把高质量、可验证、可调用的知识喂给 Agent"。

**新范式：从答案到行动。** 三阶段：22 年以前信息查询，关键词进、结果出、人判断；23~24 年生成式搜索，理解问题、综合信源、生成答案；25~26 年"执行任务"——用户表达目标而非关键词，系统拆解任务、选工具、访问知识、执行操作，交付可验证结果，即"搜索的终点从'我知道了'变成了'我的任务完成了'"。Agentic Search 架构：上层覆盖行业报告、运维诊断、自动巡检、数据洞察、电商导购，任务在沙箱中安全隔离；核心是 Agent Loop——装载上下文、推理规划、决策执行，反馈闭环持续调优；向下对接数据库、大数据产品和阿里云 Elasticsearch/OpenSearch，统一搜索与任务执行。

**记忆与自进化。** LoCoMo（转写音"Lark"）记忆榜综合得分 96.69，覆盖单跳、多跳、开放域和持续信息任务；Long Memory 榜准确率 81.37，"环境陷阱识别仍然比较难"，是后续优化方向；token 节省 68.18%。记忆的目标是准确地选择更新和遗忘，而非越多越好。自进化闭环：多 Agent 协作形成规划、检索、执行、评审闭环，结果必须可验证（执行记录、质量分、纠错、证据）；过程数据汇入统一经验流，驱动三类进化——Memory 更新记忆并解决冲突，Skill 从成功经验抽取可复用步骤，知识库沉淀新知识、建立可信引用；能力下轮按需装载，全程可观测、可评估、可回滚。GAIA（复杂任务与工具调用鲁棒性）和 FutureX（信息流预测）两个榜单均第一。

**落地案例：ES Agent。** 底层采集日志、指标、事件；中间 Agentic Search 提供知识、记忆、Skills；对外是自然语言交互层，直接问"为什么我这个延迟比较高"即可得诊断。左侧运维诊断：Agent 汇总集群状态、日志、指标与历史事件，生成结构化报告，定位异常节点、原因与建议动作，"每个判断都有证据，不是泛化建议"，负载不均问题可直接让它自动 fix；右侧数据洞察：自动理解指标口径，判断出转化率为 0、订单延迟高、广告投放效率低、退货高等问题并给根因与建议。他预告 ES Agent 几个月内将覆盖购买、实例管理、索引配置、性能调优、数据洞察全生命周期——"未来使用 ES 不需要通过控制台，只用 ES Agent 这个交互入口"。

**新引擎：为 Agent 重建检索底座。** Agent 访问模式与人类搜索差异巨大：调用频率更高、数据更新更快、租户更多、结果必须被机器直接消费，企业还要求权限隔离、低延迟、低成本。亿级用户每用户一租户，不可能建一亿个索引，只能一个索引内 namespace 隔离。方案：OSS 作统一持久化存储，租户数据按 slice 组织，冷数据不长期占用计算和本地盘，查询时按需加载进内存和 SSD——整体成本省 70%，支持亿级租户，热查 60 毫秒、冷查 600 毫秒，读写分离、写入不影响查询。标杆客户 Qoder（转写"Coder"）用后综合成本为原方案 1/7，支撑数百亿文档、千亿级向量，代码秒级更新。内核：阿里云 ES 云原生内核与自研向量内核（转写音译失真）100% 兼容 ES API，使用方式不变，只是更快、更省、更稳；VectorDB 基准 QPS 超 8 万、召回率 98%、P99 延迟 1.8 毫秒；Rally Big5 典型查询相比社区 ES 最高提升 6.87 倍；另一项全文基准（转写"TachyV"）较其 0.26 版本提升约 2 倍。评估不能只看单点分数，要看高召回、持续写入、多租户下的稳定性。

最后是"阿里云 ES 知识引擎"：提取记忆、抽取 skill、沉淀知识，提供准确上下文、降低 token 消耗；Namespace 是租户与 Agent 的唯一身份，负责隔离路由；混合检索整合冷热温数据形成增长闭环——先检索个性化上下文支撑推理行动，再把验证过的经验沉淀为长期记忆库和专属知识库供下次复用。总结句："Memory 让上下文可积累，Skill 让经验可复用，知识引擎让企业资产在一个安全边界里持续地流动。"

### 环节三：杨孔仕《面向 Agent 时代的搜索基础设施：Elasticsearch Agent 引擎版》

上一讲说"为什么要变"，这一讲是"引擎怎么造"。开场立矛盾：过去搜索引擎服务人——一个搜索框、一次查询；今天越来越多服务 Agent——完成一个任务要反复检索知识、记忆、代码；而检索空间越来越多、数据要长期保存、活跃租户只是一小部分，Agent 引擎版就围绕这个矛盾设计。

**需求侧硬指标。** 租户可以是一家企业、一个知识库或一个代码工作区，最终要支撑千万级甚至亿级租户、千亿级向量检索；存储随数据自动扩展、计算随负载自动扩缩，不再人工规划分片；性能目标 P95 小于 100 毫秒、召回率大于 95%；内存只服务缓存工作集、存储用低成本介质。传统 ES 部署四项很难同时满足，现有方案检索耗时要秒级以上。五类约束：低频数据占磁盘内存、沉睡租户耗资源、海量小租户累积海量分片开销；跨租户无效读取随总量增长，推高延时、拉低召回；存算绑定让扩容恢复都要搬数据、读写混布争抢 CPU 和 IO。

**架构：OSS 唯一持久层 + 双计算层。** 最底层 OSS 存索引段文件、预写式日志（WAL）和元数据，是全系统唯一持久化层；写入层接收文档，WAL 先落 OSS 保证不丢，再异步建索引回写 OSS；查询层从 OSS 按需读取索引文件，本地内存和 SSD 只做两级缓存、不保存持久数据。两层资源分别配置、分别扩展，节点增减不搬数据。缓存按租户实际访问分配：先内存后 SSD，未命中才读 OSS 并回填；命中毫秒级返回，冷租户首查亚秒级，业务预知访问可提前预热。

**slice：把"租户"做成一等公民。** 每个 slice 对应一个租户的检索空间，同一租户连续存放，查询、缓存、预热只针对这份数据——查租户 C 只触达租户 C 的数据空间，成本只与它自身数据量相关，不牵动其他租户缓存。slice collection 把海量 slice 组成逻辑集合，业务只用一个集合名，租户扩大时后端物理索引和分片自动扩展，入口不变。写入层和查询层各有独立扩容策略，管控系统监测各层 CPU、内存、磁盘水位，高水位自动补节点、不搬数据，自动扩容十月份上线。

**向量侧：BBQ 量化 + 租户边界进索引。** 磁盘原生向量索引 BBQ：分层 K-means 把相近向量归簇，簇内数据连续成块、适合磁盘和对象存储；质心描述簇位置、向量量化成小编码；无需重建图，构建比 HNSW 快约 10 倍。查询三步：按质心筛相关簇，用簇内量化向量快速打分，选候选原始向量精排；簇内向量按 posting list 连续存放、顺序 IO；内存不足时优势更明显，延时曲线比 HNSW 平缓。传统做法（全局聚类再按租户过滤）的致命伤：目标租户在全局聚类中占比极小，整块读回的候选大量属于其他租户被丢弃，计算量、延时上涨，召回下降。解法 slice BBQ：把租户边界带进向量索引，每个租户在自己的数据范围内聚类，引入跳表索引记录每个租户的数据范围，查询直接跳到本租户的数据区间。全文侧同样把 ES 大部分索引租户化，包括原文和 doc value。

**无状态与弹性。** 持久化数据统一在 OSS、本地缓存可重建：节点故障时替换节点读元数据即可续服，写入侧靠 WAL 恢复未完成数据，故障恢复 10 秒级；扩容同理不搬数据；写入不可用时查询仍可服务。租户级原语三件：Warm slice 预热（打开工作区前提前加载，消除首查等待）；copy slice 后台复制租户数据、建独立环境；branch slice 更轻量——从 A 建 B 共享初始数据，B 的新增修改单独保存、可独立检索，分支秒级创建，额外存储只与对 B 的修改有关。

**收益对账。** 成本：整体降 70%，存储为原来的 20%、内存约 25%、CPU 约 50%；传统部署的内存和副本随总数据量同步增长，Agent 引擎版把计算和缓存只给活跃租户，增长平缓得多。性能：同一参考负载下热查 P99 60 毫秒、向量召回率 95%，自建 ES 参考值约 2 秒和 70%；查询聚焦租户自身数据后，其他租户增长不带来额外读取和计算，全局租户数与总量上升时延时和召回更稳；冷查含 OSS 读取约 600 毫秒，可预热化解。购买页选 9.X Agent 引擎版，索引/查询节点按负载选规格数量，存储按量付费。

**四类典型场景。** 企业知识库 RAG（每企业/部门/知识库一租户，切分建全文+向量索引，秒级可查，租户内混合检索生成回答）；AI coding（每仓库/工作区一空间，打开预热、变更自动更新，branch slice 派生工作区与分支）；行业 AI（法律金融按机构建库，高召回低延时混合检索）；终端记忆（手机、车载助手每用户独立记忆，增删及时生效）。他把全场最想留的一句话放在屏幕中间："查询的范围由租户自身的数据决定——一个知识库的查询，不应该因其他租户变多而承载更多无关的读取和计算。"

### 环节四：夏小文《Qoder 与 Elasticsearch：千亿向量检索引擎的生产级落地》

引擎故事的"甲方验证"：Qoder 团队（花名陈安）讲为什么选 ES Agent 引擎版、怎么用、跑出什么数据。

**为什么要检索引擎。** Qoder 是主打编程领域的产品矩阵，延伸出任务平台、JetBrains 插件与 CLI、Agent SDK、办公场景 AI 数据员工（转写"coder wake"）。Coding 领域上下文极度分散——代码、符号、提交记录、wiki 散落各处，必须由检索引擎聚合、提炼、裁剪、精炼重排，给 Agent"精确而全面"的上下文。挑战：单库成本控制在 1 元/月以下（越低越好），检索延时 P95 尽量小、支持高并发单库检索，还不能影响 Agent 效果。他调研过 ES 开源版等方案，问题是大规模数据下"数据越多性能越差、成本指数级提升"。选 Agent 引擎版的理由承接上一讲：冷热分离、租户可扩到亿级、只有热数据参与查询、"只为活跃数据付费"。

**检索管线。** 查询理解以前用小模型拆 query（拆实体、语句），现在大模型效果够好，小模型直接砍掉。第一阶段多路召回：向量、关键词、符号、提交历史 commit，外加扩充的记忆与企业知识库，结果 merge 去重；再通过图索引"扩图"做宽关系扩展；最后重排融合输出。线上评测体系验证了重排后比单点检索效果好很多。ES 侧主要用向量做语义检索——检索本身简单，重活在索引与 embedding 数据管理：Manager 管代码数据与权限，数据进消息队列，交给跑在函数计算上的 worker（方便动态扩缩容和限流），再写入 Agent 引擎版。

**租户建模与可靠性。** 关键决策：以 codebase 维度映射 ES 的 slice 租户——竞品有按用户维度建的，但用户维度数据量大、检索性能衰减；按需创建（真正开始写数据才建）、批量写入、召回带 codebase ID 和代码路径等过滤条件，之后融合处理。可靠性：效果稳定、出错快速恢复、每次查询结果可观测——"我们给 ES 团队提了很多需求，他们做得还是蛮好的"，动态扩缩容满足高可用场景，trace 关联与耗时 KPI 监控齐全。

**线上数据与对比结论。** 写入资源 30 多台 ECS、查询资源 5 台多（写入更重），已存千亿多个向量；查询支持 1000 QPS，写入峰值 1GB/s；存算分离下写入或查询遇瓶颈可动态扩、轻松撑 QPS。与一个屏蔽了名字的竞品对比：P50 检索耗时小约 3 倍，写入带宽在现有资源上提升约 5 倍，总体成本降到原先的 15%——"当初选型的压力来自成本，评估后发现不只是成本"。后续规划：记忆、企业知识库、跨仓库知识、RepoWiki，甚至 personal agent 的个人数据；上下文融合要"控制投放预算、保证证据来源、数据全面可追溯"，再统一去重重排。

### 环节五：汤贞杰《Agentic Search 2.0 与 Elasticsearch：AI 原生搜索智能体应用新范式》

产品负责人补上最后一块：范式要变成企业可用的基础设施，缺的不是模型，是工程体系。核心判断："真正企业级可用、可交付的 Agent，分水岭不来自模型，而来自 Agent 基础设施的完备性。"

**问题定义。** 大模型已能高质量问答与推理，但企业要把 AI 搜索承接成跨系统、长链路、可验证的真实任务时，任务并没有自动完成——人还在拆解问题、切换系统、核算多信息源冲突、组装报告；模型只负责一段内容，认知负担和完成确认都压在人身上。真正的链路：理解目标与完成条件 → 动态规划 → 取数调工具 → 验证结果 → 任务状态回写系统。

**长任务运行内核。** 任务以几十分钟到小时为单位运行时（非 coding 场景），一次跑完几乎不可能，需要部分环节人工确认，更需要 Agent Loop 把任务变成可持续校正的循环：确定目标、约束与完成条件 → 选搜索引擎、调工具、subagent 并行执行 → 检查数据、知识、证据的完备性与风险，更新状态（存 Elasticsearch 底座，含自进化 memory/skill）。最重的一环是任务 trace——记录每轮决策与结果，是问题定位、测评、自我改进的基础。复杂任务拆成执行图（Agent 场景的 DAG，大/小模型组合把任务依赖自主抽象成图），Agent Swarm 蜂窝式并行几十到上百节点，单节点失败只重试该节点、任务不重来；断点续传已实现，中间结果与证据留存，客户拿到"可恢复、可观测、可控"的长任务产品。

**上下文工程：本场信息密度最高的部分。** 他的定义：上下文是"一个任务或多个任务之中所需的最小充分信息"。即便大模型普遍支持百万级 token，也无法支撑企业长周期任务——受 token 预算和执行约束。上下文含四类信息：目标与任务内容、自进化 memory（跨任务经验、偏好、历史决策）、企业知识体系（多模态知识库成主流，含可验证事实与可追溯信源）、skill 操作内容。他点名最常见的落地错误："把四类信息直接扔到一个向量库里"——模型无法判断哪些优先级更高、哪些是当前输入、哪些历史要过滤或过期、哪些要做权限校验。2.0 的做法是分类治理：合并、去重、标注冲突、排优先级、层级摘要压缩，确保动态上下文窗口里信息足够完整、事实保真。

**记忆、自进化 skill 与知识引擎。** Agent Memory 已广泛用于阿里云 ES 知识引擎和 Agentic Search 的 Agent 引擎，复杂任务中召回、融合、冲突消解需整体规划。自进化 skill 从任务过程提取高质量 trace，自动抽取操作步骤、prompt 和工具组合，经权限检查与审核，明确用途、输入输出、依赖、权限与使用边界，客户无需手工创建。他特别纠正误解："自进化并不是 Agent 自动修改代码，而是一个受控的自我改进过程"——低质量 trace 做成测评样本，形成 debug prompt，对 prompt、memory、知识提供候选更正，再由人工或经验做回归验证。传统知识库以存文档为主，Agent 还要引用事实、可追溯来源、实体关系和任务最新状态；Agentic Wiki 做"自主知识蒸馏"，自动生成知识引擎并以 Graph 图谱呈现概念、实体与关系——关键不是再造孤立知识库，而是让存量搜索和数据资产继续被有效使用。

**四层检索编排与生态。** 检索只做一层很难兼顾权限、时效与优先级，故提供四层编排：memory → 摘要式检索增强（转写音含糊）→ Agentic Wiki 图谱 → Elasticsearch/OpenSearch 统一引擎（全文过滤、向量、多模态混合检索），把私域知识、长期记忆、公网信息统一召回。引擎版把搜索引擎升级为 Agent 的状态管理和基础设施：存储统一在 OSS 之下，保存任务状态、长期记忆、企业知识，多租命名空间支撑多用户多 Agent 并行。评估场景看三点：是否跨多数据源、有无明确验证与完成条件、是否需要留下企业级证据和执行计划。

**两个案例。** 倍思（转写亦作"贝斯科技"）：统一收集行业研报、产品资料与图文数据，自定义 prompt 模板做语义理解、data agent 整合与多路召回，生成深度研究报告并沉淀为知识资产。吉利汽车：不迁移 ES 现有数据资产，用自然语言实时分析 ES 上的数据资产，连接企业组织信息、表状态与业务指标，并按需绑定现有数据的动态权限。生态图景：Agentic Search 2.0 可作为 API 或 MCP 服务集成进其他 Agent 体系，为入口 Agent 提供共享记忆、技能、知识与上下文——图中含 Qoder、openclaw harness、data agent，可对接钉钉、飞书、网易、微信。落地路径："从可验证、可复用的任务开始，先打通数据权限和知识评测，再扩大任务边界"，从能回答逐步走到完成真实业务任务。

### 环节六：圆桌《从搜索引擎到 Agent 基础设施》

主持人汤贞杰携五位嘉宾，按"需求—技术—应用场景—展望"四轮推进。

**需求轮。** 夏小文：Qoder 前身是"通用零码"（通义灵码的转写音），代码补全时代对标 GitHub Copilot，最大痛点是让 AI 理解一句话需求——"把超时的订单自动取消"背后是好几个函数和代码引用关系，必须把符号、关键字、函数定义喂给模型。谢福王（EXA）：EXA 是"给 Agent 用的 Google"——传统搜索出口是 URL，用户点击厂商就挣到钱；Agent 不 care URL，只 care 与问题相关的内容，重构搜索可更第一性、更 token 高效；"去年大家还在喊堆 token，今年没人喊了，因为完全烧不起了"。邓银河（倍思）：洞察场景两个痛点——多岗位用同一份数据但口径不一，对齐报告时"扯皮"；通用 agent 工具的产出不懂你公司业务，必须注入企业知识才能"为你所用"。伊森（识季，跨境时尚奢品电商）：用阿里云 OpenSearch 加千问 embedding，以公司沉淀十年的时尚奢品商品认知数据微调，用户在主搜对话框直接自然语言搜商品——"想要印象画派风格的上衣"这类语义需求，以前只能匹配关键字吐出一幅画，现在语义直达商品，是单轮实时的 Agentic Search。朱杰（Elastic）：需求三段演进——向量时代（改进语义理解）→ RAG 时代（chunk、embedding、快速搜索）→ Agent 时代（组织上下文、构建记忆、调用 skills）；第二条脉络是成本：向量搜索一上生产发现成本兜不住，走向量化、磁盘检索，在精度、速度、成本间找平衡。

**技术轮。** 夏小文讲范式切换：补全时代是工程主导，单轮尽量给全信息（小模型拆 query 再融合）；Agentic 时代反过来，把向量、关键词、commit、wiki 检索封装成工具，AI 通过 ReAct 自己决策怎么调——"精确度、准确率有质的飞跃"。谢福王披露：coding agent 是 EXA 最大的一类客户，"大家日常用的绝大部分 coding agent 背后用的都是 EXA"，包括 Cursor、Lovable、Replit；用法明显变化——早期把网页全文丢回 agent 清洗推理，非常浪费 context window，长程任务第一步就把窗口堵死；从 Cursor 开始，大家把搜索 spin 成 subagent，只还给主线一个简单、高密度的回答。伊森讲多模态：电商约 80% 商品的标题、描述、商详信息不全，必须从图片挖维度；把十年时尚专家知识做成提示词标签体系，结合文本和图片，与千问 embedding 团队训出专属多模态 embedding 模型——长尾词场景点击率提升 20%，以往检索不到的长尾商品曝光量翻两倍多。邓银河讲工程闭环："以终为始"——报告必须被信任、被使用；从海量评论、会话、社媒数据先模型打标，再结合企业知识库精准召回，按洞察主题与结构规则出具报告；报告写四轮精准度还不够，浪费的 token 和时间成本都极大。朱杰纠偏：GPT 出现后一度"万物皆向量"，落地后关键词、精确匹配、grep 全被找回来——多模态 agent 必须向量，语义类（客服）用混合检索最佳，纯 coding agent 直接 grep；搜索引擎为 Agent 做了三件事：应对"子 Agent 同时发起 100 个搜索"的量变（硬件利用最大化）、数据自动配置调优（无法预知 Agent 生成什么）、接口适配（ESQL 中间数据算子 + MCP/skills/CLI）。

**应用场景轮。** 伊森补充数字：专属 embedding 图搜从专家评估约 35% 准确率提到 90% 以上——"以前只能搜白底图，现在越复杂的场景搜得越准"；商品运营以前每天花七八小时检索圈选商品，现在上传 10 张以内参考图加一段自然语言描述即可精准圈选，省约 70% 时间；多模态搜索会随延时下降成为所有产品的底层通用能力。谢福王讲了两个"规划外"场景：dating APP 在 match 时给用户做 KYC，录音类客户对会议录音做 fact check——"这些场景都不是我们规划的，都是莫名其妙就出现的"。追问市场量级，他给出两个判断："互联网本身是 AI 的 system of record"（权重再大也装不下所有信息且要不断更新），以及经验法则——搜索 spending 约是 LLM spending 的 5%~10%，基本线性，按当前速度增长，五六年后 AI 搜索的成本可能超过目前谷歌的广告收入。夏小文看办公 agent：本质与 coding agent 相同，最关键是企业知识库上下文，正探索多模态解析 PDF、word 入库，聊天图片里的文本和物体也可抽取沉淀。邓银河：对内，企业会走向 AI native 组织，Agent 像虚拟同事一样强依赖企业知识上下文和岗位记忆；对外，倍思将推更多 AI 硬件，跨设备的上下文与记忆决定设备是"AI 智能硬件"还是"AI 玩具"。朱杰预测：搜索引擎正在变成 AI 的数据底座，而 Agent 生命周期长短不一、动态建库用完即删，预留资源必然失效——"多租户加 Serverless 形态，下一年会爆发式增长"。

**收尾轮（展望 + 避坑）。** 夏小文：期待 Personal Agent 的检索与隐私保护成为搜索下一题；避坑——小批量文本检索别上复杂向量，关键字就很好。谢福王：安全正从应用层要求变成 infra 层要求，EXA 为政府和银行客户提供零数据留存策略。邓银河：做 Agent 不以量取胜，企业知识上下文与记忆才是核心；避坑——不要铺得面很大，从聚焦的、以业务价值和商业成功为导向的目标切入。伊森：期待 embedding 时延从几百毫秒压到 100 毫秒以内；避坑——"不要为了做一个 Agent 而去做一个 Agent"，领域核心竞争力（我们是时尚理解）不能丢，找准确定性场景、拆解上线、拿结果、形成正向 loop。朱杰：底层数据系统正变得越来越全能（搜索→向量→持续监测→分析）；避坑——标准 benchmark 覆盖不了真实场景，让 AI 生成贴合自己业务数据的 benchmark 实测，"不要直接看各种报告"。

## 这场的意义

**对行业：一份"搜索基础设施换代"的完整论证。** 全场形成闭环证据链：范式宣言 → 引擎重构（OSS 持久层、slice 多租户、BBQ 租户内聚类）→ 生产实证（Qoder 成本降至 15%、引擎整体省 70%）→ 应用范式（四层编排、上下文治理、受控自进化）→ 行业共识（混合检索回归、多租户+Serverless 将爆发）。成本叙事最关键：Agent 把检索从"一次查询"变成"一个任务几十上百次"，传统"数据越多越贵"的曲线第一次被"只为活跃租户付费"的架构掰弯——这是 Agent 经济能否成立的底层变量之一。EXA 的"搜索花费 ≈ LLM 花费的 5%~10%、五六年后 AI 搜索成本或超谷歌广告收入"测算，把技术讨论直接抬到产业格局层面。

**对做 Agent 的团队：可直接抄走的工程结论。** 一，上下文是"最小充分信息"，任务/记忆/知识/技能四类信息分库治理、标冲突、排优先级、层级压缩后再装载，不要一锅扔进向量库；二，长任务三件套——Agent Loop、执行图断点续传与局部重试、全程 trace（自进化与评测的原料）；三，检索封装成 subagent 只回主线高密度结论，保护 context window；四，租户建模先于选型——Qoder 用 codebase 而非用户做租户，直接决定成本与性能；五，别信公开 benchmark，用 AI 生成贴合自己业务的数据实测（朱杰建议），盯"高召回 + 持续写入 + 多租户"下的稳定性。

**对个人从业者：一轮清晰的定位信号。** 当引擎层把"检索"商品化（ESQL、MCP、按量付费），单纯"会调向量库"的价值会快速稀释；圆桌反复强调的是另一侧——领域 Know-how（识季的时尚理解、倍思的企业知识治理）和基础设施判断力（成本、租户建模、评测设计）才不可替代。用伊森的话说：找准确定性场景，拆解、上线、拿结果、形成正向循环——这既是 Agent 落地的方法论，也是个人在这轮搜索换代里的生存策略。
