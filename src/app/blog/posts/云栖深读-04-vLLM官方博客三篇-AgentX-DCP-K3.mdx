# vLLM 官方博客三篇深读：AgentX / DCP / K3

> 来源：vllm.ai/blog 三篇（2026-07 ~ 2026-09），云栖演讲 Reference 页 2-4 号链接。

## ① vLLM × AgentX: Optimizing for Real-World Agentic Serving（2026-09-08）

**负载画像**（AgentX = SemiAnalysis 用真实 agent 编码轨迹造的基准）：长会话、每轮重放增长上下文、**输入中位 142K token、短输出、>96% prefix 命中、subagent 密集**。

**优化清单**：混合 KV 管理+共享块池；DeepSeek V4 packed cache 布局；经 Mooncake Store 的分层卸载（CPU/磁盘）；会话感知的前缀保留策略；长 prefill token 阈值破 head-of-line blocking；DEP rank 间 prefill 节奏对齐；P/D 两阶段速率匹配法。

**结果**：最高 83K token/GPU·s（DeepSeek V4 Pro）；服务成本比 Opus 5 API 便宜 14.6×~106×。**经验教训**：流水线并行适合冷 prefill 不适合热轮次（热轮次 KV 传输需求反转）。**预告**：agent hints 与可编程 KV cache。

## ② Efficient Decode Context Parallelism（2026-08-07，NVIDIA+Red Hat AI）

**问题**：TP 按 KV 头切分，GQA 到头数封顶；MLA 等效 1 KV 头 → latent cache 每卡全量复制，长上下文 agentic 负载显存爆炸。

**机制**：KV 沿序列维切片到各卡；每步 AllGather Q（很小）→ 本地部分注意力（LSE 在线 softmax 合并）→ 合并。一个 flag 开启：`--decode-context-parallel-size`。

**数字**：8×B200 跑 Kimi K2.6（NVFP4）：TP 基线并发 64/KV 100%/1863 tok/s/GPU 封顶；DCP 并发 512/KV 82%/**6091 tok/s/GPU**（3.3×），200K+ 序列性能稳定。

## ③ Kimi K3 Day-0 Support（2026-07-27）

**模型**：月之暗面 2.8T 参数多模态 MoE、1M 上下文。架构三新：KDA（线性注意力混合堆叠）、AttnRes（跨层注意力残差混合）、LatentMoE（896 专家激活 16，分位数平衡路由，原生 MXFP4）；chat 模板用 Python render 程序替代 Jinja。

**性能**：TP16 单流 118 tok/s，配 DSpark 投机解码 370 tok/s（3.14×，低熵任务每步接受 4.73 token）；KDA metadata builder 870μs→34μs（-96%）；skinnyGEMM 小 batch 再省 ~10% 端到端；MoE tail fusion 7-8%。基准：GSM8K 0.976 / GPQA-D 0.939。最低硬件：8×B300 或 16×B200，AMD MI355X 同步支持。

## 我的扩展

1. **三篇是一条因果链**：K3 定义了"MLA/线性混合+巨上下文"的新模型形态（③）→ 这形态让传统 TP 失效催生 DCP（②）→ agent 把这些模型放到最极端的负载下再逼出 AgentX 全家桶（①）。
2. **可编程 KV cache 是下一步看点**：AgentX 预告的方向 = 把 KV 块的准入/驱逐/传输策略从引擎内置变成应用可编程——和 tair-kvcache Manager 的多匹配策略（前缀/滑窗/KV 匹配）是同一趋势的两端（引擎侧 vs 独立服务侧）。
3. **冷热轮次的分水岭**：AgentX 教训的通用化——长上下文服务没有全局最优并行策略，冷 prefill（算力型）和热轮次（KV 传输型）要不同配置，动态切换是开放问题。
