# 自己的代码也不敢直接开源：LinguaLens 从 v0.1 到公开仓库，我审计了什么

> 你在读 Hacker News，评论区有人写了一句 "get through to him"。划词翻译回来是「与他接通」，可上下文明明在聊「说服一个人」，跟电话没有半点关系。你卡住的不是生词，是"为什么这里这么说"。市面上的翻译工具把英文变成中文就收工，这个"为什么"没人管。于是我动手自己写了一个，六天后把仓库公开了。这篇文章讲这六天，重点讲开源之前我审计了什么。

## 一、结论先行

LinguaLens 已经在 GitHub 公开：仓库 [istoolsfox/lingualens](https://github.com/istoolsfox/lingualens)，MIT 许可，2026-11-10 上线。产品一句话概括：**选中即精读的 Chrome 扩展——不止翻译，还讲透英语为什么这样表达。**

这篇文章讲三件事。第一，六天版本史里三个真 bug 是怎么被抓住的——靠的不是灵感，是假服务器、真浏览器、端到端实测三样基建。第二，开源前的三重审计怎么做的，历史、现场、人三层，每层都有可照抄的命令。第三，一个 zip 打包的压缩格式坑，讲清 zlib 包裹和裸 deflate 的区别。

先给结论：开源最难的不是代码写得好不好，是"你不确定自己没漏什么"。密钥只要在 git 历史里出现过一次，事后删掉也没用，历史照样翻得出来。所以审计要按层走，逐层排除，不能靠"我记得没提交过"。

## 二、先说清它是什么：不止翻译

LinguaLens 的核心是"划词精读"。选中任意英文（单词、短语、句子、段落都行），扩展自动路由到合适的分析模式，返回结构化讲解：双轨翻译、意群拆解、语法"为什么"、词汇构词、中英表达差异。看完还能多轮追问、收藏进知识库、基于收藏生成练习并让 AI 批改仿写。

AI 输出有一份硬纪律，写在 prompt 里当约束：不编造词源和语法规则；不确定的必须标注；把知识分成语法规则、语言习惯、作者风格三类，讲作用、不贴标签。翻译工具最常见的毛病是"一本正经地胡说"，这条纪律就是冲着它去的。

技术骨架也不复杂：React 18 加 TypeScript strict 加 Vite 双构建；没有后端，AI 请求由浏览器直连你选的厂商（OpenAI 兼容接口）；API 密钥用 AES-256-GCM 加密存本机。这个"无后端"设计后面还会提到，它是审计能全净的前提。

## 三、六天版本史：挑四个节点讲透

先交代时间线。2026-11-05 上午 11 点 40 分第一笔提交，当天连发 v0.1 到 v0.4 四个版本；11-06 打磨交互与失败治理；11-10 上午完成 v0.6.2 并开源。六天一共 15 笔提交、9 个版本。下面挑四个节点讲透。

**节点一：v0.1，一天写完全部功能，但没真机跑过一次。** v0.1 的验收表写得很诚实：TypeScript 零错误、46 个单测全绿、加密密文落盘验证通过；可是"加载扩展冒烟""真实模型验收""E2E"三行全是待办标记。当天就吃到两个平台坑：manifest 里声明了 default_locale，项目里却没有 _locales 目录，扩展直接加载失败；MV3 的 content script 不支持 ESM 模块，必须单独打成单文件 IIFE。教训一句话：单测绿了只证明逻辑对，不证明扩展真能用。

**节点二：v0.4，假服务器加真浏览器，抓出一串真 bug。** 用户反馈"还是不行、没状态、没嵌入"。诚实的回答是：前三版全程没在真机浏览器里跑过。于是搭了两样基建：一个假 OpenAI 兼容服务器（按 prompt 特征分流假响应，还能注入故障），加 Playwright 自维护 Chromium 真加载扩展跑流程。第一轮 E2E 就抓出四个真 bug。

最要命的一个：翻译管线无条件给所有端点传 jsonObject 参数，不支持这个参数的端点每批都回 400，整篇翻译直接中止——用户说的"没嵌入"，实锤就是它。配套治理跟着上线：一批解析失败不再整体中止，改成去 JSON 模式重试一次、仍败就跳过该批继续；再加覆盖度校验点名，模型漏答的段落显式标失败，不装作翻完了。

基建本身也有坑。Chrome 137 起系统 Chrome 移除了 --load-extension 参数，E2E 只能用 Playwright 自带的 Chromium。断言也踩过假阳性：失败占位文本会冒充译文节点，所以断言只认真译文文本。

**节点三：v0.6，HN 只翻 4 段的真因。** 现象很怪：在 Hacker News 页面按"文章翻译"，只翻出 4 段。排查出的根因很有代表性——正文定位的启发式把第一条评论误认成了正文容器，这一小块只占全页文本约 1%，于是"正文"就只剩它。修法是加一道守门：候选容器占全页可见文本不足两成就不认，HN 这类讨论帖自动切成整页注入；单页上限也从 5 万字符提到 8 万。启发式这东西像凭感觉圈地，得给它配一条机器能判定的验收线。

**节点四：v0.6.2，60 秒热重载自更新。** 用户的核心诉求是不想每次都删除重装。方案是两条更新通道：本地磁盘热重载——扩展后台每分钟比对 dist 目录里的 manifest 版本号，磁盘版本一更新，60 秒内自动 reload，零点击、本地数据全保留；远程通道每 6 小时拉一次版本清单，有新版就在弹窗顶部出提示条。版本号定为单一真源 public/manifest.json，APP_VERSION 常量和 zip 产物名都跟随它，另有单测断言防漂移。这套机制上线前，verify-selfupdate.mjs 把触发链整条实测过一遍。

## 四、开源前，我审计了什么（本文重点）

把仓库从私有改成公开，不是"现在的代码没问题"就完了。Git 会把每一版底稿都留着：哪怕某个密钥后来删掉了，历史里照样翻得出来。这就像草稿纸的背面没撕，你写新版之前，得先把背面检查一遍。所以审计分三层走——历史（git 全记录）、现场（工作区文件）、人（个人信息）。

**第一层：git 全历史。** 做法是全量翻账。`git log -p` 把每次提交的每行改动都吐出来，扫常见密钥模式：sk- 开头的 API Key、ghp_ 开头的 GitHub 令牌、Bearer 令牌、password 字样。再专门查"删过的文件"（`git log --diff-filter=D --summary`），密钥最容易藏在这里——写了又删，工作区干净了，历史里还在。结果全净，原因也简单：项目从第一天就把密钥挡在 .gitignore 外，密钥只存浏览器本地加密，从不进仓库。审计的价值不在抓到什么，而在确认"没有"。

**第二层：工作区。** 历史之外还有现场，查三样东西。一是未跟踪文件：.gitignore 挡的是 git，挡不住工作目录里的真实文件，打包时容易夹带。二是截图产物：E2E 存了十几张真机截图，要逐张确认没拍到密钥输入框和个人目录路径。三是构建产物：output 和 dist 里是否混入本地私有内容。

**第三层：个人信息。** 最后查"人"。每个提交的作者名和邮箱是否适合对外；代码、注释、文档里有没有本机用户名和绝对路径；有没有公司客户名和内部业务细节。这一层的权重和密钥相同——密钥泄露丢资产，个人信息泄露丢隐私，而且隐私往往没法像密钥那样换一个了事。

**审计能全净，靠的是设计不是运气。** 三重审计零发现的前提，是密钥本来就不在仓库里。LinguaLens 无后端，AI 请求由浏览器直连厂商；API 密钥用 AES-256-GCM 加密落盘，加密钥匙是设备自己的 WebCrypto 密钥，相当于给密钥配了台只认本机的保险箱。保护边界也在 README 里如实写了：这套加密防"密钥明文泄露"，不防"设备被完全控制"。本地加密的诚实边界就到这，不吹。

**可照抄的六条审计清单**：

1. `git log -p --all` 全量翻改动，配合 grep 扫密钥模式（sk-、ghp\_、AKIA、Bearer、password）
2. `git log --diff-filter=D --summary` 专查删过的文件
3. 核对每个提交的 author 和 committer 邮箱，确认适合对外
4. 工作区查三样：未跟踪文件、截图、构建产物
5. 全仓 grep 本机用户名、绝对路径、公司客户名
6. 收尾再跑一遍密钥正则扫描，确认零命中

## 五、打包脚本那个"解压必炸"的真 bug

先说现象。自动更新机制上线后做端到端实测——下载新 zip、解压、覆盖、重启——更新包解压必炸。顺藤摸瓜，问题出在自写的打包脚本 zip.mjs：它为了零依赖，手工拼 ZIP 字节。

原理分两半讲。ZIP 本身不压缩，它是个集装箱格式：每个条目在头部声明"这箱货用什么方式压过"，method 8 代表 deflate 算法。关键在于 deflate 数据有两种包装。Node 的 zlib.deflateSync 输出的是完整 zlib 格式：数据前面带 2 字节头（十六进制 78 9c），后面跟 4 字节校验尾。而 ZIP 的 method 8 要的是裸 deflate 流——只有压缩数据本身，不加任何包裹。

打个比方：zlib 格式像商品外面又套了个带品牌封条的快递箱；ZIP 集装箱要求货物裸着放进去，直接贴运单。解压端按 method 8 开箱，先读到的却是 78 9c 这两个字节，这不是合法的 deflate 数据，当场报错。而且这个错是全量的：脚本给每个文件用的同一套压缩，所有压缩条目一起炸。

修法一行：deflateSync 换成 deflateRawSync，后者输出的正是裸流。

```js
// 修复前：zlib 完整包裹（78 9c 头 + 数据 + 校验尾），ZIP 解压端必炸
const comp = deflateSync(data);

// 修复后：裸 deflate 流，ZIP method 8 要的就是它
const comp = deflateRawSync(data);
```

为什么单测没拦住？因为单测里没有"用真实解压器读回来"这一步。抓到它的是端到端实测：下载、解压、覆盖、重启，整条链跑一遍。教训一句话：压缩成功不等于压缩对了，打包格式的对错，只能靠按格式读回来验证。

## 六、开源化还做了什么

代码之外，开源当天还补了几件事。LICENSE 换成 MIT，一句话说明：可自由使用、修改、分发。README 从开发者视角重排成用户视角：为什么做这个放在最前面，安装给出三条路（下载安装包、油猴 Lite 版、源码构建），隐私与安全独立成节，最后附一份"已知问题诚实清单"——卸载后页面浮动栏残留是 Chrome 平台限制、iframe 内不注入、本地加密的保护边界，都明说。

仓库门面也整了一遍：About 简介、10 个 topic、产品截图。安装包发布到 toolsfox.top/downloads；同一份源码还构建出油猴 Lite 版，不需要扩展权限，Tampermonkey 和脚本猫都能装。质量基线留在明面上：70 个单测全绿、16 项真机 E2E 断言、TypeScript strict 零错误。

## 七、总结与行动清单

| 问题 | 答案 |
|---|---|
| 它是什么 | 选中即精读的 Chrome 扩展：翻译之外，讲透"为什么这样说" |
| 仓库 | github.com/istoolsfox/lingualens（MIT，2026-11-10 开源） |
| 技术骨架 | React 18 + TS strict + Vite 双构建；无后端浏览器直连 AI；密钥 AES-256-GCM 加密 |
| 开发节奏 | 6 天 15 笔提交，v0.1 到 v0.6.2 共 9 个版本 |
| 最贵的一课 | 单测全绿不等于能用——真机 E2E 第一轮就抓出 4 个真 bug |
| 最意外的 bug | zip 打包用了 zlib 包裹而非裸 deflate，压缩条目解压必炸 |

想把自己项目开源的，行动清单照抄：

1. 先跑上面六条审计清单，历史、现场、人三层各过一遍
2. 密钥从第一天就别进 git——事前一行 .gitignore，比事后翻历史便宜得多
3. 打包格式类代码，测试必须含"按格式读回来"的端到端验证
4. README 写一节"已知问题"，诚实清单比完美人设攒信任

最后收个尾。这六天真正值钱的不是扩展本身，而是一条纪律：**代码可以一天写完，信任得一层层挣。开源之前，先把自己当成第一个审计者，把 git 历史、工作区、个人信息翻个底朝天；让用户敢把 API 密钥填进去的，从来不是 README 里"安全"两个字，而是"作者审计过自己"这件事。**
