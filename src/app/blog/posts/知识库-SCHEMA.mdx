# SCHEMA —— 04-knowledge 知识库宪法 v1.0

> 本文件是整个知识库的"操作宪法"，实例化自 Karpathy《LLM Wiki》模式（2026-04-05 Gist）。
> AI agent 动 04-knowledge 之前**必须先读本文件**；修改本文件必须记入 `log.md` 并升版本号。
> 角色分工：**人选源、提问、把关；LLM 做全部 bookkeeping。**（"Obsidian is the IDE; the LLM is the programmer; the wiki is the codebase."）

## 1. 三层地图（本 workspace 的对应物）

| 层 | Karpathy 原版 | 本库对应 | 规则 |
|---|---|---|---|
| Raw Sources | raw/ 原始资料 | 各门类 `_raw/`；历史存量在 `03-resources/`（云栖转写、ai-evals 等，不搬家） | **只读，LLM 永远不改写 raw**。新 raw 一律放所属门类 `_raw/`，放哪门类由主题归属决定 |
| The Wiki | wiki/ 知识层 | 04-knowledge 下除 `_raw/` 外的所有 md | LLM 全权读写维护：摘要页、概念页、实体页、对比页、综合页、门类 README |
| The Schema | CLAUDE.md 类配置 | 本文件 + 根目录 AGENTS.md | 本文件管知识库；AGENTS.md 管全 workspace（铁律、项目台账） |

## 2. 页面六型（每页 frontmatter 必标 `type`）

| type | 含义 | 现成例子 |
|---|---|---|
| `source` | 来源页：一个来源一页（论文/书/演讲/网站），要点提炼 + 指向 `_raw` 或外链 | 云栖逐场总结 |
| `concept` | 概念页：技术/理论/方法论概念 | KV Cache、LLM Wiki 本身 |
| `entity` | 实体页：人/公司/产品/模型 | Karpathy、DeepSeek、胖东来 |
| `synthesis` | 综合页：多来源合成的顶层结论 | social-mechanics 各课题 SYNTHESIS.md |
| `comparison` | 对比页：结构化对比表 | DESIGN-SYSTEM 变体表 |
| `index` | 索引页：目录 + 每页一行摘要 | 根 `index.md`、各门类 README |

frontmatter 模板：

```yaml
---
type: concept        # 六型之一
tags: [rag, memory]
created: 2026-09-28
sources: ["_raw/xxx.pdf", "https://..."]
status: stable       # stable | draft | outdated（被新来源推翻时改 outdated 并链接新页）
---
```

## 3. 链接纪律（边界写死）

- **04-knowledge 内部互引**：用 Obsidian wikilink `页面名`，可带别名 `显示文字`。这是知识图谱的边。
- **指向 raw / 外网 / 跨目录**：普通 markdown 链接 `文字`。
- **铁律：各项目仓库（01-projects 等）内文档禁止 wikilink**——项目要 push GitHub，GitHub 不渲染 `...`。项目内一律相对路径。
- 建页面时至少回链一处（防孤儿页）；被引用次数多是枢纽页的信号。

## 4. 事实纪律（继承既有铁律，科普化/简化不放水）

- 数字必须带来源和日期；未核实的数字/名称/归属一律标【待核实】。
- 置信度三档标注：[实锤] / [二手] / [待核实]。
- 新文献先登记（source 页）再引用；结论必须挂来源。
- 数据更新写新日期文件，**不覆盖旧档**（历史演化也是知识）。

## 5. 三操作 SOP（对 AI agent 的操作手册）

### Ingest（触发口令："消化 XX" / "把 XX 收进知识库"）
输入：新来源（PDF/链接/转写/剪藏，已放或待放门类 `_raw/`）。
流程：读原文 → 建/更新 source 页 → 交叉引用更新相关 concept/entity/synthesis 页（**单来源典型触碰 10–15 页**，发现矛盾当场标注）→ 更新门类 README 页表 → 更新根 `index.md` → 追加 `log.md` → **git commit 一笔**（消息格式 `[ingest] 主题`）→ 向用户汇报触及了哪些页、发现了哪些矛盾。

### Query（触发口令："知识库里 XX 是什么" / "用知识库回答 XX"）
流程：先读根 `index.md` 定位 → 读相关页 → 带引用（页名+路径）合成回答。
**回写义务**：回答有沉淀价值（新对比、新综合、新洞见）必须回填成新页面或并入既有页，否则知识消失在聊天记录里。回填后同样走 README/index/log/commit。

### Lint（触发口令："知识库体检"）
流程：先跑 `05-scripts/wiki_lint.py`（机械预检：死链、孤儿页、frontmatter 缺失、`【待核实】`存量）→ LLM 深查：矛盾说法、被新来源推翻的旧结论、缺失交叉引用、该建未建的概念页、可用搜索补的数据空缺 → 出报告（分"必修/建议"两档）→ 用户点头后修 → log + commit。
频率：机械预检可随做随跑；语义深查每月或重大事件后一轮。

## 6. log.md 格式

append-only，永不删改旧条目。条目前缀固定，保证 `grep "^## \[" log.md` 可解析：

```
## [YYYY-MM-DD] ingest|query|lint|schema | 主题
- 一行做了什么
- 触及页面列表（wikilink）
- 遗留问题（无则省）
```

## 7. git 纪律

- 本目录是独立 git 仓库（远程 istoolsfox/knowledge 私有仓），**每轮操作至少一笔 commit**——这是防幻觉篡改的保险丝，也提供完整版本历史。
- `.gitignore` 排除：嵌套 git 仓库（rust-learning、gewu-llm-knowledge）、.DS_Store、大体积二进制。
- 仓库级身份：istoolsfox \<istoolsfox@users.noreply.github.com>。

## 8. 页面命名

- 主题类：`主题-子题.md` 或课题目录内编号（沿用各门类既有惯例，不强制统一）。
- source 页：`来源简称-内容标识.md`（如 `云栖-vLLM演讲-2026-09.md`）。
- 概念/实体页用其通用名（如 `LLM Wiki.md`、`Karpathy.md`），保证 wikilink 自然。
