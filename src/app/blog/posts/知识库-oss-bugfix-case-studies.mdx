## 案例一：pgx #2644 —— "半修"与"完整修复"的距离（我们输在这里）

**背景**：#2640——GORM `PrepareStmt:true` 走 `Prepare(ctx, sql, sql)`，语句在服务端叫 `stmt_<sha256>`，客户端却按 SQL 文本做 key。prepare 在 Describe 阶段失败时，清理逻辑记住的是客户端 key，之后发的 Close 指向一个不存在的名字：真语句泄漏在服务端，该连接上重试同一 SQL 永远 42P05，清理报错还会炸到连接池里下一条无关查询。

**实际落地**（merge 01d2fd3，jackc 2026-09-07 合并，零评论，两个 commit）：

1. **改名半**：`c.failedDescribeStatement = psKey` → `= psName`（用 Parse 实际发送的名字，不是客户端 key）。
2. **完整半（我们没看到的）**：`errors.As(err, &pErr) && pErr.ParseComplete`——**只有 Parse 真正完成才调度清理**。Parse 本身失败（如语法错误）时服务端根本没建语句，此时发 Close 是一次多余的往返，还可能把错误炸到无关查询上。

两个测试分别钉死两个语义：`TestPrepareWithDigestedNameHandlesTimeoutBetweenParseAndDescribe`（泄漏断言直接查 `pg_prepared_statements`）、`TestPrepareFailedParseSchedulesNoCleanup`（断言**没有** Close 消息发出）。

**出了什么问题**：
- 同题三个 PR 在场：#2642 已占"改名"半壁，#2644 是完整修复，我们的 #2646 只有改名半——**即使不被关，也已经是第三份重复劳动**。
- 我们的 diff 和他们第一半逐字等价，但没人想到多问一句"要清理的东西真的被创建了吗"。守卫条件就写在 `PrepareError.ParseComplete` 这个现成字段里，我们读了类型却没读语义。
- 他们 PR 正文的写法值得抄：生产事故经 GORM 全栈复现（v5.10.0 连接中毒 vs 分支上首试即恢复）+ 每个 commit 单独红绿声明（"both new tests fail before their respective commit and pass after"）+ 主动交代"我见过 #2642，这是补全另一半"。

**教训**：修"失败后的清理"类 bug，必问三连——失败发生在哪个协议/阶段？那个东西真的被创建了吗？清理动作本身会不会失败并污染别的请求？

## 案例二：pydantic #13767 —— 维护者怎么修我们诊断过的 bug

**背景**：#11329（我们做过根因诊断）——mypy 插件在 import cycle 下崩溃：Base 的字段引用 Sub（TYPE_CHECKING 前向引用形成环），插件推迟处理 Base 时，Sub 已经处理完，Sub 扫 MRO 找不到 Base 的 metadata，字段丢失。

**实际落地**（Viicos，2026-09-07 合并，单 commit）：

1. 每个 类 一进 `transform()` 就打标记：`info.metadata.setdefault(METADATA_TAG_KEY, {})`——"处理中"的墓碑。
2. `collect_fields_and_class_vars` 扫 MRO 时：基类没有 `METADATA_KEY`（没处理完）但**有 tag**（确实是 pydantic 模型）→ 显式 `return None, None` 触发另一轮，而不是默默跳过。
3. 字段没 ready 且 `not final_iteration` 时显式 `self._api.defer()`。**两个 defer 都有 final_iteration 守卫**——mypy 最终轮后不再重试，防无限推迟。
4. 测试是真实的双文件 import cycle fixture（`import_cycle.py` + `import_cycle_base.py`），不是 mock。

**出了什么问题（细节级的坑）**：测试里故意用 `nam=` 触发未知字段调用，结果 `nam` 被 codespell 当错别字报——连 fixture 的字段命名都要在 `pyproject.toml` 的 `ignore-words-list` 加一个词。**fixture 命名也是要过工具链的**。

**对我们的意义**：我们当时的诊断（deferral 时序 → metadata 缺失）被官方修法完整证实，但**诊断正确不得分，ship 的人得全部 credit**。诊断型贡献的价值在建立信誉和防止自己犯错，不在功劳簿。

## 案例三：celery #4251（2017）—— 复杂调度修复的"专用回调 + 接线测试"形状

**背景**：rate_limit 与 ETA 并存时 ETA 任务绕过限流（我们 #5810 考古的原点）。

**修法形状**（ca962fa7）：
- consumer 加专用方法 `_limit_post_eta`：先 `decrement_eventually`，bucket 有内容就排队，否则立即调度——**ETA 后的限流语义收进一个命名清晰的方法**，不散在策略代码里。
- strategy.py 把它接进 `call_at(eta, limit_post_eta, ...)`。
- 测试不测复杂时序，测**接线**：断言 `timer.call_at` 被以 `_limit_post_eta` 为回调调用。

**可复用模式**：延迟/异步语义的正确性靠"回调身份断言"钉死，不需要真实等待。我们的 #5810 实验和 #10595 文档都受益于先读懂了这个形状。

## 案例五：tqdm #1781 —— 归一化到既有路径

**修法**：`total == inf` 时直接 `total = None`——**不新增任何 inf 分支，把非法输入映射到既有的"未知总量"合法路径**：

```python
if total and (n >= (total + 0.5) or total == float("inf")):  # allow float imprecision (#849) or inf (#651)
    total = None
```

**测试**：一行等价性断言 `format_meter(5, float("inf"), 1) == format_meter(5, None, 1)`，塞进现有 `test_format_meter`。

**review**：casperdcl 一句 "Thanks! fixes/follow-up to #651" 直接批——**他把 PR 关联回了 9 年前的原始 issue #651**。给维护者递上历史脉络（这修的是哪个老问题的尾巴）本身就是 review 加速器。

## 案例六：tqdm #1778 —— 防御性早退，不重构

**修法**：`__init__` 半途失败后 `close()` 炸 AttributeError。修法是两道最小守卫：

```python
if getattr(self, 'disable', True):   # 未初始化时取安全默认值 True = 直接返回
    return
...
if not hasattr(self, 'last_print_t'):  # 从没显示过就无事可清理
    return
```

**模式**：初始化顺序类 bug 的修法是"给每个可能缺失的属性一个安全默认 + 早退"，**不是**把初始化重排成两阶段。review 同样一句 "Thanks!" 秒批。

## 案例七：zap #1567 —— 外部贡献者的行为变更怎么让维护者放心

**修法**（外部贡献者 fudongyingluck，sywhang "lgtm" 合并）：`AtomicLevel.ServeHTTP` 补 Content-Type——正常/业务错误路径设 `application/json`，内部错误兜底路径显式设 `text/plain; charset=utf-8`。两行 Set + 每条路径一个断言。

**关键在 PR 正文**：逐条列出行为变化，并明确声明 **"Response bodies and status codes are unchanged"**——把"我改了什么/没改什么"划清楚，维护者就不需要自己排查副作用。这就是我们 zap #1586 里"空值回退字节级兼容"声明的同款打法，已被验证有效。

## 跨案例模式总结

### 修法形状（学这个）

| 形状 | 案例 | 适用 |
|---|---|---|
| 归一化到既有路径 | tqdm #1781 | 非法/极端输入：映射到已有合法分支，不新增平行分支 |
| 防御性早退 | tqdm #1778 | 初始化顺序/生命周期：安全默认 + hasattr + 早 return，不重构 |
| 专用回调 + 接线断言 | celery #4251 | 延迟/异步调度：语义收进命名方法，测试断言"以正确回调被调度" |
| 标记 + 检测 + 显式 defer + 终轮守卫 | pydantic #13767 | 多阶段处理/环依赖：tag 处理中状态，检测到未完成依赖就推迟，防无限轮 |
| 清理前先验证存在 | pgx #2644 | 失败恢复：问"失败发生在哪个阶段，那东西真的创建了吗" |

### 出过的问题（防这个）

1. **半修**（我们 #2646 中招）：只修表象半（名字错），没修条件半（ParseComplete）。修复 = 改对 + 守卫对，缺一即半。
2. **同题 PR 密度远超想象**：pgx 一题三 PR（#2642 改名半 / #2644 完整 / #2646 我们）。撞车检查必须搜"同题 open PR"而非只看 issue 时间线。
3. **诊断正确 ≠ 有 credit**（pydantic #11329）：ship 的人拿全部功劳；诊断的价值是信誉和自我纠错。
4. **fixture 命名也会挂工具链**（pydantic 的 `nam` 触发 codespell）：新增测试文件前过一遍 lint/拼写配置。
5. **维护者对干净 PR 极少摩擦**：全部 7 案 review 往返近零（"Thanks!"/"lgtm" 秒批或原样合并）。摩擦集中在语义完整性（少了守卫、副作用未声明），风格问题几乎不存在——**把副作用声明写进正文（"X unchanged"）是最高性价比的 review 加速器**。
6. **给维护者递历史脉络**：tqdm #1781 被关联到 9 年前的 #651 立刻合。提 PR 前考古"这是不是老问题的尾巴"并写明，价值双向。

### 对在途战线的直接启示

- **zap #1585/#1586**：#1567 证明 zap 对外部行为变更 PR 的模式就是"明确声明不变量 → lgtm"。我们的字节级兼容声明已在正确轨道上，耐心等 review。
- **psycopg #1400 / celery #10595**：docs PR 两种结局（维护者亲改 / 原样收）都出现了，净零告警验证是拿到"原样收"的门票。
- **未来一切"失败清理"类 bug**：先抄 pgx 三连问（案例一末）。
- **未来一切初始化顺序类 bug**：先抄 tqdm #1778 两道守卫。
