## 1. 设计总原则（先于一切模式）

| 原则 | 含义 | 违反的典型症状 |
|------|------|----------------|
| KISS | 保持简单，最简单可行的方案优先 | 为了炫技引入框架/抽象层，三行代码能解决的事写了三层 |
| DRY | 不要重复自己：知识在系统中有唯一权威表示 | 同一业务规则在 5 处复制，改一处漏四处 |
| YAGNI | 不为想象中的未来需求写代码 | "以后可能用到的"参数、配置项、泛型接口堆满代码 |
| 关注点分离 | 一段代码只负责一类事 | 一个函数里同时做参数校验、业务计算、写库、发邮件 |
| 最小惊讶 | 代码行为与命名、直觉一致 | `getUser()` 内部悄悄写了数据库 |
| 组合优于继承 | 用对象组合/委托复用，慎用深继承 | 继承树 5 层深，改基类全崩 |

**执行口径**：重复第 3 次才抽象（Rule of Three）——第 1、2 次重复容忍，第 3 次必须收敛；YAGNI 与 DRY 冲突时，YAGNI 优先。

## 2. SOLID 详解

### 2.1 S — 单一职责（SRP）
一个类/模块只有一个变化的理由。

```python
# 反例：一个类三个变化理由（解析、计算、输出）
class Report:
    def load(self): ...
    def calc(self): ...
    def save_to_db(self): ...

# 正例：拆为 ReportParser / ReportCalculator / ReportRepository
```

判据：描述这个类职责时说不出"以及"两个字，就是单一职责。

### 2.2 O — 开闭（OCP）
对扩展开放、对修改封闭：新增行为靠**加代码**，不靠**改老代码**。手段是多态+注入，不是无限抽象。

```python
# 反例：每加一种支付方式都要改 if/elif
def pay(method, amount):
    if method == "alipay": ...
    elif method == "wechat": ...

# 正例：新增支付方式 = 新增一个类
def pay(channel: PaymentChannel, amount): channel.pay(amount)
```

红线：只有当"变化确实在反复发生"才上 OCP，否则是过度设计（YAGNI 优先）。

### 2.3 L — 里氏替换（LSP）
任何父类出现的地方，子类替换后行为不变。经典反例：`Square extends Rectangle`（正方形不能替换长方形，`setWidth` 语义被破坏）。子类**不得加强前置条件、不得削弱后置条件、不得抛出父类不声明的异常**。

### 2.4 I — 接口隔离（ISP）
接口小而专：客户端不应被迫依赖它不用的方法。8 个方法的大接口拆成 2-3 个按角色划分的小接口。Python/Go 里的体现：接受"鸭子类型/小 interface"参数而非巨型类。

### 2.5 D — 依赖倒置（DIP）
高层模块不依赖低层模块，两者都依赖抽象。业务逻辑层定义 `UserRepository` 接口，基础设施层实现它——换数据库不动业务代码。

```
反例：Service 直接 import MySQLClient（业务被基础设施绑架）
正例：Service → UserRepository(接口) ← MySQLUserRepository / MemoryUserRepository(测试用)
```

## 3. GoF 设计模式：精选与适用场景

23 种模式全景见软考集 03 §5。实践中**高频且安全**的是下面 10 个，其余模式先怀疑"是否真的需要"。

| 模式 | 一句话用途 | 何时用 | 常见误用 |
|------|-----------|--------|----------|
| 工厂方法 | 把"创建哪个类"的决定收敛到一处 | 创建逻辑含条件分支、依赖注入装配 | 为只有一个实现的类套工厂 |
| 策略 | 同一算法族可互换 | 计价规则/排序策略/风控规则按配置切换 | 只有一个实现还抽象 Strategy |
| 观察者 | 一对多事件广播、解耦发布方与订阅方 | 领域事件、消息推送 | 链式触发失控，事件流难以追踪 |
| 装饰器 | 动态叠加职责 | 加缓存/日志/重试包裹原函数 | 层数 >3 后调用栈不可读 |
| 外观 | 给复杂子系统一个简单门面 | 对外暴露的 SDK/Service 层 | 门面变成上帝类 |
| 适配器 | 转换不兼容接口 | 封装第三方 SDK，隔离外部变更 | 内部模块之间互相适配（说明分层错了） |
| 模板方法 | 固定骨架、子类填空 | 导出流程：取数→加工→渲染 三步固定 | 钩子方法泛滥，流程被架空 |
| 单例 | 全局唯一资源 | 进程内配置、连接池 | 拿单例当全局变量用，测试无法隔离 |
| 建造者 | 分步构造复杂对象 | 参数 >4 个可选的构造、SQL/HTTP builder | 三参数对象也上 builder |
| 代理 | 控制访问（懒加载/鉴权/远程） | RPC stub、权限切面 | 与装饰器边界不清时先选装饰器 |

## 4. 反模式黑名单

| 反模式 | 症状 | 处方 |
|--------|------|------|
| 上帝类/上帝服务 | 一个类/服务占 30%+ 代码，人人都要改 | 按职责拆分，见 02 模块划分 |
| 面条式回调/嵌套地狱 | if 嵌套 5 层 | 卫语句提前返回、提取函数 |
| 硬编码 | 魔法数字、写死的 URL/密钥 | 常量、配置、环境变量（密钥见 10） |
| 隐式魔法 | 靠调用顺序/全局状态才能正确运行 | 显式传参、依赖注入 |
| 过早优化 | 没有度量就调性能 | 先测量（13），热点只优化 top 20% |
| 复制粘贴编程 | StackOverflow 代码未消化直接入库 | 理解后重写，风格对齐本集 08 |
| 熔岩流/死代码 | 注释掉的大段代码、永远 false 的分支 | 删掉——Git 历史会记住它 |

## 5. 设计检查单

- [ ] 每个类/模块能用一句话说清职责（无"以及"）？
- [ ] 新需求是"加代码"还是"改老代码"？是前者才算 OCP 达标
- [ ] 业务层有没有直接 import 具体基础设施（DB/HTTP 客户端）？
- [ ] 抽象是否有 ≥2 个真实实现或明确可预见的变化点？没有则回退为具体类
- [ ] 用的每个设计模式能说出"解决什么问题"？说不出就删
- [ ] 卫语句是否消掉了深层嵌套？
- [ ] 有没有注释掉的死代码、未使用参数？删
