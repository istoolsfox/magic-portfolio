# 02 架构设计与风格选型

> 关联文档：软考集 [07-架构设计规范](/blog/%E7%9F%A5%E8%AF%86%E5%BA%93-%E8%BD%AF%E8%80%83-%E8%BD%AF%E4%BB%B6%E8%AE%BE%E8%AE%A1%E8%A7%84%E8%8C%83-07-%E6%9E%B6%E6%9E%84%E8%AE%BE%E8%AE%A1%E8%A7%84%E8%8C%83)（架构概念全景）；本文给选型决策规则与分层落地规范。
> 关联：[03-系统设计方法论](/blog/%E7%9F%A5%E8%AF%86%E5%BA%93-%E8%BD%AF%E4%BB%B6%E7%A0%94%E5%8F%91%E8%A7%84%E8%8C%83-03-%E7%B3%BB%E7%BB%9F%E8%AE%BE%E8%AE%A1%E6%96%B9%E6%B3%95%E8%AE%BA)、[04-分布式系统设计规范](/blog/%E7%9F%A5%E8%AF%86%E5%BA%93-%E8%BD%AF%E4%BB%B6%E7%A0%94%E5%8F%91%E8%A7%84%E8%8C%83-04-%E5%88%86%E5%B8%83%E5%BC%8F%E7%B3%BB%E7%BB%9F%E8%AE%BE%E8%AE%A1%E8%A7%84%E8%8C%83)

## 1. 选型决策：先单体，按需拆分

**默认答案永远是"模块化单体"**。微服务解决的问题（独立部署、独立扩缩容、团队自治）在团队 \<10 人、日活 \<10 万的场景下大多不存在，而它的成本（分布式事务、运维复杂度、联调成本）却是真实立即支付的。

| 维度 | 单体 | 模块化单体（默认） | 微服务 | 事件驱动 |
|------|------|--------------------|--------|----------|
| 适用团队规模 | 1-3 人 | 3-15 人 | >15 人、多团队 | 有明确异步业务流 |
| 部署/运维成本 | 最低 | 低 | 高（需容器编排、链路追踪） | 高 |
| 事务一致性 | 本地事务，最简单 | 本地事务 | 分布式事务（见 04） | 最终一致 |
| 独立扩缩容 | 不可以 | 不可以 | 可以 | 按消费者扩 |
| 何时选择 | 原型、内部工具 | **绝大多数业务系统的起点** | 模块间部署节奏/负载差异极大，且组织已按模块分工 | 消息推送、订单流、日志管道等天然异步流 |

**从单体拆出微服务的合法信号**（满足至少两条再动手）：
1. 某模块的发布节奏明显快于其他模块，且互相拖累；
2. 某模块负载特征特殊（如 AI 推理需 GPU、视频转码需 CPU 集群），需要独立扩缩容；
3. 团队按业务线分工后出现"改一处代码要两个团队协调发布"；
4. 故障隔离需求：某模块频繁 OOM/重启会拖垮全局。

**反信号**（出现任何一条就不该拆）：数据模型强耦合（拆开就要分布式事务）、团队没人有运维微服务的经验、"听说微服务先进"。

## 2. 模块化单体落地规范

1. **按业务能力划分模块**，不按技术层划分。顶层目录见业务（`orders/`、`users/`、`payments/`），不见技术（禁止顶层只有 `models/ views/ utils/`）。
2. **模块间依赖单向、无环**。用工具强制（Python 用 import-linter，Java 用 ArchUnit，前端用 eslint-plugin-boundaries）。发现循环依赖即视为架构 bug。
3. **模块间只通过公开接口（service 层）调用**，禁止跨模块 import 对方的 model/dao 内部实现。
4. **每个模块自带数据访问**，共享的只有身份与公共库表引用，不直接 join 别的模块的表（这条守住了，未来拆微服务就是搬代码；守不住就是永久耦合）。
5. **公共代码下沉 `shared/`，且只放无业务语义的东西**（工具函数、基础类型）。`shared/` 不得反向依赖任何业务模块。

```
app/
├── orders/          # 订单模块：api.py(对外接口) service.py models/ repo/
├── users/
├── payments/
├── shared/          # 零业务语义的工具
└── main.py          # 组装入口
```

## 3. 分层规范（无论哪种风格都适用）

经典四层，**依赖只能自上而下**：

| 层 | 职责 | 允许依赖 | 禁止 |
|----|------|----------|------|
| 接口层（api/controller） | 参数解析校验、调服务层、组装响应 | service | 直接操作数据库、写业务规则 |
| 服务层（service） | 业务规则、事务边界、编排 | repo、其他 service、外部接口 | 出现 HTTP/SQL 细节 |
| 数据访问层（repo/dao） | ORM/SQL、行与实体转换 | model | 业务判断 |
| 基础设施（infra） | DB 客户端、缓存、MQ、第三方 SDK | — | 被上层反向感知细节 |

**整洁/六边形架构的核心同一条**：业务核心不依赖任何框架和 IO 细节，依赖箭头全部指向核心。判断标准——业务 service 能否在不启动数据库、不发网络请求的单测里跑？（见 09）

## 4. 服务内部结构规则

1. **一个函数一个抽象层级**：controller 里不出现 SQL，service 里不出现 JSON 序列化细节。
2. **事务边界在 service 层显式声明**，禁止在 repo 内部隐式开事务。
3. **外部系统调用一律隔离在 adapter（适配器）里**：超时、重试、熔断参数集中在 adapter 配置，业务代码只见接口（见 04 §6）。
4. **配置分层**：代码只读配置对象，来源（环境变量/文件/配置中心）在启动装配时决定；配置项必须有默认值并在 README 记录。

## 5. 技术选型规则

- **选型即决策，必须写 ADR**（模板见附录 A），至少记录：背景、候选方案、决策理由、放弃理由、复审条件。
- 优先级：团队已掌握 > 社区主流且活跃 > 性能最强/最新潮。
- 引入一个新依赖前问三个问题：维护活跃吗（近 6 个月有提交）？出了 bug 我们有能力自己修吗？有没有更轻的替代？
- 每引入一样新技术，同步在项目 README 登记用途和负责人，避免"考古式依赖"。

## 6. 架构评审检查单

- [ ] 架构风格选择有 ADR 记录，且当前规模未过度设计？
- [ ] 模块按业务能力划分，依赖单向无环（工具已验证）？
- [ ] 跨模块只走公开接口，不碰对方内部表/实现？
- [ ] 分层清晰：接口层无业务规则、服务层无 IO 细节、业务核心可脱离基础设施单测？
- [ ] 外部调用收敛在 adapter，统一超时/重试/熔断？
- [ ] 每个关键技术选型有 ADR，含放弃理由与复审条件？
- [ ] 预留了演进路径（模块边界清晰，未来可拆）而不是直接过度拆分？
