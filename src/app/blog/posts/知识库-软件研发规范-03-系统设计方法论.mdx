# 03 系统设计方法论

> 关联文档：[02-架构设计与风格选型](/blog/%E7%9F%A5%E8%AF%86%E5%BA%93-%E8%BD%AF%E4%BB%B6%E7%A0%94%E5%8F%91%E8%A7%84%E8%8C%83-02-%E6%9E%B6%E6%9E%84%E8%AE%BE%E8%AE%A1%E4%B8%8E%E9%A3%8E%E6%A0%BC%E9%80%89%E5%9E%8B)、[04-分布式系统设计规范](/blog/%E7%9F%A5%E8%AF%86%E5%BA%93-%E8%BD%AF%E4%BB%B6%E7%A0%94%E5%8F%91%E8%A7%84%E8%8C%83-04-%E5%88%86%E5%B8%83%E5%BC%8F%E7%B3%BB%E7%BB%9F%E8%AE%BE%E8%AE%A1%E8%A7%84%E8%8C%83)、附录 A（ADR 模板）
> 本文回答：接到一个系统/功能设计任务时，按什么流程产出一份经得起评审的设计。

## 1. 系统设计四步法

任何规模的设计（从一个小功能到一个新系统）都走同一条链，只是深度不同：

```
① 澄清需求与约束 → ② 估算规模 → ③ 高层设计（API+数据模型+架构图） → ④ 深挖热点与瓶颈
```

### 第 ① 步：澄清需求（30% 的思考量在这里）
- **功能**：核心用例是什么？明确"不做什么"同样重要，写进设计文档。
- **非功能**（决定技术方案的就是它们）：
  - 一致性 vs 可用性：钱、库存、配额 → 强一致；点赞、浏览数、推荐 → 最终一致可接受；
  - 延迟要求：交互式 \<200ms？后台任务无所谓？
  - 峰值流量：日常/峰值/活动瞬时三个数；
  - 数据增长：一年后多大？冷热分层需求？
- **约束**：团队能力、预算、已有基础设施（自建 PG？云上？）、合规要求（数据出境、留痕）。

### 第 ② 步：估算（back-of-envelope）
用估算数字决定技术路线，而不是拍脑袋：

```
QPS 估算：日活 100 万 × 人均 20 次写 ÷ 86400s ≈ 230 写/s，峰值按 ×3 ≈ 700 写/s
存储估算：100 万用户 × 每天 10 条 × 500B × 365 ≈ 1.8 TB/年（判断要不要分表/归档）
带宽估算：峰值 QPS × 平均响应体大小
缓存容量：热数据集（通常 20% 数据扛 80% 读）能否放进内存
```

经验锚点：单机 MySQL 读 ~5k QPS（有索引）、写 ~2k；单机 Redis 10 万 QPS；Nginx 单机数万 QPS。估算结果决定：要不要缓存、要不要读写分离、要不要分库分表。

### 第 ③ 步：高层设计
产出三样东西，缺一不可：
1. **架构图**：框图级别，标出组件、数据流方向、同步/异步边界；
2. **API 草案**：核心 5-10 个端点（按 06 规范），先定契约；
3. **数据模型**：核心实体关系图 + 关键表结构（按 07 规范），明确主键策略。

### 第 ④ 步：深挖热点
对着架构图逐个自问：
- 哪里是单点？挂了怎么办？（→ 05 高可用）
- 读多还是写多？读多→缓存（→04 §4）；写多→异步/分片（→04 §7、§8）
- 哪两个组件之间耦合最紧？能否改异步消息？
- 数据一致性的关键路径在哪？跨服务写的补偿方案？

## 2. 设计文档模板（最小可用版）

```markdown
# <功能/系统名> 设计文档
## 1. 背景与目标（做什么、不做什么、成功指标）
## 2. 需求与约束（功能列表、非功能指标：QPS/延迟/一致性/数据量）
## 3. 总体设计（架构图 + 组件职责 + 数据流）
## 4. 详细设计（API 契约、数据模型、关键流程时序图）
## 5. 关键决策记录（每条链到 ADR）
## 6. 容量与性能（估算数字、压测计划）
## 7. 失败模式分析（每个外部依赖挂掉/超时/返回脏数据时系统的行为）
## 8. 上线与回滚方案（灰度策略、回退步骤、监控指标）
## 9. 开放问题（未定项与负责人）
```

规则：**失败模式分析（第 7 节）不可省略**。评审设计时最常见的翻车点不是功能没覆盖，而是没人问过"如果 Redis 全挂了会怎样"。

## 3. 权衡记录（ADR）

所有"二选一"级别的技术决策写 ADR（一条一个文件，模板见附录 A）。触发写 ADR 的最小集合：
- 架构风格/框架/数据库/中间件选型；
- 一致性级别选择（强一致还是最终一致）；
- 同步改异步、引入缓存、引入消息队列；
- 任何"当时吵过架"的决定。

ADR 是 append-only 的：新决策推翻旧决策时，把旧的标记为 Superseded 并链接新的，**不删除不篡改**——这是系统演进的化石层。

## 4. 评审设计时的标准问题清单

评审别人设计（或自查）时，按顺序问：

1. 最坏情况下哪个组件先倒？倒了之后用户看到什么？
2. 数据量 ×10 后，哪个环节先撑不住？
3. 这里有几处双写/跨库操作？失败补偿是什么？
4. 缓存与数据库的一致性策略是什么？缓存击穿/穿透想过吗？（→04 §4）
5. 异步链路里消息丢了/重复了怎么办？（→04 §5、§6）
6. 这个设计里有多少新概念？能否砍掉一半？
7. 一年后回头看，这个设计最先会被推翻的部分是什么？为什么现在还要这么做？

## 5. 检查单

- [ ] 明确写了"不做什么"？
- [ ] 非功能需求有具体数字（QPS、延迟、数据量、一致性级别）？
- [ ] 有容量估算，且估算数字驱动了技术选择？
- [ ] 架构图、API 草案、数据模型三件套齐？
- [ ] 每个外部依赖的失败模式有分析且有兜底？
- [ ] 关键决策有 ADR，含放弃理由？
- [ ] 上线方案含灰度与回滚步骤？
