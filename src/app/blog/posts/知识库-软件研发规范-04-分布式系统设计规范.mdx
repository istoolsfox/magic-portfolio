# 04 分布式系统设计规范

> 关联文档：[03-系统设计方法论](/blog/%E7%9F%A5%E8%AF%86%E5%BA%93-%E8%BD%AF%E4%BB%B6%E7%A0%94%E5%8F%91%E8%A7%84%E8%8C%83-03-%E7%B3%BB%E7%BB%9F%E8%AE%BE%E8%AE%A1%E6%96%B9%E6%B3%95%E8%AE%BA)（何时需要本文）、[05-高可用与性能设计规范](/blog/%E7%9F%A5%E8%AF%86%E5%BA%93-%E8%BD%AF%E4%BB%B6%E7%A0%94%E5%8F%91%E8%A7%84%E8%8C%83-05-%E9%AB%98%E5%8F%AF%E7%94%A8%E4%B8%8E%E6%80%A7%E8%83%BD%E8%AE%BE%E8%AE%A1%E8%A7%84%E8%8C%83)
> 适用时机：单体撑不住、或引入缓存/队列/多实例时。每引入一样新机制都应写 ADR。

## 1. 一致性模型：先选级别，再选手段

| 级别 | 含义 | 适用 | 手段 |
|------|------|------|------|
| 强一致 | 任何时刻读到的都是最新值 | 账务、库存扣减、配额 | 数据库事务、分布式事务、单点写入 |
| 最终一致 | 短暂不一致，收敛时间可接受（秒~分钟级） | 计数、搜索索引、缓存、跨服务副本 | 消息队列 + 幂等消费、对账任务 |
| 读己之写 | 自己写的自己立刻可见（别人可以晚见） | 发帖后自己刷新能看到 | 写后短时间内读主库 / 会话粘住主库 |

**默认规则**：能用最终一致就不要强一致；需要强一致的路径尽量收敛到单个数据库的事务里，缩小范围。

## 2. CAP 与超时：分布式三问

任何跨节点调用前必答三问：**对方挂了怎么办（超时设多少）？对方慢了怎么办（重试几次）？重试导致重复怎么办（幂等怎么做，见 §6）？** 没有答案就不允许上线这个调用。

## 3. 分布式事务：从上往下选，能用简单的就不用复杂的

1. **首选：本地事务 + 业务收敛**。把需要一致的操作塞进同一个库的同一个事务。能靠"设计"解决的就别靠"协议"。
2. **次选：消息最终一致（本地消息表/事务性发件箱 Outbox）**。业务表和"待发消息表"在同一本地事务中写入，后台任务把消息投递到 MQ，消费方幂等处理。避免"库改成功了、消息没发出去"。
3. ** Saga（编排式）**：长流程拆成 T1..Tn 与补偿 C1..Cn，失败逆序补偿。适合跨服务的多步业务（下单→扣库存→扣款）。必须为每步写补偿逻辑并测试。
4. **禁用**：2PC/XA 这类强阻塞协议（吞吐差、协调者单点），除非特殊场景。

## 4. 缓存规范

### 4.1 使用前提
先证明需要：读 QPS 超过数据库舒适区（MySQL 读 ~5k）、或单次查询计算成本高。**缓存不是默认组件**，每处缓存都要能回答失效策略。

### 4.2 模式选择
- **Cache-Aside（默认）**：读→查缓存→未命中查库并回填；写→先更新库，再删缓存（不是更新缓存）。理由：删除幂等、避免并发写缓存导致脏数据。
- 只读不写的数据（字典、配置）：可启动时加载进本地内存，进程内缓存优先于分布式缓存（少一跳网络）。

### 4.3 三大问题与标准处方

| 问题 | 场景 | 处方 |
|------|------|------|
| 穿透 | 查询不存在的 key，每次都打到库 | 空值缓存（短 TTL）；或布隆过滤器前置 |
| 击穿 | 热 key 过期瞬间大量请求打库 | 互斥锁重建（只放一个请求去查库）；热点 key 逻辑过期不失效 |
| 雪崩 | 大批 key 同时过期 / 缓存实例宕机 | TTL 加随机抖动（如 3600±600s）；缓存集群高可用；库端限流兜底 |

### 4.4 一致性底线
缓存与库的双写不一致窗口是客观存在的，规范是：**明确容忍窗口并在文档写明**（如"≤1s"），涉及强一致的数据（余额）不进缓存或用"写库后删缓存 + 延迟双删"并接受复杂度前先评审。

## 5. 消息队列规范

- **何时引入**：削峰（写入洪峰转平稳消费）、解耦（上游不需要知道谁在消费）、异步（用户请求主链路之外的旁路动作：通知、积分、审计）。三者都不沾就不引入。
- **必配四件套**：
  1. **幂等消费**：消费端按业务键（order_id）去重表/状态机判断，消息必重复；
  2. **失败处理**：重试 N 次 → 死信队列（DLQ）→ 告警 + 人工/定时补偿。禁止无 DLQ；
  3. **顺序性**：仅对必须顺序的业务（同一订单的状态流转）保证分区/队列内有序，不要全局有序；
  4. **监控积压**：consumer lag 指标 + 积压阈值告警（见 13）。
- **消息体**：带 `message_id`、`occurred_at`、`schema_version`；只传 ID+最小字段或事件全文二选一，团队内统一，禁止混用。

## 6. 外部调用与容错四件套（适配器层统一实现）

| 机制 | 默认参数 | 说明 |
|------|----------|------|
| 超时 | 连接 1s / 读取 3s，按下游 P99×2 设 | **没有超时的调用等于允许系统被拖死** |
| 重试 | 最多 2-3 次，指数退避 + 抖动；只重试幂等操作或幂等化后的操作 | 不可幂等的写调用绝不裸重试 |
| 熔断 | 连续失败率 >50%（窗口 ≥10 次）打开，半开试探恢复 | 防止故障传导；用现成库实现，不手写 |
| 降级 | 返回兜底值/缓存快照/功能开关关闭 | 降级预案写进 05 的预案表并演练 |

## 7. 幂等性规范（写接口默认要求）

所有写操作、所有消息消费、所有回调（支付通知！）必须幂等。手段从优到劣：
1. **状态机**：`UPDATE orders SET status='paid' WHERE id=? AND status='unpaid'`，影响行数为 0 即重复请求，直接返回成功；
2. **唯一键**：业务唯一键（订单号+操作类型）落表，冲突即重复；
3. **去重表/token**：客户端先取 `request_id`，服务端记录已处理集合。
4. ⚠️ `INSERT ... ON DUPLICATE KEY UPDATE` / upsert 也是幂等手段，但注意会掩盖并发冲突语义，需评审。

## 8. 数据规模演进路线（按顺序走，不跳级）

```
① 索引与 SQL 优化（先怀疑自己的查询，见 07）
② 读写分离（读扩展；注意主从延迟，读己之写场景读主库）
③ 归档与冷热分层（90% 的"数据太大"靠归档解决）
④ 引入缓存（扛读，见 §4）
⑤ 分库分表（最后手段）：先垂直按业务拆库，再水平按 shard key 拆表
```

分表规则：shard key 必须是绝大多数查询的过滤条件（如 user_id）；分片数一步到位（预估 3-5 年量级，如 16/32/64），避免二次扩容；跨片查询/事务在设计期就要识别并给出方案（冗余字段、异构索引表、ES）。

## 9. 分布式 ID

| 方案 | 特点 | 适用 |
|------|------|------|
| 数据库自增 | 简单、有序、单点瓶颈 | 单库小系统 |
| 号段模式（DB 发号段，应用内存分配） | 趋势递增、高可用、实现简单 | **默认推荐** |
| 雪花算法 Snowflake | 趋势递增、不依赖存储；需处理时钟回拨 | 高并发、无 DB 依赖场景 |
| UUID v4 | 无序（索引性能差）、无业务含义 | 仅非索引场景（如 trace id） |

## 10. 检查单

- [ ] 每个跨节点调用有超时、重试策略，且重试目标已幂等化？
- [ ] 一致性级别按数据性质明确选定并写进设计文档？
- [ ] 每处缓存能回答：失效策略、穿透/击穿/雪崩怎么防、容忍的不一致窗口多长？
- [ ] MQ 消费幂等、有 DLQ、有积压告警？
- [ ] 写接口全部幂等（状态机/唯一键/token 至少其一）？
- [ ] 分库分表是最后一招，且 shard key、分片数、跨片查询方案已定？
- [ ] 所有新引入的分布式机制有 ADR？
