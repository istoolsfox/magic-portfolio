# 05 高可用与性能设计规范

> 关联文档：[04-分布式系统设计规范](/blog/%E7%9F%A5%E8%AF%86%E5%BA%93-%E8%BD%AF%E4%BB%B6%E7%A0%94%E5%8F%91%E8%A7%84%E8%8C%83-04-%E5%88%86%E5%B8%83%E5%BC%8F%E7%B3%BB%E7%BB%9F%E8%AE%BE%E8%AE%A1%E8%A7%84%E8%8C%83)、[13-可观测性与运维规范](/blog/%E7%9F%A5%E8%AF%86%E5%BA%93-%E8%BD%AF%E4%BB%B6%E7%A0%94%E5%8F%91%E8%A7%84%E8%8C%83-13-%E5%8F%AF%E8%A7%82%E6%B5%8B%E6%80%A7%E4%B8%8E%E8%BF%90%E7%BB%B4%E8%A7%84%E8%8C%83)
> 关联软考集：[06-部署与交付规范](/blog/%E7%9F%A5%E8%AF%86%E5%BA%93-%E8%BD%AF%E8%80%83-%E8%BD%AF%E4%BB%B6%E8%AE%BE%E8%AE%A1%E8%A7%84%E8%8C%83-06-%E9%83%A8%E7%BD%B2%E4%B8%8E%E4%BA%A4%E4%BB%98%E8%A7%84%E8%8C%83)（交付流程）

## 1. 可用性目标：先定 SLA，再谈架构

| 可用性 | 年停机时间 | 适用 |
|--------|-----------|------|
| 99% | 3.65 天 | 内部工具、原型 |
| 99.9% | 8.76 小时 | 一般业务系统（**默认目标**） |
| 99.95% | 4.38 小时 | 核心交易链路 |
| 99.99% | 52.6 分钟 | 支付、基础设施层 |

规则：SLA 写进设计文档并对外口径一致；**为达不到 99.99% 的系统按 99.99% 做架构是浪费**，按目标反推冗余级别。

## 2. 高可用三板斧

### 2.1 去单点
- 逐个盘点组件：应用（多实例 + 负载均衡）、数据库（主从自动切换）、缓存（集群/哨兵）、MQ（集群）、对象存储（云上天然多副本）。
- 每个单点都要回答：挂了会怎样？恢复要多久？有没有自动切换？
- **应用无状态化**是第一原则：会话/文件外置（Redis/OSS），实例可随时增减。

### 2.2 容量冗余与隔离
- 常态水位 ≤50%：峰值翻倍时不需要扩容就能扛；
- 核心与非核心隔离：报告生成、爬虫、AI 推理这类重任务放独立进程/队列/实例，**不允许旁路功能拖垮主链路**；
- 线程池/连接池按下游隔离，一个下游变慢不占光全局连接。

### 2.3 故障预案（写下来，演练它）
每个关键依赖一行：故障场景 → 表现 → 自动缓解 → 人工处置 → 负责人。

| 依赖 | 故障表现 | 预案 |
|------|----------|------|
| 缓存全挂 | DB 压力激增、响应变慢 | 库端限流 + 应用侧降级返回缓存快照/兜底值（见 04 §6） |
| 下游 API 超时 | 接口变慢拖垮线程池 | 熔断打开 + 降级开关 |
| DB 主库故障 | 写入全部失败 | 切换从库（自动/手动手册化）、期间只读降级 |
| MQ 不可用 | 异步动作丢失 | 降级为同步关键部分 + 本地暂存重投 |

## 3. 数据可靠性

- **备份三原则**：自动化（定时任务，不靠人手）、异地（备份与主库不同可用区/机器）、可恢复（**恢复演练每月一次，没演练过等于没有备份**）。
- 数据库：每日全量 + 增量/binlog，保留 ≥7 天 + 月度长期保留；删除类操作用软删除或延迟删除窗口（防手滑）。
- 迁移脚本必须可回滚（见 07 §6），大变更先在影子库/从库验证。

## 4. 性能规范

### 4.1 性能预算
接口在设计期就定预算，写进设计文档：如 `列表接口 P95 ≤ 300ms，其中 DB ≤ 50ms、外部调用 ≤ 200ms`。超预算就是 bug，走缺陷流程而不是口头容忍。

### 4.2 优化铁律
1. **先测量后优化**：没有 profiler/慢日志证据不动手（ premature optimization 是万恶之源）；
2. 只优化 top 热点：抓 P95/P99 长尾，不管平均值的"感觉慢"；
3. 优化顺序：**架构（缓存/异步/批量）> 索引与 SQL > 代码算法 > 参数调优**。90% 的性能问题在前两级；
4. 每次优化有前后对比数据（同压测条件），没提升就回滚代码。

### 4.3 常见性能模式（按见效排序）
| 模式 | 场景 | 要点 |
|------|------|------|
| 批量化 | N+1 查询、逐条 RPC | 批量接口 + 内存组装；一条 SQL 换 100 条 |
| 异步化 | 主链路外的动作 | 发消息/任务队列，接口只做核心事 |
| 缓存 | 热点读 | 见 04 §4 |
| 池化 | 连接/线程频繁创建 | 连接池参数进配置：池大小 ≈ 核数×2 起，压测定参 |
| 预计算 | 复杂聚合实时算 | 离线算好放结果表/物化视图 |
| 流式/分页 | 大结果集 | 强制分页、游标分页（见 06 §5） |

### 4.4 压测规范
- 上线前对核心接口压测：目标 = 峰值 ×2 持续 30 分钟无错误、无内存泄漏（对比压测前后 RSS）；
- 压测环境数据量级与生产同数量级（1 万行和 1 亿行的执行计划完全不同）；
- 生产压测需隔离标记（影子流量），并选业务低峰。

## 5. 发布与变更（可用性的一半靠变更管理）

- **灰度**：新版本先 1 实例/小流量 → 观察 ≥30 分钟 → 全量；关键指标（错误率、P95、业务转化）对比基线；
- **回滚第一**：任何发布前先回答"怎么回滚"。回滚必须是一个动作（切回旧镜像/旧配置），不能是"再改半小时代码"；
- **变更窗口**：大变更避开业务高峰；周五下午不发布核心系统（团队约定）；
- 变更记录进运维日志：谁、何时、改了什么、如何回滚（关联软考集 11 变更管理流程）。

## 6. 检查单

- [ ] 有明确 SLA 目标，架构冗余级别与目标匹配？
- [ ] 单点盘点完成，每个单点有自动或手册化的切换方案？
- [ ] 应用无状态，实例可水平扩展？
- [ ] 旁路任务与主链路隔离？
- [ ] 每个关键依赖有故障预案行（场景/表现/缓解/处置/负责人）？
- [ ] 备份自动化 + 异地 + 恢复演练 ≤1 个月前做过？
- [ ] 核心接口有性能预算与压测报告？
- [ ] 发布有灰度步骤和一键回滚方案？
