# 06 API 设计规范

> 关联文档：[07-数据库设计与SQL规范](/blog/%E7%9F%A5%E8%AF%86%E5%BA%93-%E8%BD%AF%E4%BB%B6%E7%A0%94%E5%8F%91%E8%A7%84%E8%8C%83-07-%E6%95%B0%E6%8D%AE%E5%BA%93%E8%AE%BE%E8%AE%A1%E4%B8%8ESQL%E8%A7%84%E8%8C%83)、[10-安全编码规范](/blog/%E7%9F%A5%E8%AF%86%E5%BA%93-%E8%BD%AF%E4%BB%B6%E7%A0%94%E5%8F%91%E8%A7%84%E8%8C%83-10-%E5%AE%89%E5%85%A8%E7%BC%96%E7%A0%81%E8%A7%84%E8%8C%83)
> 范围：HTTP REST API 为主；GraphQL/WebSocket 项目可裁剪，但命名、错误模型、版本化、幂等等原则通用。

## 1. 契约先行

API 是系统间合同：**先写契约（OpenAPI/接口文档）并评审，再写实现**。契约变更即走评审，不允许实现完再"补文档"。契约文件随代码入库、随 CI 校验（实现与契约 drift 检查）。

## 2. 资源建模与命名

- **URL 是名词，方法是动词**：`GET /orders`、`POST /orders`、`GET /orders/123`、`PATCH /orders/123`；
- 复数小写、连字符分隔：`/user-profiles`（不用驼峰、不下划线）；
- 嵌套 ≤2 层，深了就拍平用查询参数：`GET /orders/123/items` ✅；`GET /users/5/orders/123/items/7/comments` ❌ → `GET /comments?order_item_id=7`；
- 动作类端点（无法映射 CRUD 的）：用动词子资源：`POST /orders/123/cancel`、`POST /payments/456/refund`；
- 禁止 URL 里出现动词混合资源（`/getOrderList` ❌）。

## 3. HTTP 方法与状态码

| 方法 | 语义 | 幂等 | 常用码 |
|------|------|------|--------|
| GET | 读，**无副作用** | 是 | 200 / 404 |
| POST | 创建 / 非幂等动作 | 否 | 201（返回资源+Location）/ 200 / 422 |
| PUT | 全量替换 | 是 | 200 / 204 |
| PATCH | 部分更新 | 视实现 | 200 / 204 |
| DELETE | 删除 | 是 | 204 / 404 |

硬规则：
- 2xx=成功、4xx=**客户端错**（参数错、无权限、不存在）、5xx=服务端错。客户端不能拿 200 包错误码 body（历史遗留除外，新接口禁止）；
- 认证失败 401，权限不足 403，不许混淆；
- 5xx 响应体不带堆栈等内部信息（见 10 §7）。

## 4. 请求与响应结构

统一响应包络（团队内二选一并全局一致）：

```jsonc
// 方式 A：直接返回资源（REST 原教旨），错误走统一错误结构
// 方式 B：包络式
{ "code": 0, "message": "ok", "data": { ... } }        // 成功
{ "code": 40102, "message": "token 已过期", "data": null } // 失败
```

规则：
- 错误码分**段管理**：如 4 位数，前两位=模块（40=认证），后两位=具体原因；维护错误码注册表，禁止随手编；
- 字段命名：JSON 用 `snake_case` 或 `camelCase`，全局唯一，由序列化层统一转换；
- 时间一律 **ISO 8601 UTC**（`2026-09-04T12:00:00Z`），时区转换交给客户端；
- 金额用字符串/整数最小单位（分），**禁止浮点**；
- ID 对外用不连续的标识（UUID/雪花转字符串），防枚举遍历。

## 5. 列表接口：分页、过滤、排序

```
GET /orders?page=1&page_size=20            # 页码式（后台管理默认）
GET /orders?cursor=xxx&limit=20            # 游标式（数据量大/无限滚动默认）
GET /orders?status=paid&created_after=...  # 过滤：字段名=值
GET /orders?sort=-created_at,total_amount  # 排序：- 前缀表示降序
```

- `page_size` 上限强制（如 100），防一次拖全表；
- 列表响应必须带总数或 `next_cursor`，客户端不猜；
- 游标分页用于大表与实时流（offset 深翻页性能塌方）。

## 6. 幂等与并发控制

- 所有 POST 写接口支持 `Idempotency-Key` 头（或业务侧唯一键），同 key 重放返回首次结果（见 04 §7）；
- 乐观锁控制并发更新：实体带 `version` 字段，`PATCH` 携带，不匹配返回 409 Conflict；
- 支付回调、webhook 默认会重发——消费方幂等是自己的责任。

## 7. 版本化与兼容性

- 版本放 URL：`/v1/orders`（简单直接）；header 版本仅在有强理由时用；
- **向后兼容铁律**：只加字段、只加端点，不改语义。禁止：删字段、改字段类型、改字段含义、把必填改选填的反向操作；
- 废弃流程：文档标记 `deprecated` + 响应头 `Sunset` 通告 → 保留 ≥2 个版本周期 → 监控旧版本流量归零后删除；
- 内部服务间接口同样守此规则（消费方可能没跟着发版）。

## 8. 安全基线（详见 10）

- 全站 HTTPS；认证用 Bearer Token（JWT/Opaque）；
- 接口级鉴权默认拒绝（deny by default），逐个显式放行；
- 限流按 API key/IP/用户维度（429 + `Retry-After`）；
- 敏感字段（手机号、身份证）在日志和响应中脱敏（见 10 §7）。

## 9. 文档

- OpenAPI 3.x 为唯一事实源；每个端点：功能一句话、参数表、成功/错误响应示例、幂等性说明、所需权限；
- 提供最小可运行示例（curl）；SDK/客户端生成自契约。

## 10. 检查单

- [ ] 契约先于实现，随代码入库？
- [ ] URL 名词复数、方法语义正确、嵌套 ≤2 层？
- [ ] 状态码语义正确，无 200 包错误？
- [ ] 错误码分段注册，客户端可据 code+message 处理？
- [ ] 时间 UTC ISO 8601、金额非浮点、ID 防枚举？
- [ ] 列表有分页上限，大表用游标？
- [ ] 写接口幂等，并发更新有版本控制/冲突处理？
- [ ] 变更向后兼容，废弃有 Sunset 流程？
- [ ] 每个端点文档含示例与权限说明？
