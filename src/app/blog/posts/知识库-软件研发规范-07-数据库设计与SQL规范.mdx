# 07 数据库设计与 SQL 规范

> 关联文档：[04-分布式系统设计规范](/blog/%E7%9F%A5%E8%AF%86%E5%BA%93-%E8%BD%AF%E4%BB%B6%E7%A0%94%E5%8F%91%E8%A7%84%E8%8C%83-04-%E5%88%86%E5%B8%83%E5%BC%8F%E7%B3%BB%E7%BB%9F%E8%AE%BE%E8%AE%A1%E8%A7%84%E8%8C%83) §8（规模演进）、[10-安全编码规范](/blog/%E7%9F%A5%E8%AF%86%E5%BA%93-%E8%BD%AF%E4%BB%B6%E7%A0%94%E5%8F%91%E8%A7%84%E8%8C%83-10-%E5%AE%89%E5%85%A8%E7%BC%96%E7%A0%81%E8%A7%84%E8%8C%83)
> 基准：关系型数据库（PostgreSQL/MySQL）。其他存储（Redis/Mongo/ES）另按各自最佳实践。

## 1. 建模流程

1. 从业务用例出发列实体与关系（关联软考集 02 需求分析），先画 ER 图再写 DDL；
2. 每个表回答四问：主键是什么？唯一约束有哪些？谁在写（频率）？最常见的 3 个查询是什么？
3. **按查询设计索引，按写入设计约束**——表的形态取决于它怎么被查，不取决于 JSON 长什么样。

## 2. 命名规范

| 对象 | 规则 | 示例 |
|------|------|------|
| 表 | 小写复数/单数（团队二选一）+ snake_case | `user_orders` |
| 字段 | snake_case，布尔带 `is_/has_` 前缀 | `is_paid`、`total_amount` |
| 主键 | 统一 `id`（业务键另加唯一索引，不用业务键当主键） | `id BIGINT` |
| 外键字段 | `<关联表单数>_id` | `user_id` |
| 索引 | `idx_<表>_<字段...>`，唯一 `uk_<表>_<字段>` | `idx_orders_user_id` |
| 时间 | `created_at` / `updated_at`，UTC | — |

## 3. 字段设计规则

- **NOT NULL 默认**，确实可为空才允许 NULL（NULL 参与比较/索引的坑远多于便利）；字符串默认 `''`，数字默认 0；
- 类型够用即可：金额 `DECIMAL`/整数分，**禁止 FLOAT/DOUBLE 存钱**；状态用 SMALLINT + 代码内枚举（附注释/字典表）；手机号 VARCHAR(20)（要容纳 +86）；
- 每表标配：`id`、`created_at`、`updated_at`；软删除加 `deleted_at`（配合所有查询默认过滤，ORM 层统一处理）；
- 大字段（长文本/JSONB）拆扩展表，主表保持窄（影响缓存行数与回表效率）；
- 枚举值、字典值必须有出处：代码枚举类或字典表二选一，**禁止魔法数字散落 SQL**。

## 4. 范式与反范式

- 默认 **3NF**：每个事实存一处；
- 允许的受控反范式（写 ADR 说明）：高频读的冗余字段（订单冗余用户昵称快照）、汇总表（计数、日结金额）。冗余字段必须写明"权威来源+同步机制"，无同步机制的冗余是数据腐化的起点。

## 5. 索引规范

- 主键索引之外，索引服务于具体查询：为 WHERE 高频条件、JOIN 键、ORDER BY 组合建索引；
- 联合索引遵循**最左前缀**：`(user_id, status, created_at)` 支持 `user_id=?`、`user_id=? AND status=?`，不支持跳过 user_id；
- 区分度低的列（性别、状态）单独建索引无意义，放联合索引尾部；
- 单表索引 ≤5 个（写多表 ≤3）：每个索引都是写放大；
- 上线前用 `EXPLAIN` 验证核心查询走索引，禁止隐式类型转换（字符串列传数字不走索引）、禁止对索引列套函数（改用函数索引或改写）。

## 6. SQL 编写与迁移

- 应用代码**一律参数化查询**，字符串拼接 SQL 直接打回（安全见 10 §3）；
- 禁止 `SELECT *`：显式列名（防表结构变更污染、减 IO）；`UPDATE/DELETE` 必带 WHERE，ORM 层开启全表更新拦截；
- 大批量操作分批（每批 500-5000 行），避免长事务锁表；
- **迁移（migration）管理**：结构变更全部走版本化迁移脚本（Alembic/Flyway/golang-migrate 等），禁止手工改库；
  - 每个迁移可回滚（down 脚本）；加列默认值用"加可空列→回填→加默认"三步，禁止直接 `ALTER ADD NOT NULL DEFAULT` 大表（长锁）；
  - 改列类型/删列走 **expand → migrate → contract** 三段式，先双写兼容再清理，配合 06 §7 的向后兼容铁律。

## 7. 事务规范

- 事务尽量短：事务内禁止 RPC 调用、禁止发消息（要发则用 04 §3 的 Outbox 模式）、禁止等待用户输入；
- 隔离级别默认读已提交（RC）；用到串行化/可重复读需评审（死锁与幻读处理）；
- 并发更新统一乐观锁（version 字段）或 `UPDATE ... WHERE status=旧值` 状态机，禁止"先查再改"两步无保护写；
- 死锁处理：固定加锁顺序（按表名字典序）、捕获死锁异常重试一次。

## 8. ORM 使用边界

- ORM 用于 CRUD 与简单查询；**复杂查询（多表 join、窗口函数、报表）写 SQL**（或 QueryBuilder），放 repo 层并配集成测试；
- 禁止在业务代码里手写裸 SQL 字符串绕过 repo 层；
- ORM 的懒加载陷阱：列表页循环访问关联对象=N+1，必须用预加载（`select_related`/`joinedload` 等），CR 时 N+1 是必查项。

## 9. 访问与权限

- 应用账号最小权限：业务库账号不给 DDL、不给 DROP；手工运维用独立账号并留痕；
- 生产数据查询走审批/跳板，导出脱敏（见 10 §7）；测试环境禁止直接拷贝生产敏感数据，需要则脱敏后导入。

## 10. 检查单

- [ ] ER 图先行，每表能答"主键/唯一约束/读写频率/三个高频查询"？
- [ ] 命名、时间、软删除字段全局统一？
- [ ] 金额非浮点、NOT NULL 默认、枚举有字典？
- [ ] 核心查询 EXPLAIN 验证过，联合索引最左前缀设计？
- [ ] SQL 全参数化、无 SELECT *、UPDATE/DELETE 带 WHERE？
- [ ] 迁移全部版本化且可回滚，大表变更走三段式？
- [ ] 事务内无 RPC/发消息，并发写有乐观锁/状态机？
- [ ] 复杂查询有集成测试，无 N+1？
