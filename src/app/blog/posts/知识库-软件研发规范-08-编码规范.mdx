# 08 编码规范

> 关联文档：[01-软件设计原则与设计模式](/blog/%E7%9F%A5%E8%AF%86%E5%BA%93-%E8%BD%AF%E4%BB%B6%E7%A0%94%E5%8F%91%E8%A7%84%E8%8C%83-01-%E8%BD%AF%E4%BB%B6%E8%AE%BE%E8%AE%A1%E5%8E%9F%E5%88%99%E4%B8%8E%E8%AE%BE%E8%AE%A1%E6%A8%A1%E5%BC%8F)、[12-代码评审规范](/blog/%E7%9F%A5%E8%AF%86%E5%BA%93-%E8%BD%AF%E4%BB%B6%E7%A0%94%E5%8F%91%E8%A7%84%E8%8C%83-12-%E4%BB%A3%E7%A0%81%E8%AF%84%E5%AE%A1%E8%A7%84%E8%8C%83)
> 定位：语言无关的整洁代码规则 + 各语言官方规范索引。语言细节以官方规范为准，本文管共性。

## 1. 语言规范索引（项目 CI 必须配齐自动检查）

| 语言 | 风格规范 | 工具链 |
|------|----------|--------|
| Python | PEP 8 + 项目约定（line length、import 分组） | ruff（lint+format）、mypy/pyright |
| TypeScript/JS | Airbnb/Standard 或 ESLint 官方推荐 | eslint + prettier、tsc strict |
| Go | gofmt 即法律 | go vet、golangci-lint |
| Java | Google Java Style / 阿里巴巴 Java 开发手册 | Checkstyle、SpotBugs、ErrorProne |
| SQL | 本集 07 | sqlfluff、squawk（迁移检查） |

规则：格式化交给工具（保存即格式化、CI 卡 lint），**评审中不讨论格式**；每个新项目初始化第一天就配好 lint+format+CI，晚配一天就多一天欠账。

## 2. 命名

- **名实相符是第一规范**：看名字不看实现能猜对行为 80%，就是好命名；
- 函数用动词短语：`calculate_total`、`is_expired`、`send_verification_code`；布尔用 is/has/can/should 前缀；类用名词；
- 禁止无意义名：`data`、`info`、`tmp`、`handle`、`do_process`；禁止拼音英文混用和 1-2 字母名（循环变量 i/j/k 除外）;
- 单位进名字：`timeout_ms`、`size_bytes`、`amount_cents`——单位错误是隐性 bug 之王；
- 常量大写蛇形 + 集中管理；魔法数字一律提取并命名（`if retries > 3` → `MAX_RETRIES`）。

## 3. 函数

- 一个函数做一件事、一个抽象层级（见 01 §1）；能用一句话概括职责；
- **长度软约束**：超过 ~50 行就必须审视能否拆分（不是硬切，是按职责切）；
- 参数 ≤3 个；更多就收拢为参数对象；布尔开关参数（`process(data, True)` 可读性为零）改拆两个函数或枚举；
- **卫语句早返回**，消灭嵌套：

```python
# 反例                            # 正例
def f(user):                      def f(user):
    if user:                          if not user:
        if user.active:                   return None
            if user.age >= 18:        if not user.active:
                ...                       return None
                                          if user.age < 18:
                                              return None
                                          ...
```

- 无副作用原则：`get_/is_/has_` 开头的函数禁止修改状态或发 IO；有 IO 的函数命名里体现（`fetch_xxx_from_db`）；
- 返回值统一：要么全返回对象/None，要么全抛异常，不混用（"失败返回 null"和"失败抛异常"并存是调用方噩梦）。

## 4. 注释与文档

- **好代码自解释，注释解释"为什么"而不是"是什么"**：
  - 该写：业务背景（为什么阈值是 3）、坑位提醒（下游接口超时率高）、取舍（为什么不用更简单的方案）、TODO 带上下文（`TODO(zhang): 等 v2 API 上线后移除，#123`）；
  - 不该写：复述代码的注释（`# i 加 1`）、过时注释（改代码不改注释 = 负资产，要么同步要么删）、被注释掉的代码块；
- 公共函数/模块写 docstring：一句话职责 + 参数/返回/异常 + 一个示例（关键处）；
- git 提交历史承担"改了什么"，代码注释承担"为什么这样"，两者不互相顶替。

## 5. 错误处理

- **禁止吞异常**：`except: pass` / 空 catch 是 bug 温床；确实要忽略必须注释理由并收窄范围（`except FileNotFoundError`）；
- 异常带上下文再抛：捕获底层异常后包一层业务语义（`raise OrderError(...) from e`），顶层统一兜底（全局 error handler 返回 5xx + 记日志）；
- 错误分类：**预期内错误**（用户输入错、资源不存在）用返回值/业务异常走正常分支；**预期外错误**（bug、基础设施挂）fail-fast 抛出去，不要试图在业务层"修复"；
- 对外错误信息不泄露内部细节（路径、SQL、堆栈），对内日志记全上下文（见 13 §2、10 §7）；
- 资源释放用语言机制（`with`/`defer`/try-with-resources），不手工 close。

## 6. 并发与异步

- 共享可变状态是万恶之源：能不可变就不变，能线程封闭就不共享；共享必加锁，且锁顺序固定（防死锁，见 07 §7）；
- 默认用高层并发原语（队列、线程池、asyncio 任务、Future），不裸起线程；池大小进配置；
- async 代码里禁止阻塞调用（同步 sleep/同步 IO），超时全覆盖（见 04 §6）；
- 后台任务必须可观测：启动/结束/失败有日志，失败有重试与告警。

## 7. 日志（编码侧约定，规范详见 13）

- 关键路径打点：入口（参数摘要）、外部调用前后（耗时）、状态变更、异常（含上下文）；
- 用结构化日志 + 正确级别：DEBUG 开发期、INFO 关键业务动作、WARN 可自愈异常、ERROR 需要人看的异常；
- 禁止 print 调试语句入库；禁止在循环里打 INFO（刷屏掩盖真日志）。

## 8. 代码坏味道速查（CR 高频打回项）

| 坏味道 | 信号 | 处方 |
|--------|------|------|
| 超长函数/类 | >100 行函数、一个类多职责 | 按 01 §2 SRP 拆 |
| 深嵌套 | 缩进 ≥4 层 | 卫语句 + 提取函数 |
| 发散/霰弹式修改 | 一个需求改 10 个文件 / 一个类改动引发处处改 | 收敛职责边界 |
| 依恋情结 | 函数大量访问别的模块的数据 | 函数搬到数据所在模块 |
| 数据泥团/基本类型偏执 | 一组字段总是成对出现 | 收拢为对象 |
| 重复代码 | 复制粘贴（含"相似但不完全一样"） | Rule of Three 后抽象 |
| 夸夸其谈通用性 | 没用上的配置项、泛型、钩子 | 删（YAGNI） |

## 9. 提交前自查（开发者版）

- [ ] 新代码有测试？（见 09）本地测试全绿？
- [ ] lint/format 过，无调试残留（print、注释代码、假数据）？
- [ ] 命名见名知义，无魔法数字？
- [ ] 异常处理齐：无吞异常、有上下文、资源用 with/defer 释放？
- [ ] 外部调用有超时？新配置有默认值并登记？
- [ ] 涉及 SQL 的：参数化、无 SELECT *、索引考虑了？
