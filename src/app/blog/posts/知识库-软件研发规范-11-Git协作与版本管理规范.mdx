# 11 Git 协作与版本管理规范

## 1. 分支模型（按团队规模裁剪）

### 默认：轻量 GitHub Flow（小团队/持续发布）
```
main（受保护，常绿可发布）
 └── feature/xxx ── PR ── 评审+CI 绿 ── squash 合并 ── 删分支
```

### 需要多环境版本维护时：Git Flow 简化版
- `main`：生产，只接受 release/hotfix 合入，打 tag；
- `develop`：集成主线；`feature/*` 从 develop 拉出；`release/*` 发布准备；`hotfix/*` 从 main 拉出并双向回灌。

裁剪规则：**能 GitHub Flow 就不 Git Flow**；分支存在的前提是"有明确的合入时间表"，没有的分支两周内要么合并要么删除（僵尸分支清理）。

分支命名：`feature/<issue号>-<短描述>`、`fix/`、`hotfix/`、`refactor/`、`docs/`，全小写连字符。

## 2. 提交（Commit）规范：Conventional Commits

```
<type>(<scope>): <subject>

[optional body：动机与方案，说"为什么"]
[optional footer：BREAKING CHANGE: / Refs #123]
```

| type | 用途 |
|------|------|
| feat | 新功能 |
| fix | 修 bug |
| refactor | 重构（行为不变） |
| perf | 性能优化 |
| test | 补测试 |
| docs | 文档 |
| chore | 构建/依赖/配置 |
| ci | CI 配置 |

规则：
- subject 祈使句、≤50 字、不加句号：`fix(orders): 幂等键缺失导致重复扣款`；
- **一次提交一个完整意图**：修复+重构+换格式混在一条，回滚和定位都废掉——用 `git add -p` 拆分；
- 本地可以碎提交，合并前 squash 成一条干净的（PR 标题自动成为 commit message）；
- main 禁止 force push；rebase 只在自己的 feature 分支上做。

## 3. PR/MR 流程

- **小步快跑**：PR ≤400 行 diff 为佳（评审质量随体积指数下降），>800 行必须说明理由或拆分；
- PR 描述模板：做什么/为什么、改动范围、怎么测的（测试证据截图/命令）、风险与回滚方式、勾选自查单（附录 A）；
- 开 PR 即草稿模式自审一遍 diff（自己先发现自己都会打回的项）；
- 合并条件（分支保护强制）：≥1 个批准评审 + CI 全绿 + 无未解决对话；禁止自己批准自己的 PR、禁止"评审中直接 push 覆盖评审意见未读"；
- 合并方式：团队统一 squash（主干历史 = 每条 PR 一行）或 merge commit，禁止混用。

## 4. 版本号与发布

- 对外发布的软件/库用**语义化版本** `MAJOR.MINOR.PATCH`：不兼容改 MAJOR，向后兼容新增 MINOR，修 bug PATCH；0.x 阶段接口不稳定，破坏性变更升 MINOR 并在 changelog 声明；
- 内部服务部署不需要 tag 版本号时，至少：镜像 tag = git short hash（可追溯到代码），禁止 `latest` 上生产；
- CHANGELOG.md 自动生成（从 Conventional Commits），人工润色面向用户的条目。

## 5. 仓库卫生

- `.gitignore` 第一天配齐：密钥/环境文件、虚拟环境、构建产物、`.DS_Store`、IDE 目录；
- 大文件（模型、数据集、音视频）不进 git——用 Git LFS 或对象存储+指针；
- 敏感信息一旦提交过，视为已泄露：轮换密钥，然后才谈清理历史（filter-repo）；
- 仓库标配文件：`README.md`（是什么/怎么跑/怎么测）、`CHANGELOG.md`、CI 配置、`.editorconfig`、契约/迁移目录。

## 6. 常用救援操作（知道有这回事，别慌）

| 场景 | 动作 |
|------|------|
| 提交错内容还没 push | `git commit --amend` 或 `git reset --soft HEAD~1` |
| 已 push 想撤销某次合并 | `git revert <sha>`（生成反向提交，公共分支禁止 reset+force） |
| 开发到一半要切分支修线上 | `git stash` / WIP commit |
| 找一个"消失"的提交 | `git reflog` |
| 二进制/锁文件冲突 | 以一边为准重生成（lockfile 删掉重装），不手拼 |

## 7. 检查单

- [ ] 分支模型明确，main 受保护，僵尸分支定期清理？
- [ ] 提交符合 Conventional Commits，一次提交一个意图？
- [ ] PR ≤400 行，描述含测试证据与回滚方式，自查后才请人评？
- [ ] 合并有门槛：评审批准 + CI 绿？
- [ ] 版本号语义化/镜像可溯源，CHANGELOG 在维护？
- [ ] .gitignore 齐全，仓库无密钥无大文件？
