# 12 代码评审规范

> 关联文档：[08-编码规范](/blog/%E7%9F%A5%E8%AF%86%E5%BA%93-%E8%BD%AF%E4%BB%B6%E7%A0%94%E5%8F%91%E8%A7%84%E8%8C%83-08-%E7%BC%96%E7%A0%81%E8%A7%84%E8%8C%83)、[11-Git协作与版本管理规范](/blog/%E7%9F%A5%E8%AF%86%E5%BA%93-%E8%BD%AF%E4%BB%B6%E7%A0%94%E5%8F%91%E8%A7%84%E8%8C%83-11-Git%E5%8D%8F%E4%BD%9C%E4%B8%8E%E7%89%88%E6%9C%AC%E7%AE%A1%E7%90%86%E8%A7%84%E8%8C%83) §3
> 目标：CR 不是找茬，是**三件事**——守住质量底线、传播系统知识（至少两个人懂每段代码）、保持风格一致。

## 1. 评审优先级（先看什么）

1. **正确性**：逻辑对吗？边界齐吗？并发/事务安全吗？（必须逐行）
2. **安全性**：越权/注入/密钥/敏感信息（对照 10 检查单）
3. **可维护性**：命名、职责、复杂度、测试质量
4. **一致性**：与项目既有风格/模式一致吗
5. 格式问题：**交给 lint 工具，评审里不提**

## 2. 评审操作规范

- 时限：**24 小时内首次响应**（哪怕只是"今天看"）；紧急修复走快速通道（指定评审人）；
- 评审人：作者指定 1 名熟悉该模块的 + CI 全绿；核心模块（支付/鉴权/数据迁移）强制 2 人；
- 逐条评论绑定具体行；按 4 级标注让作者好排期：
  - `[blocker]` 必须改才能合并（bug、安全、数据丢失风险）
  - `[should]` 强烈建议（可维护性问题），作者不改需回复理由
  - `[nit]` 小瑕疵（命名、措辞），作者自行定夺
  - `[question]` 不确定，是提问不是要求
- 大 PR（>400 行）评审人有权直接打回要求拆分，不硬看。

## 3. 评论措辞（对人宽松，对代码严格）

| ❌ 刺激防御 | ✅ 对事不对人 |
|------------|--------------|
| 这写得什么玩意 | 这个函数现在同时做解析和校验，拆开会不会更清楚？ |
| 你为什么不用 X | 这里考虑过 X 吗？当时是出于什么取舍选了现在的方案？ |
| 这有明显问题 | 我没看懂这段的意图，`[question]` 能加个说明或测试吗 |
| 照我说的改 | 一个可选思路：… 供参考 |

规则：不确定就问，不要默认作者错了；**批准 ≠ 每一行都喜欢**，blocker 清零即可批准；意见分歧两轮没收敛 → 拉第三个人/团队约定裁定，不在 PR 里辩论超过三轮。

## 4. 作者义务

- 自审 diff 后才请评审（自己能发现自己 60% 的问题）；
- 每条评论必须回应：改了（说明怎么改的）或解释为什么不改——**已读不回是最伤协作的**；
- 改动超出原 PR 意图时拆新 PR；评论解决一条关一条，合并时无悬置对话；
- 合并后删分支，观察 CI/监控一个周期。

## 5. 评审反模式

| 反模式 | 危害 | 处方 |
|--------|------|------|
| "LGTM" 秒批 | CR 沦为形式，责任稀释 | 没时间就明说并转给别人，不假批 |
| 只看自己关心的文件 | 覆盖有黑洞 | 至少扫全量 diff |
| 用 CR 推销个人偏好 | 团队标准碎片化 | 偏好先写成团队规范再引用 |
| 巨型 PR 扔群里等人捡 | 拖延 + 烂评审 | 拆分 + 指定评审人 |
| 评审意见石沉大海 | 作者重复犯错 | 定期（周会）过未决 CR |
| 只在 CR 才发现设计问题 | 返工成本最大化 | 复杂设计先行前评审（设计文档/ADR），CR 只管实现 |

## 6. 评审检查单（评审人视角）

**正确性**
- [ ] 逻辑覆盖边界：空、零、极大、并发、重复请求？
- [ ] 错误路径处理了：外部调用失败、超时、部分失败？
- [ ] 数据一致：事务边界对？幂等？并发写有保护？

**安全**
- [ ] 新端点有鉴权与属主校验？输入有校验？无密钥/敏感信息入库或入日志？

**可维护**
- [ ] 测试齐且测的是行为不是实现？增量覆盖率达标？
- [ ] 命名/职责清晰，没有明显复制粘贴？
- [ ] 有副作用的地方（迁移、配置变更、依赖升级）说明了吗？

**一致性**
- [ ] 与项目既有模式一致（不是"更好"就擅自引入新范式）？
- [ ] 文档/契约/changelog 同步更新了？
