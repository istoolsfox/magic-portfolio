# 13 可观测性与运维规范

> 关联文档：[05-高可用与性能设计规范](/blog/%E7%9F%A5%E8%AF%86%E5%BA%93-%E8%BD%AF%E4%BB%B6%E7%A0%94%E5%8F%91%E8%A7%84%E8%8C%83-05-%E9%AB%98%E5%8F%AF%E7%94%A8%E4%B8%8E%E6%80%A7%E8%83%BD%E8%AE%BE%E8%AE%A1%E8%A7%84%E8%8C%83)、[04-分布式系统设计规范](/blog/%E7%9F%A5%E8%AF%86%E5%BA%93-%E8%BD%AF%E4%BB%B6%E7%A0%94%E5%8F%91%E8%A7%84%E8%8C%83-04-%E5%88%86%E5%B8%83%E5%BC%8F%E7%B3%BB%E7%BB%9F%E8%AE%BE%E8%AE%A1%E8%A7%84%E8%8C%83) §6
> 关联软考集：[06-部署与交付规范](/blog/%E7%9F%A5%E8%AF%86%E5%BA%93-%E8%BD%AF%E8%80%83-%E8%BD%AF%E4%BB%B6%E8%AE%BE%E8%AE%A1%E8%A7%84%E8%8C%83-06-%E9%83%A8%E7%BD%B2%E4%B8%8E%E4%BA%A4%E4%BB%98%E8%A7%84%E8%8C%83)
> 立场：可观测性是功能需求，不是锦上添花——**没有指标的系统出事时你只能靠用户当监控**。

## 1. 三支柱与最小落地

| 支柱 | 回答什么问题 | 最小落地 |
|------|--------------|----------|
| 日志 Logs | 出了什么事？细节是什么 | 结构化日志 + 集中收集（哪怕先聚到文件轮转） |
| 指标 Metrics | 系统健康吗？趋势如何 | 四个黄金指标 + 基础资源指标 |
| 追踪 Traces | 一次请求慢在哪/错在哪 | 跨服务调用链（初期可只做入口+外部调用两跳） |

**四个黄金指标**（每个服务必配）：流量（QPS）、错误率、延迟（P95/P99）、饱和度（队列积压/连接池水位/CPU）。出问题时按"错误率↑→看日志→看 trace 定位"的链路走。

## 2. 日志规范

- 结构化（JSON 行），必备字段：`ts`、`level`、`service`、`trace_id`、`msg`；业务事件带实体 ID（order_id/user_id）；
- 级别纪律（呼应 08 §7）：
  - `ERROR`：需要人介入（外部依赖持续失败、数据不一致）——**ERROR 必须可行动**，收到告警却没有对应处置动作的 ERROR 降级为 WARN；
  - `WARN`：可自愈异常（重试成功、降级触发）；
  - `INFO`：关键业务动作（下单、支付回调、配置变更），带实体 ID；
  - `DEBUG`：诊断细节，生产默认关、可动态开。
- 每次 HTTP 请求一条访问日志：方法、路径、状态码、耗时、用户标识；
- **日志内容红线**（呼应 10 §7）：无密钥/token/密码/完整身份证；请求体先脱敏再记；
- 保留策略：ERROR/安全类 ≥90 天，常规 ≥14 天，超期自动清理；日志有轮转，**磁盘打满本身就是事故**。

## 3. 指标与告警

- 业务指标与技术指标同权：下单成功率、支付回调延迟这类业务指标往往比 CPU 先报警；
- 告警三要素：**有阈值、有持续时间、有处置动作（Runbook 链接）**。发出去没人知道干嘛的告警是噪音制造机；
- 分级路由：P1（主链路不可用）电话/强提醒，任何时间响应；P2（部分功能劣化）工作时间响应；P3（趋势异常）周报跟踪；
- 告警收敛：同根因的告警聚合；每周回顾——误报率 >50% 就调阈值，**告警疲劳是真实事故的放大器**。

## 4. 追踪与关联

- 入口生成 `trace_id`，贯穿：HTTP 头传递 → 日志字段 → MQ 消息体 → 下游调用；
- 外部调用（DB/第三方/MQ）打点起止与结果，慢调用（>预算）单独采样记录；
- 没有完整 APM 时，退而求其次：入口中间件记 `trace_id` + 各 adapter 手动打点，足够回答"慢在哪一跳"。

## 5. Runbook（运维手册）

每个服务一份 `RUNBOOK.md`，与告警互链，内容最小集：

```markdown
# 服务名 Runbook
## 服务概览：做什么、依赖什么、被谁依赖
## 关键指标与看板链接
## 常见告警处置
### ERROR 率突增
  症状 → 排查步骤（1. 看发布记录 2. 看 trace 3. 看依赖状态页）→ 缓解动作 → 升级路径（找谁）
### 延迟 P99 超标
### 队列积压
## 发布与回滚：怎么发、怎么回、前置条件
## 应急开关：降级开关列表、位置、效果（呼应 05 §2.3）
## 联系人与升级路径
```

规则：每次真实故障后回填 Runbook（故障演练价值最高的时刻）；值班交接看 Runbook 而不是看聊天记录。

## 6. 故障复盘（无指责原则）

- 触发线：P1 必复盘，P2 抽样；复盘在修复后 48h 内完成；
- 格式：时间线 → 影响面 → 根因（问到流程/设计层，不停在"手滑"）→ 为什么告警/预案没拦住 → 行动项（责任人+期限，自动化优先于"下次注意"）；
- 复盘产出进本集知识库迭代（规范是活的，事故是最好的规范来源）。

## 7. 发布检查单（上线前最后一道）

- [ ] 测试全绿、核心接口压测达标（05 §4.4）？
- [ ] 迁移脚本验证过且可回滚（07 §6）？灰度与回滚步骤写在发布单里？
- [ ] 新端点鉴权/限流在位，安全检查单（10）过完？
- [ ] 新指标/日志/告警已配置并试触发？
- [ ] 配置项有默认值，密钥走环境注入？
- [ ] 相关人知道发布窗口与观察指标？发布后观察 30 分钟再撤离？

## 8. 检查单

- [ ] 四个黄金指标齐，业务指标与技术指标同权？
- [ ] 日志结构化、带 trace_id、级别纪律执行、红线内容零出现？
- [ ] 每条告警有 Runbook 链接，误报率受控？
- [ ] trace_id 贯穿全链路？
- [ ] RUNBOOK.md 存在且与最近一次故障同步过？
- [ ] 复盘行动项闭环，规范有迭代？
