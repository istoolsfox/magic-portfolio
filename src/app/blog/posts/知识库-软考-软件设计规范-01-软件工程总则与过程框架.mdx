# 01 软件工程总则与过程框架

> 来源：《系统集成项目管理工程师教程（第3版）》第5章、第9章

## 1. 软件工程的由来与定义

### 1.1 软件危机
20世纪60年代中期，软件规模、复杂度急剧增长，出现"软件危机"：
- 软件开发进度难以预测；
- 软件开发成本难以控制；
- 软件功能难以满足用户期望；
- 软件质量无法保证；
- 软件难以维护；
- 软件缺少适当的文档资料。

### 1.2 软件工程定义
应用**计算机科学、数学及管理科学**等原理，以**工程化的原则和方法**解决软件问题，目的是**提高生产率、提高质量、降低成本**。

IEEE 定义：将系统的、规范的、可度量的工程化方法应用于**软件开发、运行和维护的全过程**及上述方法的研究。

### 1.3 软件工程的三大组成
| 组成 | 作用 |
|------|------|
| **方法** | 完成软件项目的技术手段，支持整个软件生命周期 |
| **工具** | 智力与体力的扩展与延伸，自动/半自动支持开发与管理、文档生成 |
| **过程** | 为获得软件产品，在工具支持下由工程师完成的一系列软件工程活动 |

管理人员在过程中要对**质量、进度、成本**进行评估、管理和控制（人员组织、计划跟踪与控制、成本估算、质量保证、配置管理）。

## 2. 软件开发方法

### 2.1 结构化方法（面向数据流）
- 自顶向下、逐层分解、逐步求精、模块化；
- 分为**概要设计（总体结构设计）**与**详细设计**两个阶段。

### 2.2 面向对象方法
- 以对象为中心，更接近现实世界；
- 核心思想：抽象、封装、可扩展性（继承+多态）。

### 2.3 其他工程化要求
- 需要完整文档，文档是开发过程的组成部分；
- 方法、工具、过程三者结合；
- 编码是设计的自然结果，程序质量主要取决于设计质量。

## 3. 软件生命周期与项目生命周期

### 3.1 概念区分
| 概念 | 定义 |
|------|------|
| 项目阶段 | 项目从开始到结束经历的一系列阶段，一组有逻辑关系的活动集合，以可交付成果完成为结束标志 |
| 项目管理过程组 | 为达成项目特定目标，对项目管理过程进行的**逻辑分组**（5组） |
| 生命周期类型 | 预测型、适应型（迭代/增量）、混合型 |

### 3.2 适应型（敏捷）生命周期要点
- 启动过程通常在每个迭代期开展；频繁回顾并重新确认项目章程；
- 先基于初始需求制定高层级计划，再逐步细化；
- 通过迭代进行工作指导与管理，演示成果并回顾审查；
- 用「未完项清单（Backlog）」跟踪进展与变更；
- 收尾对工作进行优先级排序，先完成最具业务价值的工作。

### 3.3 项目立项流程（软件开发前置）
```
项目建议与立项申请 → 项目可行性研究 → 项目评估与决策 → 立项批准
```
- 可行性研究：技术、经济、社会/法律、运行环境等维度；
- 项目评估与决策：评估可行性研究报告，形成决策结论。

## 4. 软件工程过程的活动划分（推荐开发流程）

| 阶段 | 主要活动 | 关键产出 |
|------|----------|----------|
| 需求 | 需求获取、分析、定义 | SRS、需求跟踪矩阵 |
| 设计 | 概要设计、详细设计 | 设计说明书、UML模型、数据库设计 |
| 实现 | 编码、配置管理 | 源代码、构建版本 |
| 测试 | 单元→集成→系统→验收 | 测试用例、测试报告、缺陷记录 |
| 部署交付 | 部署、验收、交付 | 发布版本、用户手册、验收报告 |
| 运维与收尾 | 运维支持、项目总结 | 运维移交、经验教训库 |

## 5. 软件开发项目的关键成功要素

1. 有明确、可度量的目标（以 SRS 和基准为准）；
2. 需求变更受控（变更管理）；
3. 配置管理贯穿全程（版本、基线）；
4. 质量内建（测试贯穿开发过程，不只是最后阶段）；
5. 文档规范齐全（按文档分级标准）；
6. 全过程监控（进度、成本、质量、风险）；
7. 干系人充分参与与沟通。

## 6. 裁剪原则（规范不是教条）

根据项目规模、复杂度、行业、合同要求，对流程、文档、过程组进行裁剪：
- 小项目：简化变更流程、降低文档级别；
- 高风险/大型项目：加强监控、评审与配置控制；
- 敏捷项目：用 Backlog 取代繁重需求文档，仍保留设计、测试、配置管理核心动作。
