# 03 软件设计规范

> 来源：《系统集成项目管理工程师教程（第3版）》第5章

## 1. 软件设计的目标与定位

- 根据软件分析的结果完成软件构建：**绘制软件蓝图**，权衡技术方案，分配资源，形成设计方案与模型；
- 需求阶段解决"做什么"，设计阶段解决"怎么做"；
- 合理设计既保证质量，也提高开发效率；
- 设计方法分为：**结构化设计（SD）**与**面向对象设计（OOD）**。

## 2. 结构化设计（SD）

面向数据流的方法，以 SRS、DFD、数据字典为基础，自顶向下、逐层分解、逐步求精、模块化。

### 2.1 两个阶段
| 阶段 | 任务 | 产出 |
|------|------|------|
| 概要设计（总体结构设计） | 确定系统结构、功能需求模块划分、模块功能/接口/调用关系 | 模块结构图（系统结构图 SC） |
| 详细设计 | 为每个模块设计实现细节（I/O、处理流程、数据存储、UI、安全可靠性） | 详细设计文档 |

### 2.2 模块化核心概念
模块是组成系统的基本单位，具有**功能（做什么）、逻辑（怎么做）、状态（使用环境与条件）**三个属性。

- **信息隐藏与抽象**：封装实现细节为"黑盒"，模块间只通过接口交互，简化接口、便于理解维护；
- **模块外部特性**：模块名、参数表、对系统的影响；**内部特性**：代码与内部数据。外部环境只需了解外部特性；设计时应先定外部特性，再定内部特性。

### 2.3 耦合（模块间联系程度）
原则：**降低耦合**。耦合类型从低到高：

| 耦合类型 | 描述 |
|----------|------|
| 非直接耦合 | 两模块无直接关系，经上级模块控制与调用 |
| 数据耦合 | 借助参数表传递简单数据 |
| 标记耦合 | 通过参数表传递记录等复杂信息（数据结构） |
| 控制耦合 | 传递的信息中包含控制模块内部逻辑的信息 |
| 通信耦合 | 一组模块共用一组输入信息或整合输出 |
| 公共耦合 | 多个模块访问同一公共数据环境（全局数据结构、共享通信区等） |
| 内容耦合 | 一个模块直接访问另一个模块内部数据、非正常入口、代码重叠、多入口 |

### 2.4 内聚（模块内部联系紧密程度）
原则：**提高内聚**。内聚类型从高到低：

| 内聚类型 | 描述 |
|----------|------|
| 功能内聚 | 完成单一功能，各部分协同、缺一不可 |
| 顺序内聚 | 处理元素相关且必须顺序执行 |
| 通信内聚 | 所有处理元素集中在一个数据结构区域上 |
| 过程内聚 | 处理元素相关且必须按特定次序执行 |
| 时间内聚 | 任务必须在同一时间间隔内执行 |
| 逻辑内聚 | 完成逻辑上相关的一组任务 |
| 偶然内聚 | 完成一组无关系或松散关系的任务 |

> 目标：**高内聚、低耦合**。内聚越高通常耦合越低（非绝对），模块可单独开发维护、可理解性与维护性更强。

### 2.5 系统结构图（SC）
- 概要设计工具，反映系统功能实现与模块间联系通信、层次结构；
- 从 DFD 按规则导出初始 SC。

### 2.6 详细设计
- 目标：模块算法逻辑正确；算法描述简明易懂；
- **详细设计须遵循概要设计**；详细设计更改不得影响概要设计；如需改概要设计须经项目经理同意；
- 设计步骤：
  1. 分析确定 I/O 数据逻辑结构；
  2. 找出 I/O 数据结构中有对应关系的数据单元；
  3. 按规则由 I/O 数据结构导出程序结构；
  4. 列出基本操作与条件，分配到程序结构图适当位置；
  5. 用伪码写出程序。

### 2.7 详细设计表示工具
| 类别 | 工具 | 说明 |
|------|------|------|
| 图形工具 | 业务流程图、程序流程图、NS图（盒图）、PAD图 | 描述过程细节；NS/PAD 强制结构化 |
| 表格工具 | 判定表 | 列出可能操作与相应条件 |
| 语言工具 | 伪码、PDL（程序设计语言） | 外层语法确定（控制结构），内层语法不确定（具体操作）；可作注释插入源码、可由 PDL 自动生成代码 |

## 3. 面向对象设计（OOD）

OOD 是 OOA 的延续，基本思想：抽象、封装、可扩展性（继承+多态）。核心任务是**类和对象的设计**（属性、方法、类间关系），目标是同时提高**可维护性与可复用性**。

### 3.1 常用 OOD 原则
| 原则 | 要点 |
|------|------|
| 单一职责 | 一个类有且仅有一个引起它变化的原因，否则应拆分 |
| 开闭原则 | 对扩展开放，对修改封闭 |
| 里氏替换 | 子类可替换父类，可扩展功能但不可改变原有功能 |
| 依赖倒置 | 依赖抽象而非具体实现；针对接口编程 |
| 接口隔离 | 多个专门接口优于单一总接口 |
| 组合复用 | 尽量使用组合而非继承达到复用 |
| 迪米特（最少知识） | 对象应对其他对象有尽可能少的了解，降低耦合 |

### 3.2 类的三种类型
| 类型 | 特征 | 说明 |
|------|------|------|
| 实体类 | 映射需求中的每个实体，保存需持久存储的信息；通常为名词、永久性；一定有属性，不一定有操作 | 从 SRS 中与数据库表对应的名词找起 |
| 控制类 | 控制用例工作的类，由动宾短语转化；封装用例特有行为；通常无属性、一定有方法；用例执行完毕即消亡 | 如"身份验证器" |
| 边界类 | 封装用例内、外流动的信息/数据流，位于系统与外界交接处（窗体、报表、硬件接口、其他系统接口）；可分隔外部变更，既有属性也有方法 | 每个参与者与用例交互至少一个边界类 |

## 4. 统一建模语言（UML）

### 4.1 UML 结构
- **构造块**：事物（thing）、关系（relationship）、图（diagram）；
- **规则**：命名、范围、可见性、完整性、执行；
- **公共机制**：规格说明、修饰、公共分类、扩展机制。

### 4.2 事物（建模元素）
| 类型 | 内容 |
|------|------|
| 结构事物 | 类、接口、协作、用例、活动类、构件、节点（7种，静态） |
| 行为事物 | 交互、状态机（动态） |
| 分组事物 | 包（纯概念，仅开发阶段存在） |
| 注释事物 | 模型解释部分 |

### 4.3 关系（4种）
依赖、关联、泛化、实现。

### 4.4 UML 2.0 十四种图
- 静态：类图、对象图、构件图、组合结构图、用例图、制品图、包图、部署图；
- 动态：顺序图、通信图、定时图、状态图、活动图、交互概览图。

| 常用图 | 用途 |
|--------|------|
| 类图 | 静态设计视图（最常见） |
| 用例图 | 用户与系统交互的最简表示，行为组织与建模 |
| 顺序图 | 强调消息时间次序 |
| 状态图 | 实体基于事件反应的动态行为 |
| 活动图 | 控制流与数据流，功能/业务流程建模 |
| 部署图 | 运行时处理节点与构件配置 |

### 4.5 UML 五大视图
逻辑视图、进程视图、实现视图、部署视图、用例视图。

## 5. 设计模式

- 定义：前人经验的总结，复用成功的软件设计，降低分析设计实现难度，提高可复用性与灵活性；
- 要素：模式名称、问题、目的、解决方案、效果、实例代码、相关设计模式；
- 按处理范围：类模式（静态，继承）、对象模式（动态，运行时刻关系）；
- 按目的与用途：
  - **创建型**：工厂方法、抽象工厂、原型、单例、建造者；
  - **结构型**：适配器、桥接、组合、装饰、外观、享元、代理；
  - **行为型**：职责链、命令、解释器、迭代器、中介者、备忘录、观察者、状态、策略、模板方法、访问者。

## 6. 软件设计检查单

- [ ] 模块划分是否满足"高内聚、低耦合"？
- [ ] 是否遵循信息隐藏（黑盒设计）？
- [ ] OO 设计是否落实 7 原则？
- [ ] 是否区分实体/控制/边界类？
- [ ] 详细设计是否遵循概要设计、更改受控？
- [ ] 是否用 UML 图表达静态结构与动态行为？
- [ ] 是否复用合适的设计模式？
- [ ] 设计文档是否纳入配置管理？
