# 04 编码与配置管理规范

> 来源：《系统集成项目管理工程师教程（第3版）》第5章

## 1. 软件编码

编码是把软件设计结果翻译成计算机可理解的形式（用某种程序设计语言书写的程序）。编码是设计的自然结果，程序质量主要取决于软件设计质量，但语言特性与编码途径也会深刻影响可靠性、可读性、可测试性、可维护性。

### 1.1 程序设计语言选择
- 编码前的重要工作：选择恰当的程序设计语言；
- 语言特性会影响思维、解决问题方式、通信方式与质量、他人阅读理解难易程度。

### 1.2 程序设计风格
读程序的时间比写程序多，程序不仅自己看得懂，也要别人看得懂。风格四方面：
1. **源程序文档化**；
2. **数据说明**；
3. **语句结构**；
4. **输入/输出方法**。

### 1.3 程序复杂性度量
- 定量度量程序复杂程度，复杂度乘以适当常数可估算故障数量与工作量；
- 用于比较两个设计或算法的优劣、作为模块规模精确限度；
- 常用：McCabe 环路复杂度等。

### 1.4 编码效率
| 类型 | 要点 |
|------|------|
| 程序效率 | 执行速度与占用内存；任何对效率无重要改善、却不利简单性/可读性/正确性的方法不可取 |
| 算法效率 | 与详细设计阶段确定的算法效率直接相关 |
| 存储效率 | 选择可生成较短目标代码、存储压缩性能优良的编译程序 |
| I/O 效率 | 面向人的 I/O 要方便简单直观；面向设备的 I/O 考虑设备性能特性 |

### 1.5 编码规范要求
- 命名规范统一、有意义；
- 统一注释格式（程序开始含程序名称、功能、调用关系、设计人等）；
- 统一的代码布局与缩进；
- 避免魔法数，使用常量/枚举；
- 控制函数/方法复杂度。

## 2. 软件配置管理（SCM）

SCM 是一种标识、组织和控制修改的技术，应用于整个软件工程过程。目标：标识变更、控制变更、确保变更正确实现、向有关人员报告变更。

> 核心内容：**版本控制**和**变更控制**。

### 2.1 版本控制
- 追踪文件变更：什么时候、谁、改了文件的什么内容；
- 每次文件改变，版本号增加；
- 支持**并行开发**：解决版本同步、开发通信问题；
- 通过**分支与合并**解决多版本 Bug 修正问题。

### 2.2 变更控制
- 目的不是控制变更发生，而是**管理变更，确保变更有序进行**；
- 变更来源两类：外部变更要求（客户修改范围/需求）；内部变更要求（测试发现问题修改源码甚至设计）；
- 最难处理的是外部需求变更（概率大、工作量巨大，尤其后期）。

### 2.3 SCM 活动
| 活动 | 内容 |
|------|------|
| 软件配置管理计划 | 了解组织结构与环境联系，明确配置控制任务 |
| 软件配置标识 | 识别受控配置项，为配置项及版本建立基线 |
| 软件配置控制 | 管理软件生命周期中的变更 |
| 软件配置状态记录 | 标识、收集、维护并报告配置状态信息 |
| 软件配置审计 | 独立评价软件产品和过程是否遵从规则、标准、指南、计划、流程 |
| 软件发布管理与交付 | 创建特定交付版本，关键是软件库 |

### 2.4 SCM 与质量保证的关系
SCM 与 SQA 密切相关，帮助达成软件质量保证目标。

## 3. 常用工具与落地建议

- **版本控制**：Git（本地/集中式/分布式仓库），统一分支模型（如 main / feature / release / hotfix）；
- **CI/CD**：持续集成（构建+单元测试）、自动化发布流水线；
- **依赖管理**：锁定版本、统一构建产物可复现；
- **代码评审**：合并前必须评审，作为静态测试与质量门禁。

## 4. 编码与配置管理检查单

- [ ] 是否统一了编码规范并执行评审？
- [ ] 程序风格是否符合文档化、结构化要求？
- [ ] 是否使用版本控制管理代码、文档、配置、构建脚本？
- [ ] 是否定义了分支与合并策略？
- [ ] 是否建立并维护了基线（需求、设计、代码、测试、发布）？
- [ ] 变更是否全部通过变更控制流程？
- [ ] 是否定期开展配置审计？
- [ ] 发布版本是否可追溯、可回退？
