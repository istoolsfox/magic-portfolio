# 06 部署与交付规范

> 来源：《系统集成项目管理工程师教程（第3版）》第5章

## 1. 软件部署

软件部署是软件生命周期的重要环节（开发后期活动），通过配置、安装、激活等保障软件后续运行。部署技术影响整个软件过程的运行效率与投入成本，管理代价占软件管理开销的大部分。**软件配置过程极大影响部署结果正确性，应用系统配置是部署过程中的主要错误来源。**

### 1.1 部署风险来源
- 应用软件越来越复杂（多构件、版本、变种）；
- 应用发展很快（两版本间隔可能只有几个月）；
- 环境的不确定性；
- 构件来源多样性。

### 1.2 部署过程特征与模型
- 特征：过程覆盖度、过程可变更性、过程间协调、模型抽象；
- 抽象部署模型：应用模型、组织模型、站点模型、产品模型、策略模型、部署模型。

### 1.3 部署关注问题
安装与系统运行的变更管理、构件间相依与协调、内容发放、异构平台管理、部署过程可变更性、与互联网集成和安全性。

### 1.4 部署模式
| 模式 | 适用场景 |
|------|----------|
| 面向单机软件的部署 | 运行于操作系统之上的单机软件（安装、配置、卸载） |
| 集中式服务器应用部署 | 用户访问量小（50人以下）、硬件要求不高（中小组织、高校在线学习、实训平台） |
| 基于微服务的分布式部署 | 访问量大、并发性高、云原生应用；借助容器与 DevOps 持续部署与集成 |

## 2. 软件交付

传统交付流程：业务想法 → 开发实现 → 测试 → 用户使用收益 → 运维。

### 2.1 传统交付存在的问题
1. 需求文档沟通效率低、描述不明确、变更频繁；
2. 测试工作量渐增、自动化程度低、质量难把控；
3. 运维排期被挤占、手工运维繁琐、运维质量难保证。

### 2.2 传统交付的困境
- 表现层：进度不可控、流程不可控、环境不稳定、协作不顺畅；
- 根源层：分支冗余合并困难、缺陷过多阻塞测试、环境不统一导致未知错误、代码提交版本混乱无法回溯、等待上线周期过长、部署操作复杂常失败、上线问题需紧急回滚、架构设计不合理无法准确定位错误。

## 3. 持续交付（Continuous Delivery）

一系列开发实践方法，确保代码能快速、安全地部署到生产环境；完全自动化，业务开发完成可一键部署。

持续交付的解决要点：
- **需求阶段**：抛弃传统需求文档，使用便于开发人员理解的**用户故事**；
- **开发测试阶段**：做到**持续集成**，让测试人员尽早进入项目开始测试；
- **运维阶段**：打通开发与运维通路，保持开发环境与运维环境统一。

### 3.1 持续交付与持续部署
- 持续交付：代码随时可安全部署到生产（发布是业务决策）；
- 持续部署：通过自动化把每个通过测试的变更直接部署到生产环境。

## 4. 部署与交付规范要求

- [ ] 明确部署模式（单机/集中式/微服务分布式）并按规模选择；
- [ ] 建立统一的开发/测试/预发布/生产环境并保持配置一致性；
- [ ] 配置项（环境、参数、脚本、密钥）纳入版本与配置管理；
- [ ] 部署过程自动化（CI/CD 流水线：构建→测试→打包→发布）；
- [ ] 发布前制定回退计划与回退触发条件（详见 11 配置与变更管理规范）；
- [ ] 部署后进行验证测试（冒烟测试/验收测试）；
- [ ] 建立发布记录、版本可追溯；
- [ ] 运维移交：上线发布或运维移交按规定整理成果。

## 5. 验收与试运行要点（结合项目管理）

- 验收测试依双方合同约定的系统环境，确保功能与非功能满足需求；
- 试运行期间发现问题可能是缺陷也可能是新需求；**新需求须走变更流程，不得擅自处理**；
- 试运行期间可加载部分数据/配置进行正常操作；
- 最终验收标志项目结束与售后服务开始；由双方撰写验收报告并提请双方主管认可。
