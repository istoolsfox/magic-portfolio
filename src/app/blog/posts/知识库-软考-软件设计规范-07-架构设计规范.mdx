# 07 架构设计规范

> 来源：《系统集成项目管理工程师教程（第3版）》第4章

## 1. 架构基础

### 1.1 指导思想与设计原则
架构规划的设计原则因组织的业务战略、运营模式、信息化与数字化远景不同而异，应建立在组织的信念和价值观之上，以显性知识方式表达。原则要点：
- 为架构和规划决策、政策、程序和标准制定及矛盾局势解决提供基础；
- **原则不需要多**，要面向未来，得到高级管理人员认可、拥护和坚持；
- 太多原则会降低架构灵活性，通常限制在 **4~10 项**。

典型设计原则（参考）：坚持以人为本、坚持创新引领、坚持问题导向、坚持整体协同、坚持安全可控、坚持科学实施。

### 1.2 建设目标
建设目标是集成建设的最终目的、达到的效果、为什么服务——一种概念性方针，通常来自高层领导构想与愿景；各项业务目标均为建设目标服务。

### 1.3 总体框架（信息系统体系架构参考框架）
框架是用于规划、开发、实施、管理和维持架构的概念性结构，为架构设计提供路线图。总体框架四部分（与"管理金字塔"层次一致）：

| 层次 | 组成部分 | 对应管理层次 | 作用 |
|------|----------|--------------|------|
| 第一层 | 战略系统 | 战略管理 | 决策支持；向业务提出创新重构要求，向应用提出集成要求 |
| 第二层 | 业务系统 + 应用系统 | 战术管理 | 业务过程优化与管控；应用系统提供信息数据手段 |
| 第三层 | 信息基础设施 | 运行管理 | 提供计算、传输、数据支持 |

- **战略系统**：高层决策支持系统 + 组织战略规划体系（长期规划较稳定，短期规划易变）。
- **业务系统**：完成一定业务功能的系统（生产、销售、采购、人事、会计等），由业务过程完成功能；必要时开展**业务流程重组（BPR）**。业务系统建模 → 确定相对稳定的数据 → 开发应用系统与建设基础设施。
- **应用系统**：应用软件系统（TPS、MIS、DSS、ES、OAS、CAD/CAPP/CAM、MES 等）。从架构角度含两个基本部分：**内部功能实现部分 + 外部界面部分**。
- **信息基础设施**：分三部分——技术基础设施（计算机设备、网络、系统软件、数据交换协议等）、信息资源设施（数据与信息本身、交换标准、处理方法）、管理基础设施（组织架构、人员分工、管理方法与制度）。

## 2. 系统架构（信息系统架构）

### 2.1 架构定义与理解
信息系统架构反映组织信息系统的各组成部分之间的关系，以及信息系统与业务、技术之间的关系。理解要点：
1. 架构是对系统的**抽象**，仅外部可见属性属于架构；
2. 架构由**多个结构**组成；
3. 任何软件都存在架构，但不一定有架构描述文档（文档过时不反映架构）；
4. 元素及其行为的集合构成架构内容（静态：大粒度总体结构；动态：关键行为共同特征）；
5. 架构具有"基础"性：解决关键重复问题的通用方案（复用性）、架构敏感的重要决策（贯彻后更改代价昂贵）；
6. 架构隐含"决策"：由架构设计师根据功能/非功能需求（质量属性与约束）决策，**重大决策应经评审**。

### 2.2 架构分类
- **物理架构**：不考虑实际工作与功能，抽象考察硬件系统空间分布 → 集中式 / 分布式。
  - 集中式：资源集中、便于管理、利用率高；但规模扩大后维护困难、资源过度集中造成系统脆弱；
  - 分布式：按需配置资源、应变能力强、扩展方便、安全性好、单节点故障不致整体瘫痪；但管理标准难统一、协调困难。分布式又分一般分布式与客户端/服务器（C/S）。
- **逻辑架构**：信息系统的功能综合体和概念性框架（按管理职能划分的子系统集合）。

### 2.3 系统融合
各子系统统一规划、整体融合：**横向融合**（同层职能融合，如人事+工资）、**纵向融合**（同职能各层次融合）、**纵横融合**（信息模型+处理模型综合，信息集中共享、程序模块化、提取通用部分、建立公用数据体系）。

### 2.4 一般原理（架构的柔性）
架构包含**组成部分 + 组成部分之间的关系**。为适应环境变化：**析出相对稳定的组成部分与关系，在稳定部分支持下重组相对变化较多的部分**，从而使系统具有一定适应能力（柔性）。

## 3. 常用架构模型

| 模型 | 说明 |
|------|------|
| 单机应用 | 运行在一台物理机上的独立应用（可多进程/多线程） |
| 两层 C/S | "胖客户端"：前台客户端 + 后台数据库 |
| 三层 C/S | 前台界面与后台之间通过协议通信（Socket/消息机制/RPC/CORBA/Java RMI/JMS/HTTP）；B/S 是采用通用客户端界面的三层 C/S |
| 多层 C/S | 三层以上，实践常见四层：浏览器 → Web 服务器 → 中间件（应用服务器）→ 数据库服务器；中间件提高可伸缩性、并发性能、数据安全性 |
| MVC 模式 | 模型-视图-控制器：表示层与数据层代码分开，控制器连接不同模型与视图（J2EE: View=浏览器、Controller=Web服务器、Model=应用逻辑+持久化） |
| SOA 面向服务架构 | 将多层服务的单点应用看作一个服务，服务间通过消息/中间件通信；本质是消息机制或 RPC；实践分为异构系统集成、同构系统聚合、联邦体系结构；Web Service 是典型应用（SOAP、WSDL） |
| 组织级数据交换总线 | 不同组织应用间进行信息交换的公共通道（连接器 Connector，基于消息/交易中间件或 CORBA/IIOP），按配置或消息头进行数据/请求/回复的接收与分发 |

## 4. 架构规划与设计

集成架构随业务发展与数字化成熟度持续演进，工业企业示例：
- **以应用功能为主线架构**：中小型或数字化初级阶段，采购成套应用软件，以部门/职能为单元，核心关注软件功能（财务、设备、资产等），通过软件接口集成，统一规划、分步实施；
- **以平台能力为主线架构**：以平台为基础承载能力；
- **以互联网为主线架构**：以互联网为依托整合内外资源。

## 5. 应用架构设计原则
常用应用架构设计原则：**业务适配性原则、应用企业化原则、IT专业化原则、风险最小化原则、资产复用化原则**。

- 分层分组：应用按层次（如表现层、应用逻辑层、数据层）与业务分组组织；
- 高内聚、低耦合：系统内高内聚，系统间低耦合，减少重复建设；
- 通用能力抽取为共享/公用部分。

## 6. 数据架构设计原则
常用数据架构设计原则：**数据分层原则、数据处理效率原则、保障数据一致性原则、保证数据架构可扩展性原则、服务于业务原则**。

- 数据分层：按数据主题/层级组织（详见 08 数据工程规范）；
- 数据标准化：统一数据标准与数据模型；
- 数据共享：建立系统公用数据体系，避免重复建设。

## 7. 网络架构
网络架构围绕基础架构提供高质量服务而设计，包括：局域网架构、广域网架构、移动通信网架构、软件定义网络（SDN）等，按规模与需求选型。

## 8. 安全架构

### 8.1 安全威胁
安全威胁通常包括：硬件故障、硬件资源瓶颈（CPU/网卡带宽耗尽）、业务流量超出软件设计能力、影响系统可用性的网络攻击等。

### 8.2 安全机制与安全服务
- OSI 开放系统互联安全体系包含 **5 类安全服务**：鉴别、访问控制、数据机密性、数据完整性和抗抵赖性；
- WPDRC 信息安全体系架构模型（信息安全系统架构常用模型）包括多个环节与要素（见 09 信息安全工程规范）。

### 8.3 安全架构设计要点
- 网络安全架构设计（分层防护、访问控制、边界防护）；
- 数据库系统安全设计（数据加密、脱敏、权限控制、完整性约束）；
- 整体安全架构设计需结合威胁建模与风险分析。

## 9. 云原生架构

### 9.1 发展概述
以云计算为底座，强调弹性、韧性与自动化，通常需借助容器与 DevOps 技术进行持续部署与集成。

### 9.2 云原生架构原则
**服务化原则、弹性原则、可观测原则、韧性原则、所有过程自动化原则、零信任原则、架构持续演进原则**。

### 9.3 常用架构模式
服务化架构模式、Mesh化架构模式、Serverless 模式、存储计算分离模式、分布式事务模式、可观测架构、事件驱动架构。

### 9.4 云原生应用效益
成本（按量付费、免运维）、稳定性（高 SLA、异地备份）、效率（一站式研发运维、分钟级持续集成）、赋能业务（云组件开箱即用）。

## 10. 架构设计检查单

- [ ] 是否明确了设计原则（4~10项）并获高管认可？
- [ ] 是否定义总体框架（战略/业务/应用/基础设施）？
- [ ] 是否在静态（分层）与动态（关键行为）两方面描述架构？
- [ ] 是否选择了适配的架构模型（C/S、多层、SOA、总线、云原生）？
- [ ] 应用架构是否落实分层分组与"高内聚低耦合"？
- [ ] 数据架构是否落实分层、一致性、可扩展、服务业务原则？
- [ ] 安全架构是否覆盖鉴别/访问控制/机密性/完整性/抗抵赖？
- [ ] 云原生场景是否落实七大原则？
- [ ] 重大架构决策是否经过评审？
