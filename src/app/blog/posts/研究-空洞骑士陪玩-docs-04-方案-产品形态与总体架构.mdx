# 04 · 方案：产品形态与总体架构

> 定稿：2026-09-23（基于 01/02/03 三篇调研）。本文回答：做成什么样、怎么分层、用什么技术、复用什么资产、有哪些风险。

## 1. 产品定位

**AI 陪玩小骑士**：一个陪伴玩家通关《空洞骑士》的 LLM 角色。它「坐你旁边」：

- **看得见**：实时知道你在哪个场景、多少血、打哪个 boss、死在哪；
- **聊得来**：会打气、会安慰（空洞骑士玩家死 300 次是常态）、会剧透克制（问才说）、懂梗；
- **教得了**：报点导航（「左边墙上有条暗道」）、boss 打法提示、护符流派建议；
- **下得去场**（进阶）：能演示某个 boss 怎么打、能替你试险；
- **同屏冒险**（远期）：变成第二只小骑士，和你在同一张地图上跑跳砍。

## 2. 四种形态（渐进式选型）

| 形态 | 体验 | 技术依赖 | 工程量 | 风险 | 结论 |
|------|------|---------|--------|------|------|
| **A 教练陪伴** | 旁观游戏状态 + 聊天/提示/导航 | mod 读状态 + LLM 对话 | 小（2 周级） | 几乎零（不碰操控） | **首发** |
| **B 演示代打** | AI 操控玩家本体演示打法/替打 | 语义动作库 + 输入注入/直接调用游戏类；可选视觉兜底 | 中（3 周级） | 操作手感、出错影响玩家存档（可控） | 第二步 |
| **C 第二骑士** | AI 作为第二玩家实体同屏冒险 | HKMP addon：AI 实体接入联机同步协议 | 大（1 月级+，需读 HKMP 源码） | HKMP 无现成 bot API【待核实 addon 能力】 | 远期 spike |
| **D 丝之歌移植** | 同上体验移植到续作 | BepInEx 系生态（已启动但早期） | 跟随 A/B 重验证 | 新作版本变动频繁 | 观望 |

**推荐路线 A → B → C**：A 先建立「陪玩」的人格与感知闭环（这是粘性来源），B 建立操控底座，C 才有「一起玩」的实体感。任何一步出问题，上一步形态独立成立、可单独交付。

## 3. 总体架构（三层 + 一通道）

```

│  │ Companion Mod (C#, BepInEx/Modding API)      │                    │
│  │  · 状态采集：场景/位置/HP/灵魂/吉欧/          │                    │
│  │    boss HP/死亡/受伤/过门事件                 │                    │
```

### 3.1 游戏内 Mod 层（环境桥，参照 Mineflayer 的角色设计）

- **状态采集**：hook 游戏管理类拿权威状态【具体类名待核实，参照 DebugMod/HKMP 源码】：当前场景、玩家位置/朝向、HP、灵魂、吉欧、当前 boss 与其血量、死亡/受伤/过门/存档事件。频率：事件驱动为主 + 低频 tick（如 2–5 Hz）兜底，省性能也省 token。
- **命令接口**（按形态渐进开放）：
  - A 形态只需读 + 少量「不碰玩家」的辅助命令（如查询地图信息）；
  - B 形态开放语义动作：`move/跳/斩/闪避/治疗/回城/传送`，先由 bridge 把语义动作翻译成参数，mod 内直接调用游戏逻辑（参照 DebugMod 的实现）或注入输入；
  - C 形态开放 HKMP 实体控制。
- **通信**：mod 内起 WebSocket 服务端（或 HTTP + SSE），bridge 以 JSON 通信。帧率/延迟不是瓶颈（陪玩不需要 60fps 反馈），**可靠性**才是——掉线重连、状态对账要设计。
- **视觉兜底**：mod 侧不做；bridge 侧用系统截屏 + qwen3-vl 处理「结构化状态说不清」的画面问题（如boss招式前摇识别），按需调用降成本。

### 3.2 大脑层（LLM）

> **2026-09-23 修订**：大脑实现形态已定为「ZCode 会话 + MCP gateway」，本节描述的大脑*职责*不变（何时开口/多模型分工/人设/记忆），但*实现载体*换为 ZCode（hook 注入状态、定时自动化做主动开口），自写状态机退居备胎。详见 [06-方案-ZCode大脑-MCP路线](/blog/%E7%A0%94%E7%A9%B6-%E7%A9%BA%E6%B4%9E%E9%AA%91%E5%A3%AB%E9%99%AA%E7%8E%A9-docs-06-%E6%96%B9%E6%A1%88-ZCode%E5%A4%A7%E8%84%91-MCP%E8%B7%AF%E7%BA%BF)。

- **事件驱动的「何时开口」**（陪玩质感的核心，借鉴 omniscient-agent decider 经验）：死亡→安慰，卡关（同区域死亡≥N 次）→给提示，进新场景→好奇评论，打 boss→战况播报，闲逛→闲聊。**沉默也是行为**：默认少说，触发才说。
- **多模型分工**（Mindcraft 模式）：日常陪聊用便宜快模型；导航/攻略用强文本模型；截屏理解才调 VLM。全部可配。
- **人设**：profile 文件（参照 Mindcraft profiles）+ 少量 few-shot；性格方向待用户拍板（见 05 决策点）。
- **记忆**：三类——进度记忆（打到哪、解锁什么）、事件记忆（死亡史、卡关史）、关系记忆（聊天偏好、梗）。存储起步用 SQLite/JSON 落盘即可。

### 3.3 陪伴通道

- 起步（2026-09-23 修订）：**ZCode 会话界面本身就是聊天通道**（大脑与通道合一，零开发）；二期由 gateway 托管本地 Web 聊天页（手机/副屏打开，`hk.speak` 推送主动台词）；
- 语音（加分项，二期）：输入复用已验证的 volc-asr 链路（30h 资源包 2027-09 到期，额度充足）；输出接任意 TTS（先 edge-tts/火山 TTS 比价）。

## 4. 技术选型速断

| 组件 | 选择 | 理由 |
|------|------|------|
| Mod 框架 | BepInEx 5 为主、兼容 Modding API【M0 定】 | 丝之歌同路线，保移植；HK1 生态两者并存 |
| Mod→外部通信 | WebSocket + JSON | 跨语言、bridge 侧生态好、调试直观 |
| Bridge/大脑 | **hk-gateway（薄，Python）+ ZCode 会话当大脑**（2026-09-23 定，见 [06](/blog/%E7%A0%94%E7%A9%B6-%E7%A9%BA%E6%B4%9E%E9%AA%91%E5%A3%AB%E9%99%AA%E7%8E%A9-docs-06-%E6%96%B9%E6%A1%88-ZCode%E5%A4%A7%E8%84%91-MCP%E8%B7%AF%E7%BA%BF)）；备胎：自写 Python 循环直连 LLM API | 大脑工程量≈0，MCP 协议保证大脑可替换 |
| LLM 供应商 | **ZCode 会话内置（GLM-5.3）**；备胎大脑用 DeepSeek/Qwen 系（OpenAI 兼容） | 复用现有 ZCode 订阅；接口可换 |
| VLM | qwen3-vl 系（WR-077 验证过可用性与额度管理） | 已有实战 |
| ASR | volc-asr（已验证、已购资源包） | 零新成本 |
| 对话/事件编排 | 自写轻量状态机（不做重框架） | 陪玩逻辑清晰、可控；Mindcraft/Airi 是参考不是依赖 |

## 5. 已有资产复用清单

| 资产 | 用在哪 |
|------|--------|
| volc-asr 链路（skill + 30h 资源包） | 语音输入 |
| qwen3-vl 使用与配额经验（WR-077） | 视觉兜底 |
| omniscient-agent 的 decider（回复时机）/proactive（主动性关怀）/mood（情绪）工程经验 | 「何时开口」与陪玩质感 |
| omniscient-agent Web 聊天界面经验 | 陪伴通道 UI |
| 开源贡献的红队/预检纪律 | mod 发布前的质量流程（若开源） |

## 6. 风险与对策

| 风险 | 等级 | 对策 |
|------|------|------|
| macOS 注入不稳（Rosetta + mod） | 高（影响一切） | M0 第一天就验证；备选 Win 机器/虚拟机/云机 |
| Modding API vs BepInEx 选型反复 | 中 | M0 出结论；代码分层隔离框架依赖 |
| LLM 开口太频繁毁体验 | 高（体验层） | 「少说为佳」默认值 + 触发白名单 + 用户可调 |
| 演示形态误操作毁玩家进度 | 中 | B 形态先在「复制存档/神居」环境跑；存档自动备份 |
| HKMP addon 能力不足（C 形态） | 中 | 早期只做 spike 验证，不押注；失败则 C 降级为「影子骑士」（非联机实体，mod 内自绘第二角色）【待核实可行性】 |
| 游戏/大版本更新破坏 mod | 低-中 | 锁版本开发；丝之歌同理 |
| 成本失控（长时在线 LLM） | 低 | 事件驱动低频调用；模型分级；本地缓存攻略问答 |

## 7. 合规边界

- 单机游戏 mod：无反作弊、无联机竞技公平问题，Team Cherry 官方对 mod 态度友好【待核实官方明文】；
- 若 C 形态用到 HKMP：遵守其 LGPL-2.1 许可，addon 开源为佳；
- 攻略内容：优先引用公开 wiki，注意不整段复制受版权文本；
- 若未来开源/发布：AI 生成内容披露遵循各平台惯例（参考开源贡献手册的 AI 政策意识）。
