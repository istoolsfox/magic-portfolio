# 05 · 路线图：MVP 里程碑与决策点

> 定稿：2026-09-23。配合 [04-方案](/blog/%E7%A0%94%E7%A9%B6-%E7%A9%BA%E6%B4%9E%E9%AA%91%E5%A3%AB%E9%99%AA%E7%8E%A9-docs-04-%E6%96%B9%E6%A1%88-%E4%BA%A7%E5%93%81%E5%BD%A2%E6%80%81%E4%B8%8E%E6%80%BB%E4%BD%93%E6%9E%B6%E6%9E%84) 阅读。每个里程碑独立交付、独立验收；时间预估按业余时间节奏（非全职）。

## 里程碑总览

```
M0 环境 spike ──▶ M1 状态桥 ──▶ M2 教练形态(首发MVP) ──▶ M3 演示代打 ──▶ M4 第二骑士 spike
   (2-3天)        (1周)          (1-2周)                  (2-3周)         (远期)
```

原则：**M2 结束就应该「好玩」**——哪怕 AI 完全不碰操控，陪聊+报点+安慰已经构成完整体验。后面都是加分项。

> **2026-09-23 晚追记**：平台改为 Windows（家用机，macOS spike 取消）；mod/gateway/接线/语音代码已**盲写完成 v0.1**（gateway 在 Mac 用 `--sim` 假 mod 自测通过，mod 待真机编译）。原 M0/M1 的验证工作不消失，改为回家按 [07-搭建指南](/blog/%E7%A0%94%E7%A9%B6-%E7%A9%BA%E6%B4%9E%E9%AA%91%E5%A3%AB%E9%99%AA%E7%8E%A9-docs-07-%E6%90%AD%E5%BB%BA%E6%8C%87%E5%8D%97-Windows-%E5%9B%9E%E5%AE%B6%E6%B8%85%E5%8D%95) 一次性销账（第 3 节=M0，第 4/7 节=M1 验收）。

## M0 · 环境 spike（验证「能不能做」，2–3 天）

**目标**：把最大的不确定性（macOS 跑 mod）一次性消灭。

1. 本机装 HK1（Steam）→ 装 Lumafly → 装 DebugMod → 进游戏开调试面板，跑 30 分钟看稳定性与帧率（Apple Silicon/Rosetta）；
2. 用 dotnet 建 hello-world mod（打日志+读一次玩家位置），跑通「自写 mod 加载」；
3. mod 内起最小 WebSocket 服务，外部 Python 连上收到一条场景名消息；
4. 顺带确认 Modding API / BepInEx 在 HK1 上的共存关系，定框架选型。

**验收**：外部脚本实时收到游戏内位置/场景变化。
**若 macOS 失败**：切换 Windows 方案（虚拟机/物理机/云机），重跑本里程碑。
**产出记录**：notes/m0-spike.md（环境版本、坑、帧率数据）。

## M1 · 状态桥（「看得见」，约 1 周）

**目标**：AI 所需的感知信号全部流到 bridge。

1. 状态采集补全：场景、位置、HP、灵魂、吉欧、boss 及血量、死亡/受伤/过门/存档事件（参照 DebugMod/HKMP 源码定位游戏类【类名待核实】）；
2. 协议定稿：`state.tick` / `game.event` / `cmd.*` 三类 JSON 消息（schema 写进 docs/）；
3. hk-gateway（Python，2026-09-23 修订，见 06 文档）：WS 客户端、事件落盘（JSONL，参照 omniscient-agent games 事件做法）、重连与状态对账、**MCP server 化**；
4. 简单验收工具：终端实时打印「我死了」「进了苍绿之径」等事件流；ZCode 会话里调 `mcp__hk__get_state` 成功返回。

**验收**：完整打通一关（如苍绿之径→真菌荒地），事件流无缺漏；ZCode 通过 MCP 工具读到实时状态。

## M2 · 教练形态（首发 MVP，「聊得来」，1–2 周）

**目标**：可日常使用的陪玩体验。

1. 「何时开口」机制（2026-09-23 修订：载体 = ZCode，见 06 文档）：UserPromptSubmit hook 自动注入游戏状态（被动响应）+ 工作区定时自动化每 1–2 分钟 poll 事件（主动开口），人设约束「默认沉默」；死亡安慰 / 卡关提示（同区域死亡计数）/ 新场景评论 / boss 战况；
2. 陪聊链路：聊天通道起步直接用 ZCode 会话界面，人设 profile 写成仓库内 skill/markdown；Web 聊天页由 gateway 托管（`hk.speak` 推送，二期）；攻略知识注入（地图/boss/护符速查表，可配 WebSearch）；
3. 记忆 v1：进度（打到哪）+ 死亡史 + 聊天偏好，落盘文件/SQLite，SessionStart hook 注入开局摘要；
4. 报点/导航：基于状态的结构化提示（当前场景的隐藏通道、boss 门口提醒），攻略知识库手工整理起步；
5. 效果调优：开口频率、剧透克制（问才说、可分级）。

**验收**（真实通关测试）：从零开档，陪玩陪同打完假骑士+苍绿之径，过程中：死亡安慰≥3 次不重复、主动报点≥2 次准确、聊天响应≤3 秒、一晚上 token 成本可忽略。
**交付**：README 更新「怎么运行」，玩家（用户本人）连续使用≥3 天不弃坑。

## M3 · 演示代打（「下得去场」，2–3 周）

**目标**：AI 能操控玩家本体做演示。

1. 语义动作库 v1：移动/跳/斩/闪避/治疗/回城/传送（mod 侧实现，参照 DebugMod 能力）；
2. 安全护栏：**自动备份存档**、演示限定模式（神居/假骑士等可重打场景）、一键中断；
3. 演示链路：LLM 输出动作序列 → bridge 翻译 → mod 执行 → 状态反馈修正（简单闭环，先不做高频实时对抗）；
4. VLM 兜底实验：截屏 → qwen3-vl 识别 boss 前摇 → 建议闪避（验证视觉路线的必要性，不达标就砍）。

**验收**：在神居用演示模式打过一个简单 boss（如假骑士/Vengefly King），全程无存档损伤，观众视角能看懂 AI 在干什么（动作前有解说台词）。

## M4 · 第二骑士 spike（「同屏冒险」，远期，1 月级）

**目标**：验证 HKMP addon 路线是否成立，不承诺体验。

1. 读 HKMP 源码/docs，确认 addon API 能力边界【02 文档待核实项】；
2. 写最小 addon：让 AI 以第二个玩家实体进主机世界，同步位置/动作；
3. AI 决策驱动该实体做简单跟随/模仿动作；
4. **Go/No-Go**：若 HKMP 同步协议对「无头客户端/托管实体」不友好，评估降级方案（mod 内自绘第二角色，不走联机栈）。
