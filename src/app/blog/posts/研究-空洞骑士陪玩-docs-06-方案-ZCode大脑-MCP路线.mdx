# 06 · 方案：大脑就用 ZCode——MCP 路线（haksnbot 范式移植）

> 定稿：2026-09-23。承接 [01-先例调研](/blog/%E7%A0%94%E7%A9%B6-%E7%A9%BA%E6%B4%9E%E9%AA%91%E5%A3%AB%E9%99%AA%E7%8E%A9-docs-01-%E8%B0%83%E7%A0%94-AI%E9%99%AA%E7%8E%A9%E6%B8%B8%E6%88%8F%E5%85%88%E4%BE%8B) 与同日补充调研（Mindcraft 源码级拆解、haksnbot 全家桶直读）。回答一个问题：**大脑层不自己写循环、不绑 Claude，直接用 ZCode 会话行不行？** 结论：行，且工程量比 04 原方案小一个量级。

## 结论（先看这个）

1. 「把 AI 接入游戏」有两条先例路线：**自写循环**（Mindcraft：Mineflayer 桥 + 自研 agent 循环，LLM 只是 API）和 **MCP 路线**（haksnbot：游戏暴露成 MCP 工具，大脑直接用 Claude Agent SDK，一行决策代码不写）。
2. **ZCode 具备当 MCP 大脑的全部机制**（本会话一手验证）：MCP 客户端、hooks 注入上下文、定时自动化、技能、文件记忆、WebSearch。不需要 Claude Agent SDK，也不需要自写「何时开口」状态机 v1。
3. **决策（2026-09-23）**：大脑 = 本项目工作区里的 ZCode 常驻会话；04 方案的「Bridge+大脑(Python 自写)」降级为备胎。gateway 对外协议按 MCP 定死——**大脑可替换**是这条路线的保险：ZCode 不满意随时换回自写循环，mod 层零改动。

> **同日晚修订（用户拍板「要实时的、Windows、语音全套、盲写先行）**：①平台=家里 Windows 机；
> ②「mod↔gateway 用 WebSocket」改为**裸 TCP + NDJSON**（127.0.0.1:35516，盲写零依赖更稳）；
> ③实时性按三层实现——**Tier-0 gateway 反射层**（死亡/残血/boss 结束 \<1s 固定台词开口，不等
> 任何 LLM）、**Tier-1 ZCode**（hook 每轮注入状态 + Stop hook 朗读回复）、**Tier-2 速答**
>（按住 F9 说话：ASR(volc)→LLM→TTS，与 ZCode 共享 brain/ 人设记忆，可选启用）；
> ④全部代码 v0.1 已盲写并入库（gateway 侧经 `--sim` 自测通过），真机步骤见
> [07-搭建指南](/blog/%E7%A0%94%E7%A9%B6-%E7%A9%BA%E6%B4%9E%E9%AA%91%E5%A3%AB%E9%99%AA%E7%8E%A9-docs-07-%E6%90%AD%E5%BB%BA%E6%8C%87%E5%8D%97-Windows-%E5%9B%9E%E5%AE%B6%E6%B8%85%E5%8D%95)。

## 1. 先例复盘：两条路线的源码级事实

| | 路线一：Mindcraft（自写循环） | 路线二：haksnbot（MCP） |
|---|---|---|
| 大脑 | 自研 Node.js agent 循环，Claude/GPT 等只是被调用的模型 | Claude Agent SDK 本尊，零决策代码 |
| 游戏接口 | Mineflayer（MC 多人协议库） | haksnbot-tools：Mineflayer 包成 MCP server（40+ 工具，stdio） |
| LLM→动作 | LLM 回复嵌 `!命令(参数)` 文本，正则解析后查本地命令表执行（约 40 动作 + 8 查询） | LLM 调 MCP 工具（chat / craft_item / place_block…） |
| 高频反应 | 全走 LLM | **不走 LLM**：haksnbot-guts（吃饭/逃跑）+ haksnbot-body（寻路/跟随）当「脊髓反射」 |
| 感知 | 每轮把方块/实体/背包/血量/聊天序列化进 prompt | 事件驱动：chat-poll.sh 盯服务器日志（聊天/进出/死亡/成就）→ 喂给 agent |
| 记忆/人设 | 落盘历史 + embedding 检索示例 + profile JSON | prompts/*.md + docs/*.md 按字母序拼系统提示词 |

来源：Mindcraft 源码直读（`src/agent/commands/index.js` 的命令正则与命令表、`src/models/prompter.js` 的 prompt 组装、`src/agent/self_prompter.js` 三态自驱循环）[实锤]；haksnbot README 直读 [实锤]。

**对本项目的关键启示**：haksnbot 证明「游戏 = MCP 工具集，大脑 = 现成 agent 运行时」成立；它的 guts/body 分层（高频反应走规则、LLM 只做决策）正是咱们 mod 语义动作该扮演的角色。

## 2. ZCode 版架构

```
┌──────────────────────────────────────────────────────────────┐
│ 《空洞骑士》+ Companion Mod (C#, 内嵌 WebSocket 服务)         │  ← 与 04 方案完全相同
└────────────────────────▲─────────────────────────────────────┘
                         │ WS: state.tick / game.event / cmd.*
┌────────────────────────┴─────────────────────────────────────┐
│ hk-gateway（Python 常驻进程，≈300 行级）                     │
│  · WS 客户端 + 重连/对账      · 事件缓冲 + JSONL 落盘        │
│  · MCP server（stdio）：把状态/动作暴露成 mcp__hk__* 工具    │
│  · 可选：Web 聊天页（手机/副屏），供 hk.speak 推台词         │
└────────────────────────▲─────────────────────────────────────┘
                         │ MCP (stdio)
┌────────────────────────┴─────────────────────────────────────┐
│ ZCode 会话 = 大脑（本项目工作区）                             │
│  · 被动响应：UserPromptSubmit hook → 注入最新游戏状态        │
│    （玩家每说一句话，上下文自动带状态，无需主动查询）         │
│  · 主动开口：工作区定时自动化（每 1–2 分钟 poll 事件，        │
│    按人设决定说话或沉默——「沉默也是行为」）                  │
│  · 现成能力：WebSearch 查攻略、文件记忆、skills、node_repl   │
└──────────────────────────────────────────────────────────────┘
```

### 三个核心机制（均一手验证）

1. **MCP 客户端**：工作区 `<repo>/.zcode/config.json` 写 `mcp.servers`，stdio 起 gateway（`command` 用绝对路径——配置文件不展开模板变量），会话启动自动连接，工具以 `mcp__hk__*` 出现。状态查看/修复走 设置 → MCP。[实锤：zcode-guide 官方插件文档 + 本会话正挂着 feishu/notion 等 MCP]
2. **hook 注入**：`hooks.events.UserPromptSubmit` 配一个脚本（curl gateway 的 HTTP 端点），输出 JSON 的 `additionalContext` 字段会被注入对话——**这就是「陪玩睁着眼睛」的实现**，每次玩家开口都自动看到实时血量/场景/最近事件。`SessionStart` hook 同理可注入开局摘要。注意：配置文件 hooks 需显式 `hooks.enabled: true`。[实锤：zcode-guide 官方插件文档，七个事件名与输出 schema 均确认]
3. **定时自动化**：工作区支持 cron 式计划任务（每 N 分钟一条 prompt 在会话内执行、带完整对话历史），做「主动关怀」：死亡安慰、卡关提示、boss 战报。轮询粒度即主动性延迟上限（约 1 分钟级，陪玩场景可接受）。[实锤：本会话即有该工具]

## 3. hk-gateway MCP 工具清单 v0（草案）

| 工具 | 形态 | 说明 |
|------|------|------|
| `hk.get_state()` | A 起 | 全量快照：场景/位置/HP/灵魂/吉欧/当前 boss 血量 |
| `hk.poll_events(since?)` | A 起 | 自上次以来事件队列：死亡/受伤/过门/进 boss/存档 |
| `hk.history(scene?, boss?)` | A 起 | 落盘数据查询：该场景死亡次数、boss 尝试次数 |
| `hk.speak(text, tone?)` | A 起 | 往 Web 聊天页推一句台词（主动开口的出口） |
| `hk.do_action(name, params)` | B 起 | 语义动作：移动/跳/斩/闪避/治疗/回城/传送 |
| `hk.backup_save()` / `hk.restore_save()` | B 起 | 演示前后护栏 |

原则：工具少而粗（状态一把抓、动作按语义），细节留给 prompt 与 hook 注入——**接口越粗，大脑越省 token**（Mindcraft 40+ 命令的教训：命令表本身就要吃掉一大截 prompt）。

## 4. 与 04 原方案的关系（修订而非推翻）

- **不变**：三层结构、mod 层设计（状态采集/命令接口/WS 通信）、四形态路线、风险对策。
- **替换**：原「Bridge + 大脑（Python，自写状态机 + 直连 LLM API）」→「hk-gateway（薄）+ ZCode 会话（大脑）」。
- **收益**：M2 的三大自研件（「何时开口」状态机、聊天链路、Web UI）全部消失——状态机由「定时 prompt + 人设约束」承担，聊天通道起步直接用 ZCode 界面本身，Web 页后置为 `hk.speak` 的展示端。
- **备胎**：若 ZCode 长程陪玩不可靠（见风险），gateway 协议不变，另写一个吃同样 MCP/WS 接口的薄循环（DeepSeek/Qwen API）替换大脑。**MCP 化的意义就是大脑可替换。**

## 5. 风险与对策

| 风险 | 等级 | 对策 |
|------|------|------|
| 主动性延迟（cron 粒度 ~1 分钟） | 低 | 陪玩非实时对抗；死亡安慰在玩家下次开口时 hook 注入即时补发 |
| 长会话 context 膨胀 | 中 | 一局一 session；记忆落盘文件（进度/死亡史/偏好），SessionStart hook 注入摘要 |
| ZCode 版本演进（hooks/MCP schema 变动） | 中 | gateway 接口稳定；升级前跑验收脚本；大脑可替换 |
| 语音通道（ZCode 无原生 ASR/TTS） | 低 | 二期仍走 gateway + volc-asr / TTS，与大脑解耦 |
| token 成本（高频轮询 + hook 注入） | 低 | hook 注入只带增量摘要；cron prompt 明确「无事件则沉默」；ZCode 订阅内使用 |
| 玩家不开 ZCode 就没陪玩 | 低 | 本来就是「坐在电脑前开着一局」的场景；远期再考虑 headless 自写循环 |

## 6. 对 05 路线图的影响

- **M0 不变**（环境 spike 与大脑路线无关，仍是第一优先级）。
- **M1**：交付物从「Python bridge」改为「hk-gateway」——WS 客户端 + 事件 JSONL 落盘 + MCP server 化（验收：ZCode 会话里能调 `mcp__hk__get_state`）。
- **M2**：新增工作区配置件——`.zcode/config.json`（gateway 挂载）、`hooks`（UserPromptSubmit/SessionStart 注入脚本）、人设 profile（写成仓库内 skill 或 markdown）；验收标准不变（死亡安慰≥3、报点≥2、响应≤3 秒、连续使用≥3 天）。
- **决策点销账**：「首发 LLM 供应商」已定（ZCode 会话即大脑，GLM-5.3）；DeepSeek/Qwen 直连仅作为备胎大脑的选型，推迟到需要时再议。
